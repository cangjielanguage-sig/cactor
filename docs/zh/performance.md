# CActor 性能调优指南

本文说明如何让基于 CActor 的程序跑得更快，以及如何为 CActor 本身做性能优化。
文中的数字都来自仓库里的基准程序（见 §6），测试机器为 32 核 Intel Xeon、仓颉 1.2.0，换一台机器会有差异。
与 Akka 的同机对比和问题定位的完整过程，见 [性能分析](../plan/20261028-performance.md)。

## 1. 当前性能水平

| 场景 | CActor | Akka 2.6.21（同机，已预热） |
|---|---|---|
| 单 Actor 吞吐 | 5.6–7.2 M msg/s | 2.7–3.4 M msg/s |
| 扇出（8 发送方 × 100 Actor） | 2.5–4.5 M msg/s | 9.1–11.9 M msg/s |
| ping-pong 往返 P50 / P99 | 1.9–4.0 / 2.7–11 µs | 3.0 / 5.9–6.7 µs |
| Ask 往返 P50 / P99 | 5.0–6.0 / 11–13 µs | 8.8 / 10–16 µs |
| 远程 TCP（本机回环） | 146–194 k msg/s | 约 308 k msg/s |

可以看出：

- **点对点**（一个发送方对一个 Actor、请求-应答）已经不弱于 Akka。
- **大量发送方对大量 Actor 的扇出**和**远程**仍然明显落后，原因见性能分析 §3.4、§3.5。

如果你的负载以扇出或远程为主，需要预期这部分差距。

## 2. 第一步：确认开启了编译优化

这是收益最大、也最容易漏掉的一项：**cjpm 默认不传 `-O` 参数，cjc 默认是 `-O0`**，产物放在 `target/release` 下也一样。

CActor 自己的 workspace 已经在 `cjpm.toml` 中配置了：

```toml
compile-option = "-O2 -Woff unused -Woff parser --diagnostic-format=noColor"
```

**你自己的工程也要配置**。依赖 CActor 的应用工程，它自己的代码同样默认是 `-O0`：

```toml
[package]          # 或 [workspace]
compile-option = "-O2"
```

可以这样确认是否生效：

```bash
cjpm build -V 2>&1 | grep -o "cjc .*" | head -3   # 每条 cjc 命令里应该有 -O2
```

实测效果（同一份代码，只改编译选项）：

| | -O0 | -O2 |
|---|---|---|
| 远程 TCP 吞吐 | 47 k/s | 175 k/s（3.6 倍） |
| 扇出吞吐 | 0.55 M/s | 0.72 M/s |
| 接口调用 | 11 ns | 0.2 ns（去虚化后内联） |
| 不逃逸的对象分配 | 9.8 ns | 被消除 |

## 3. 运行时参数

所有参数都通过环境变量设置，在进程启动时读取一次。

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `CACTOR_DISPATCHER_THREADS` | CPU 核数的 1/4（4–64） | 执行 Actor 的工作线程数 |
| `CACTOR_DISPATCHER_SPIN_US` | `50` | 工作线程空闲后自旋多少微秒再休眠 |
| `cjProcessorNum` | CPU 核数 | 仓颉运行时最多同时运行的线程数（最大为核数的 2 倍） |
| `cjHeapSize` | 256MB（物理内存不足 1GB 时为 64MB） | 仓颉堆的上限 |
| `cjStackSize` | 128KB | 每个仓颉线程的栈大小 |

示例：

```bash
CACTOR_DISPATCHER_THREADS=8 CACTOR_DISPATCHER_SPIN_US=50 ./your_app
```

### 3.1 工作线程数：不是越多越好

每个 Actor 在创建时按顺序固定分配给一个工作线程（亲和调度）。线程多了，每个线程分到的 Actor 少，空闲、休眠、唤醒会更频繁，扇出反而会变慢。

实测（32 核，空闲自旋 50µs；4 和 8 各跑 4 次，16 跑 2 次，32 跑 1 次）：

| `CACTOR_DISPATCHER_THREADS` | 单 Actor | 扇出 | ping-pong P99 |
|---|---|---|---|
| 4 | 4.6–7.2 M/s | 2.3–7.7 M/s（波动很大） | 2.2–2.7 µs |
| 8（默认） | 5.3–6.1 M/s | 2.7–4.8 M/s | 3.2–11 µs |
| 16 | 4.7–4.8 M/s | 1.3–1.6 M/s | 2.7–10 µs |
| 32 | 8.1 M/s | 1.4 M/s | 2.6 µs |

可以看出：

- 16 和 32 个线程时，扇出稳定地降到 1.3–1.6 M/s。
- 4 和 8 之间没有稳定的优劣，运行间波动比两者的差别还大。
- 单 Actor 吞吐和 ping-pong 延迟基本不受线程数影响。

建议：

- 先用默认值。
- 不要随着核数增加而盲目加大线程数。只有在你自己的压测中确认有收益时，才调整线程数。
- 同一进程里还有其他 CPU 密集的仓颉线程（如发送方、I/O）时，线程数更要保守。

### 3.2 空闲自旋：用 CPU 换延迟

工作线程没活时，先自旋 `CACTOR_DISPATCHER_SPIN_US` 微秒，再进入休眠。一次休眠后的唤醒约需 1.4–2.6 µs，并且尾延迟会明显变差。

实测（32 核，8 个工作线程；50µs 跑 2 次，其余各 1 次）：

| `CACTOR_DISPATCHER_SPIN_US` | ping-pong P50 / P99 / P99.9 | Ask P50 | 代价 |
|---|---|---|---|
| 0 | 20.9 / 140 / 8418 µs | 27.8 µs | 空闲时几乎不占 CPU |
| 20 | 2.1 / 2.7 / 12.9 µs | 5.0 µs | 消息间隙最多空转 20 µs |
| 50（默认） | 2.0–4.0 / 3.2–11 / 17–27 µs | 5.2–5.3 µs | 最多空转 50 µs |
| 200 | 4.0 / 10.4 / 18.4 µs | 5.4 µs | 最多空转 200 µs |

可以看出：

- 关闭自旋（0）后，延迟变差约 10 倍，P99.9 达到毫秒级。
- 只要自旋时长在 20µs 以上，延迟就差不多：20、50、200 之间的差别小于运行间的波动。
- 吞吐基本不受这个参数影响。

建议：

- **延迟敏感**（交易、游戏、RPC）：保持默认值。加大到 200 没有带来可测量的收益。
- **CPU 紧张或共享机器**（后台任务、批处理、和其他服务混部）：可以降到 20；降到 `0` 能省下更多空闲 CPU，但请求-应答类延迟会变差约 10 倍。
- 无论设多少，休眠中的工作线程都会每 10ms 醒来检查一次，所以空闲进程不会完全零 CPU。

### 3.3 仓颉运行时参数

- `cjProcessorNum`：一般保持默认。把它调得比工作线程数还小，会限制整个进程的并行度。
- `cjHeapSize`：实测从 256MB 调到 2GB，对上述基准没有可测量的影响。如果你的消息很大、或者 Actor 状态很多，导致 GC 频繁，可以加大；先用 `MRT_REPORT=<路径>` 输出 GC 日志，确认是 GC 的问题再调。
- 更多参数见 [仓颉运行时环境变量](https://docs.cangjie-lang.cn/en/docs/1.0.0/user_manual/source_en/Appendix/runtime_env.html)。

## 4. 编写 Actor 的性能规则

### 4.1 不要在 `receive` 里阻塞

`receive` 在工作线程上执行，一个工作线程上有很多 Actor。阻塞会占住这个线程，**同一线程上的所有 Actor 都会停住**。

下列操作都会阻塞：

- `sleep`。
- 同步文件或网络 I/O。
- 等待 `Future.get()`。
- 等待锁或条件变量。
- `AskFuture.get()` 和 `await()`。
- `RemoteActorRef.tell`：远程发送是同步写 socket，网络慢的时候会阻塞。

其中，**在 `receive` 中阻塞地 ask 另一个 Actor 可能卡到超时**：如果目标 Actor 恰好和自己分在同一个工作线程上，它要等当前 `receive` 返回才能运行，而当前 `receive` 又在等它。实测：

| 情况 | 结果 |
|---|---|
| 两个 Actor 分在不同的工作线程上 | 68 µs 拿到应答 |
| 两个 Actor 分在同一个工作线程上 | 等满 2 秒，超时失败 |

两个 Actor 是否分在同一个线程，取决于它们的创建顺序，不能指望。正确的写法有两种。

一是用回调，不要阻塞等待：

```cangjie
askManager.ask(target, request).onComplete({ r =>
    // 回调中不要直接修改 Actor 状态（它可能在其他线程执行），
    // 而是把结果作为一条消息发回给自己
    selfRef.tell(ResultMessage(r))
})
```

二是直接用 tell 加回复消息：请求里带上自己的引用，对方处理完以后 `tell` 一条回复回来。这是 Actor 模型最自然的方式，开销也最小。

确实需要做阻塞 I/O 的话，用 `spawn` 把它放到单独的仓颉线程去做，完成后用 `tell` 把结果发回来。

### 4.2 Ask 比 tell 贵得多

| 操作 | 开销 |
|---|---|
| `tell` | 发送方耗时约 0.15 µs/条（单 Actor 场景，100 万条约 150 ms） |
| ask 往返 | P50 约 5 µs，并且每次会创建请求 ID、临时应答引用和 Future |

只在系统边界（例如 HTTP 请求进来、需要等待结果）使用 ask；Actor 之间的交互用 tell。

### 4.3 热路径上不要打日志

一次字符串插值（`"actor-${id} ..."`）约 60–90 ns，比投递一条消息的开销还大，`println` 还要加上 I/O。高频消息的处理逻辑中不要 `println`，也不要拼接调试字符串。

### 4.4 消息设计

- 消息对象尽量**不可变**。不可变的消息可以复用，例如基准里同一个 `StringMessage` 实例发了 100 万次。
- 一次分配约 7.5 ns，不需要为了省分配做对象池。但也不要每条消息里放大块的拷贝数据，例如把整个数组复制一份。
- 跨节点的消息只能是可序列化的类型。自定义消息要注册编解码器（`MessageCodecRegistry`），并且尽量让编码结果紧凑，因为远程吞吐目前受每条消息一次 `write` 限制。

### 4.5 热点 Actor 要拆分

单个 Actor 是串行执行的，上限约为 6–7 M msg/s（处理逻辑为空时）。处理逻辑越重，上限越低。所有请求都打到同一个 Actor 时，它就是瓶颈：

- 按 key 把状态拆到多个 Actor 上，比如按用户 ID 取模分片。
- 读多写少的数据，可以复制给多个只读 Actor。

拆分后会变成扇出的形态，而扇出目前比 Akka 慢（§1），要压测确认收益。

### 4.6 不要按请求创建 Actor

创建 Actor 要加多把锁、检查重名、登记注册表、执行 `preStart`，比发送一条消息重得多。长期存在的实体用长期存在的 Actor；短任务直接用消息或 `spawn`。

## 5. 目前不生效的配置

以下 API 或配置存在于代码中，但**目前不会改变消息的处理方式**。不要指望通过它们调优：

| API / 配置 | 实际情况 |
|---|---|
| `actorOfWithMailbox`、`Props.withMailbox(...)` | 只记录名字；所有 Actor 都使用同一种邮箱（无锁 MPSC） |
| `actorOfWithDispatcher`、`Props.withDispatcher(...)` | 只记录名字；所有 Actor 都由同一个亲和调度器执行 |
| `runtime.dispatcher.*`、`runtime.mailbox.*` 下的各种调度器和邮箱实现（WorkStealing、Batching、RingBuffer 等） | 不在主消息路径上 |
| `HighPerformanceActorSystemConfig` 等配置预设 | 不影响主消息路径 |
| 每个 Actor 每次最多处理的消息数（64） | 硬编码在 `SimpleUserActorRef.THROUGHPUT`，不能配置 |

这些重复实现会在去重阶段收敛或删除（见 [开发计划](../plan/20261028.md) M3）。

## 6. 如何测量

```bash
source ~/.cangjie/1.2.0/cangjie/envsetup.sh
cjpm build
./target/release/bin/cactor_examples.real_benchmark     # CActor 端到端
./target/release/bin/cactor_examples.micro_benchmark    # 仓颉原语的单次开销
bench/akka/run.sh 3                                      # Akka 对比（需要 JDK 17+）
bench/compare.sh                                         # 两边依次运行，结果保存到 bench/results/
```

注意事项：

- **机器要空闲**。机器上有编译等其他负载时，两边的数字都会大幅下降。曾有一次在负载约为 32 的机器上跑，远程吞吐从约 150k 掉到 56k。
- **至少跑 3 次**。M:N 调度下运行之间的波动比较大，例如扇出在 2.5–4.5 M/s 之间。看范围，不要只看一次的结果。
- **Akka 要预热**。取最后一轮；第一轮的数字比预热后低几倍。
- **测你自己的负载**。基准里的 Actor 几乎不做事。真实业务的处理逻辑通常比消息投递更重，这时瓶颈往往在业务代码里。
- 调参时一次只改一个参数，每次修改后都重新测量。

更多说明见 [bench/README.md](../../bench/README.md)。

## 7. 为 CActor 本身做优化

### 7.1 流程

1. **先测量，再修改**：用 `real_benchmark` 找到慢的场景。
2. **用微基准定位原因**：在 `micro_benchmark` 里加一个只测可疑原语的小用例，例如某个队列、某次唤醒。这次定位到的问题都是这样找出来的：
   - `ConcurrentLinkedQueue` 一次入队加出队需要 190 ns，自写的 MPSC 只要 36 ns。
   - 全局就绪队列在线程多时争用崩溃。
   - 自旋挡住了被唤醒的线程。
3. **修改，然后跑全部测试**：`cjpm test` 全部通过，尤其是 `unit/runtime/concurrency` 下的并发语义测试。
4. **再跑基准，至少 3 次**，并对照 Akka。把结论和数字写进 [性能分析](../plan/20261028-performance.md)。

### 7.2 热路径规则

主消息路径位于 `modules/runtime/src/guardian/runtime_user_guardian.cj`：`tell` → `CellMailbox` → `ActorCellDispatcher` → `run` → `invoke`。

- **每条消息的分配次数**是主要成本。目前每条消息要分配：邮箱节点及其中的原子引用；调度时的 `RunNode` 及其中的原子引用；以及 `SimpleUserActorContext`。仓颉的原子类型是独立的堆对象，不能像 JVM 那样作为字段嵌入节点，所以每多一个原子字段就多一次分配。
- **不要用标准库的并发容器做热路径**：`ConcurrentLinkedQueue` 一次入队加出队约 190 ns，`LinkedBlockingQueue` 约 300 ns。
- **CAS 之前先读**：标志已经设置时，先读只要 2 ns；直接 CAS 要 9 ns，并且会让缓存行在核之间来回同步。
- **自旋要按时间限制，不要按次数**。按次数时，代码一变快，自旋时间就跟着变短，尾延迟会悄悄变差。
- **无锁算法中需要等待其他线程的地方，不要原地自旋**：在 M:N 调度下，你等的那个线程可能正排在你所在的处理器上。应该返回并稍后重试，或者让出处理器。
- **一个线程休眠前要考虑谁来唤醒它**：被 `notify` 唤醒的仓颉线程，可能要等唤醒者所在的处理器空出来才能运行。等待方先短暂自旋（如 `Completion.await`），可以避免这个延迟。
- **热路径上不要 `println`，也不要拼接字符串**。

### 7.3 尚未完成的优化方向

| 方向 | 预期收益 |
|---|---|
| 远程出站写合并，接收端批量解析多帧 | 远程吞吐追平 Akka |
| 减少每条消息的分配：复用就绪节点，或把 Cell 本身作为侵入式节点 | 扇出吞吐 |
| 在亲和调度上增加工作窃取 | 负载不均时的吞吐 |
| 独立的阻塞调度器（阻塞 I/O、FFI 专用） | 避免阻塞拖慢普通 Actor（§4.1） |
| 评估 `--lto=thin` 和 PGO（`--pgo-instr-gen` / `--pgo-instr-use`） | 跨包内联、热点去虚化 |
