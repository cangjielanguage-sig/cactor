## 0. 结论

1. **技术内核已有竞争力，产品可信度还不够。**
   - 内核：单机运行时的延迟、创建速度和规模已接近一线框架。ping-pong P50/P99 为 1.0/2.0 µs，每 Actor 约 1.2 KB，500 万 Actor 规模验证通过。
   - 可信度：按 20261106 审计，生产代码中约一半是零引用或假实现；远程没有 TLS 和鉴权；持久化没有 fsync；没有 CI 流水线，也没有发布 tag。
   - **今天的 CActor 可以演示、可以试点，但还不能对生产做承诺。**
2. **最大的价值是「补空白」，而不是「抢存量」。**
   - 仓颉语言白皮书曾规划内置 Actor，但现行语言规范中没有这部分内容（外部）。
   - CActor 在 Cangjie-SIG 名下，是仓颉生态中功能覆盖最完整的 Actor 运行时（判断，AP5 核实），包括监督、类型化、远程、集群、分片、CRDT 和事件溯源。
   - 用仓颉编写的高并发有状态服务和多 Agent 系统，都需要这一层。
3. **国产替代的主战场是「新建的仓颉原生系统」。**
   - 已有的 Akka 系统要替换，代价最小的选择是 Apache Pekko：语言相同，API 相同。换成 CActor 就等于换语言。只有当系统本来就要迁到仓颉或鸿蒙技术栈时，这条路才成立。
   - CActor 的替代价值在于：仓颉/鸿蒙技术栈不必为了 Actor 能力退回 JVM、.NET 或 BEAM。
4. **首选落地方向是 AI Agent 运行时**，其次是鸿蒙端云协同和信创实时后端。
   - 业界正在形成「用 Actor 承载 Agent」的共识：AutoGen 0.4 的核心层就是 Actor 模型；Akka 于 2025 年 7 月推出了 Agentic 平台（外部）。
   - 仓颉侧已有 Cangjie Magic 负责「Agent 怎么写」，缺的是「Agent 怎么跑」，也就是并发、隔离、容错、持久化和分布式。这正是 CActor 的定位。
5. **商业化路径：先建立信誉，再谈收入。**
   - CActor 采用 MIT 许可，库本身不收费。收入只能来自技术支持订阅、行业方案、企业合规增强、培训和生态资助。
   - 前提有三条：2.0.0 冻结 API；分布式与持久化可信；有 1–2 个灯塔案例。
   - ROADMAP 估算单人需要 40–45 人周，再叠加本文的 C 线。判断最早在 2027 年下半年具备条件。
6. **下一步（§6）**：
   - C0 可信基线：与 M0/M1 合并推进；
   - C1 Agent 运行时 MVP：同时做 Cangjie Magic 适配 PoC 和 OpenHarmony / 鲲鹏平台验证；
   - C2 生产可信与信创适配；
   - C3 灯塔试点，发布 2.0.0。

### 1.2 能力成熟度

分级口径：
- **L3 可试点**：在主消息路径上生效，有语义测试，主要语义与 Akka 对齐；
- **L2 可演示**：能跑通，但有已知缺陷，或语义与 Akka 有偏差；
- **L1 原型**：实验性实现；
- **L0 缺失**。

| 能力 | 等级 | 说明（缺口对应的 E 项） |
|---|---|---|
| 单机运行时（邮箱、调度、生命周期） | L3 | 性能见 §1.3；扇出是短板；`receive` 中做阻塞调用必须改用 blocking 调度器 |
| 类型化 API（behaviors、timers、stash、ask、adapter、拦截器） | L3 | 缺：按嵌套层级匹配监督规则、ChildFailed、SpawnProtocol（E36、E63） |
| DSL（枚举即协议、`@actor`、`@Message`、`@StateMachine`、时间字面量、`<<`） | L3 | 仓颉独有的卖点：编译期穷尽检查 |
| 监督与失败语义 | L2→L3 | 启动失败默认 Stop、退避已统一（E27、E6′，待提交）；DeathWatch 时序和「重启前等子 Actor 停完」尚未对齐（E32、E33） |
| 测试工具（BehaviorTestKit、ManualTime、TestProbe） | L2 | ManualTime 驱动不了真实运行时（E52）；缺类型化 TestProbe（E62） |
| 可观测性（结构化日志、Prometheus、健康检查） | L2 | 没有追踪；直方图格式不规范（E45） |
| 路由 | L2 | 已止血（E25）；路由器本身还不是 Actor（E37） |
| 远程 | L2 | 已有远程 ask、watch 和可靠投递；缺 TLS 和鉴权，connect 会阻塞调用线程（E40、E7′、E65） |
| 集群（成员、SBR、Singleton、PubSub、分片、Grains、CRDT） | L1–L2 | 功能面广，但存在以下问题：<br>• 没有 UID，也没有鉴权；<br>• 分片移交没有握手；<br>• 一个节点不可达就导致全局缓冲；<br>• CRDT 崩溃根因未明（N0） |
| 持久化（事件溯源、快照、DurableState） | L1–L2 | 没有 fsync，记录不带 seqNr，4 套 API 并存；没有类型化持久化（E8′、E44） |

| HTTP | L0–L1 | 只有提供健康检查和指标的 ManagementServer；HTTP 服务端、客户端和 WebSocket 都未开始（ROADMAP 1.4.0 / 1.6.0） |
| Agent 原语（取消、流式回复、持久化 reminder、LLM 客户端） | L0 | 见 E61；现有 Agent 示例中的工具全是模拟的（`best10_agent_workflow`、`dsl_agent`） |

> **口径警示**：上表多数数据测于负载 21–80 的 macOS 开发机上。ROADMAP §2.2 已注明需要在空闲机器上复测（E53）。扇出在 perf20261101 之后又有 +42% 的改进，但还没有和 Akka 同机复测。**对外宣传前必须先完成 AP3 复测**；每 Actor 内存仍约为 Akka 的 2 倍，不能说成「全面领先」。

非性能优势：

- **AOT 编译**：没有 JIT 预热，启动快，尾延迟稳定，适合边缘侧、端侧和短生命周期服务。
- **枚举即协议**：配合 `@actor` 宏，在编译期发现漏处理、协议漂移和重复处理器，保障程度与 Scala sealed trait 相当。
- **中文优先**：中文文档和注释，托管在国内平台，国内团队上手成本低。
- **MIT 许可**：没有许可证风险，可闭源商用。

### 1.4 制约商业落地的短板

按对商业化的阻碍程度排序：

1. **可信度**：约 3.8 万行零引用或假实现代码；P0/P1 问题没有清零；历史上文档与代码多次不一致（20261106 §0）。一旦被用户发现，信誉会一次性受损。
2. **安全**：没有 TLS；`$sys`、成员协议和管理端口都没有鉴权。任何跨机部署都不能进生产网络。
3. **数据持久性**：没有 fsync，无法承诺「已确认的数据不丢」。
4. **发布工程**：没有流水线、tag 和 API 兼容检查，也没有发布到中心仓，企业无法做依赖管理和版本审计。
5. **生态依赖**：HTTP 服务端/客户端、WebSocket、MQTT 和数据库驱动都依赖仓颉生态，自建成本高。
6. **平台**：只在 Linux x86_64 和 macOS arm64 上运行过。多线程自旋带来的能耗（perf20261101 §D）在端侧是硬伤。
7. **人力**：只有 1 个贡献者，做不出任何支持承诺。

## 2. CActor 能做什么

一句话概括：把**数量大、长期存活、有状态、会失败、可能分布在多台机器上的实体**，变成可组合、可监督、可测试的程序单元。

### 2.1 能解决的问题

| 典型问题 | 传统做法的痛点 | CActor 的做法 | 对应能力（成熟度） |
|---|---|---|---|
| 百万级有状态实体（会话、设备、玩家、订单） | 共享内存加锁，或每次都读写数据库 | 一个实体一个 Actor，状态常驻内存，串行处理，不需要锁 | `typedActorOf`、Grains、分片（L3 / L1–L2） |
| 长流程、多步骤、等待外部事件 | 轮询数据表、回调嵌套、超时逻辑散落各处 | 用「行为切换 + 定时器 + stash」表达状态机 | `withTimers`、`withStash`、`@StateMachine`（L3） |
| 外部依赖不稳定（LLM、第三方 API、设备） | `try/catch + sleep` 散落在业务代码中 | 声明式的监督树、指数退避和断路器 | `supervise(...).onFailure(restartWithBackoff)`（L3，待提交） |
| 过载保护 | 线程池被打满、OOM | 有界邮箱，配合溢出策略：丢弃、失败或阻塞 | 有界邮箱（L3） |
| 从单机扩展到多机 | 重写成 RPC 服务 | 位置透明的 tell / ask / watch；集群分片按实体 ID 路由 | remote、cluster（L2 / L1–L2） |
| 全局唯一的协调者 | 依赖 ZooKeeper / etcd 选主 | Cluster Singleton 加脑裂处理 | `membership/singleton.cj`（L2） |
| 状态需要可回放、可审计 | 业务表与审计表双写 | 事件溯源加快照 | `EventSourcedActor`（L1–L2） |
| 多副本、最终一致的小数据（配置、计数、在线集合） | 引入外部 KV 存储 | CRDT 加 Replicator | `cluster/ddata`（L1） |
| 并发逻辑的确定性测试 | 靠 sleep 赌时序 | BehaviorTestKit 加 ManualTime | `cactor_testkit`（L2） |

### 2.2 不适合做的事

- **硬实时控制**：有 GC，调度不具确定性。
- **大规模批量数据计算**：这是 Spark / Flink 的领域。
- **跨实体强一致事务**：例如账务核心。Actor 只保证单个实体内的串行一致性，不提供分布式事务。
- **CPU 密集的单任务并行**：直接用仓颉的 `spawn` 或线程池即可。

## 3. 商业价值分析

### 3.1 受益方与价值形式

| 受益方 | 得到什么 | 价值形式 |
|---|---|---|
| 仓颉 / 鸿蒙生态（华为、Cangjie-SIG） | 补齐「高并发有状态服务」和「多 Agent 运行时」这块基础设施，可以证明仓颉能写出 Akka / Orleans 级别的系统 | 生态完整性，战略价值 |
| 采用仓颉的企业和 ISV | 不必自研并发、容错和分布式底座；一套编程模型覆盖端（鸿蒙）、边、云 | 降低研发成本，提高稳定性 |
| 项目维护方 | 技术支持、行业方案、培训、生态资助 | 直接收入（远期） |

### 3.2 可能的商业模式

| 模式 | 付费方 | 前提条件 | 最早时间（判断） | 备注 |
|---|---|---|---|---|
| 生态合作与资助（开源基金、厂商生态激励、科研课题） | 华为生态相关计划、基金会、高校与科研机构 | Cangjie-SIG 项目身份，路线清晰 | 现在 | 近期最现实的资金来源；具体渠道在 AP4 中确认 |
| 培训与课程（仓颉并发编程、Actor 设计） | 高校、企业内训、人才计划 | 文档可编译，示例进 CI（E23′、E54） | 2027 上半年 | 门槛低、回报小，但能扩大人才池 |
| 技术支持订阅（SLA、补丁、安全通告、LTS 版本） | 把 CActor 用在生产的企业 | 2.0.0 冻结 API；有 tag 和发布流程；有漏洞响应流程 | 2027 下半年 | 与 MIT 许可不冲突 |
| 行业方案与项目交付（与信创集成商合作） | 政企客户，通过集成商 | 有灯塔案例，有信创适配清单 | 2027 下半年 | 需要合作伙伴，不建议独立做集成 |
| 企业合规增强（国密 TLS、审计日志、多租户限流、国产数据库持久化插件） | 金融、政务客户 | 开源版先具备 TLS 和鉴权基础；企业版只做合规增强 | 2028 | 是否允许闭源插件，需要与 SIG 治理协商（AP4） |
| Agent 托管运行平台 | 中小开发者 | 集群、持久化、多租户全部可信 | 远期 | 投入大，只作为选项保留 |

### 3.3 当前价值是「期权价值」

今天 CActor 没有直接收入，它的价值在于：**在仓颉生态里占住「Actor / Agent 运行时」这个生态位，并保留后续兑现的选项。** 兑现需要四个条件，缺一不可：

| 条件 | 含义 | 对应工作 |
|---|---|---|
| 可信 | 内核语义对齐 Akka / OTP；分布式与持久化不丢、不乱、不被伪造 | M1、M2（E32–E45、E7′、E8′） |
| 可依赖 | 有版本号、tag、API 快照和中心仓发布，破坏性变更有记录 | E50、E51、ROADMAP 2.0.0 |
| 可证明 | 有复测的基准数据和灯塔案例 | AP3、AP17、AP19 |
| 可获得 | 文档可编译，示例能跑，有人响应问题 | E23′、E54，第二维护者（AP4） |

### 3.4 竞争格局

| 方案 | 语言 / 运行时 | 许可 | 与 CActor 的关系 |
|---|---|---|---|
| Akka（含 2025 年的 Agentic 平台） | JVM（Scala / Java） | BSL 1.1（2022-09 起）：生产使用需要商业许可，年收入低于 2500 万美元的组织可免费获得许可，但须申请（外部） | 语义对标对象；它的许可风险是替代动因之一 |

| Ray | Python / C++ | Apache-2.0 | 面向训练、推理和批处理的分布式计算，不是会话型 Agent 运行时 |

### 3.5 差异化定位

> **仓颉原生、AOT 编译、端云一体的 Akka Typed 级 Actor 运行时，为多 Agent 系统而设计。**

这句话中的每个词都需要证据支撑，对外使用前逐项核对：

| 词 | 现状 |
|---|---|
| 仓颉原生、AOT 编译 | ✅ |
| 端云一体 | 待 AP10、AP11 |
| Akka Typed 级 | 待 M1 |
| 为多 Agent 系统而设计 | 待 AP6–AP9 |

| 语言与编译器 | Java / Scala（JVM）、C#（.NET）、Erlang（BEAM）、Go | 仓颉 | 构建在仓颉之上 |
| Actor / 分布式运行时 | Akka（BSL）、Orleans、Erlang/OTP、Proto.Actor、Dapr | Skynet（游戏领域）、CActor（仓颉） | 仓颉侧功能最完整的选择（判断，AP5 核实） |
| Agent 运行时 | Akka Agentic（BSL）、AutoGen core、Ray | Cangjie Magic（开发框架）+ CActor（运行时） | 与 Cangjie Magic 互补 |

### 4.2 驱动力（按强弱排序）

1. **仓颉 / 鸿蒙原生技术栈的结构性空白。**
   - 语言白皮书规划过内置 Actor，现行规范没有落地。
   - 仓颉已被定位为鸿蒙官方编程语言。到 2025 年底，已有 450 多个用仓颉开发的鸿蒙应用上架（外部）。
   - 这些团队一旦需要高并发有状态的服务端或多 Agent 能力，在仓颉侧几乎没有现成选择。
2. **许可证风险。**
   - Akka 自 2022 年起改为 BSL，2025 年推出的 Agentic 平台同样采用 BSL（外部）。
   - 对于要求源码许可清晰、可长期自主维护的项目，MIT 许可的 CActor 没有这类风险。
3. **全栈可审计。**
   - 语言、编译器、运行时和框架的源码都可审计，文档以中文为主，托管在国内平台。
   - 对需要做供应链审查的政企项目，这是加分项。
4. **端侧能力。**
   - AOT 编译、运行时小，能在鸿蒙设备上运行（待 AP10 验证）。
   - JVM 和 BEAM 方案很难进入这个场景。

### 4.3 不应夸大的地方

- **JVM 不是「卡脖子」环节。** OpenJDK 有毕昇 JDK、腾讯 Kona、阿里 Dragonwell 等国内发行版，Pekko 是 Apache 许可。因此「Akka 改了许可，所以换成 CActor」对存量系统不成立。
- **迁移成本高。** 换框架就要换语言，等于重写，还要重新招聘或培养仓颉人才。
- **成熟度差距大。** Akka 有十多年的生产积累；CActor 只有约 1.5 年历史，贡献者只有 1 人。
- **结论**：CActor 替代的是**新建系统的技术选型**，尤其是已经确定采用仓颉或鸿蒙的系统，而不是去存量系统里抢替换。对外表述应是「仓颉生态的 Actor 运行时」，不宜说成「Akka 国产替代品」。

## 5. 应用场景

### 5.1 评估方法

每个场景按四个维度打 1–5 分：
- **契合度**：Actor 模型是否正好解决该场景的核心难题；
- **就绪度**：CActor 现有能力离可用还有多远；
- **替代拉力**：国产化或许可证因素带来的需求强度；
- **价值**：场景的商业价值。

### 5.2 场景总表

| 场景 | 契合 | 就绪 | 替代拉力 | 价值 | 建议 |
|---|---|---|---|---|---|
| **AI Agent 运行时**（仓颉原生，可作 Cangjie Magic 的底座） | 5 | 3 | 5 | 5 | **主攻**（C1） |
| **鸿蒙端云协同 / 端侧多 Agent / 设备协同** | 4 | 1 | 5 | 4 | **先做 PoC**（AP10），结论不利就降级 |
| **信创实时后端**（会话、IM、在线状态、推送、告警聚合） | 5 | 3 | 3 | 4 | **灯塔候选**（C2） |
| 业务流程编排（订单 / 工单状态机、Saga） | 4 | 2 | 3 | 4 | M2 之后，需要可信持久化 |
| IoT 边缘网关 / 设备数字孪生 | 5 | 2 | 4 | 3 | 生态合作推动（缺 MQTT、Modbus 接入） |
| 游戏服务端（房间、玩家） | 5 | 2 | 2 | 3 | 社区驱动（缺 WebSocket、KCP） |
| 实时风控 / 行情分发 | 4 | 2 | 3 | 4 | 远期，需要可信持久化和复测基准 |
| 电信信令 / 车联网 | 4 | 1 | 4 | 4 | 远期 |
| 交易撮合 / 账务核心 | 3 | 1 | 3 | 5 | **近期不做**（见 §2.2） |

就绪度的打分依据：Agent 运行时已有类型化 Actor、监督、带超时的 ask、blocking 调度器、定时器和 stash，缺取消、流式回复、HTTP 客户端和类型化持久化；鸿蒙场景的平台本身还没有验证；信创后端缺 HTTP / WebSocket、TLS 和数据库插件。

### 5.3 重点场景一：AI Agent 运行时

**为什么最契合**：Agent 是长期存活、有私有上下文、由事件驱动、经常失败、需要被监督的实体，这几乎就是 Actor 的定义。详见 [INTRODUCTION.md](../zh/INTRODUCTION.md) 第五节。

**目标形态**：

```
              网关（HTTP / SSE）
                    │ 按会话 ID 分片
         ┌──────────┴──────────┐
     SessionAgent（每个会话一个；事件溯源保存对话与记忆）
         │ 监督：restartWithBackoff
   ┌─────┼─────────────────┬────────────────────────┐
 Planner   ToolActor ×N             ModelClient Actor
 (编排)    (blocking 调度器，       (限流、断路器、
            失败退避重启)            流式 token)
         │
   人工审批：stash + 定时器，等待 Approve / Reject / 超时
```

**已有能力**（仓库）：
- `TypedAsk.ask` 和 Actor 内的 `ctx.ask`；
- `withTimers`、`withStash`；
- blocking 调度器；
- `supervise(...).onFailure(restartWithBackoff)`；
- Receptionist（单机版）；
- Grains 和分片；
- 示例 `best10_agent_workflow`、`dsl_agent`。

**缺口**：
- E61 Agent 原语：ask 取消令牌、类型化流式回复、异步退避重试、持久化 reminder；
- E44 类型化持久化；
- HTTP 客户端（ROADMAP 1.6.0，需要提前做一个子集）；
- 集群版 Receptionist（E63）。

**与 Cangjie Magic 的分工**（判断，需在 AP5 读源码确认）：

| Cangjie Magic 负责（怎么写） | CActor 负责（怎么跑） |
|---|---|
| `@agent` / `@prompt` / `@tool` 定义 | 一个 agent 实例对应一个类型化 Actor，状态隔离 |
| 工具调用、MCP | ToolActor 跑在 blocking 调度器上，失败时受监督 |
| 多 Agent 协作 | 消息、Receptionist、编排者监督子 Agent |
| 规划、RAG | 长会话：事件溯源、分片、可恢复 |

**分层约束**：
- 本仓库**不依赖** Cangjie Magic，适配层放到独立工程（AP8），避免两边耦合。
- 新增的 `cactor_agent` 模块放在 persistence / cluster 之上，与 xstate 同层，并同步更新 `tools/check_module_deps.py`。
- 模型调用定义为 `ModelClient` 接口，具体实现放在 HTTP 模块中，以遵守「stdx 只能进 json / http / integration」的约束（ROADMAP §11）。

### 5.4 重点场景二：鸿蒙端云协同 / 端侧多 Agent

**为什么值得做**：这是仓颉独有、JVM 方案进不去的场景。
- 端侧 Agent 处理隐私数据，支持离线；
- 云端 Agent 承担重计算；
- 手机、手表、车机、智慧屏之间的设备协同，天然是「每台设备一个 Actor」加消息的结构。

**主要风险**（AP10、AP11 要回答的问题）：
1. CActor 依赖的 `std.net`、`std.fs`、cgroup 读取等在 OpenHarmony 上是否可用；
2. 包体积和常驻内存；
3. 多线程自旋造成的空闲 CPU 占用和耗电：perf20261101 §D 记录过自旋 50 µs 和定期窃取探测，端侧必须有不自旋的调度配置；
4. 弱网下的可靠投递：接收端重启后通道停滞（N2）。

**判定方式**：如果 AP10 的结论是平台限制无法绕过，鸿蒙场景降级为「云侧服务 + 鸿蒙客户端」，不再投入端侧运行时。

### 5.5 重点场景三：信创实时后端

**形态**：
- 一个用户、会话或工单对应一个 Actor；
- 按 ID 分片；
- 事件溯源写入国产数据库；
- 由 Singleton 负责全局调度。

**缺口**：
- HTTP / WebSocket（ROADMAP 1.4.0 / 1.6.0）；
- TLS 和鉴权（E65、E7′）；
- fsync 与 Journal v2（E8′）；
- 分片两阶段移交（E13′）；
- 国产数据库插件（AP13）。

**灯塔策略**：先挑一个**低风险的内部系统**，例如通知聚合、告警降噪或会话网关，运行 4 周以上，再接触外部客户。

### 5.6 其他场景要点

| 场景 | Actor 拓扑 | 关键缺口 |
|---|---|---|
| IoT 边缘网关 / 数字孪生 | 一台设备一个 Actor；网关上的 Singleton 负责上云同步 | MQTT、Modbus 协议库；断网缓存 |
| 游戏服务端 | 房间 Actor 加玩家 Actor，按房间分片 | WebSocket、KCP；热更新 |
| 实时风控 / 行情分发 | 一个账户或标的一个 Actor；用 PubSub 扇出 | 扇出性能（Akka 约为 CActor 的 3 倍）；可信持久化 |
| 电信信令 / 车联网 | 一路呼叫或一辆车一个 Actor | 高可用集群（M2）；协议栈 |

## 6. 后续计划

### 6.1 原则

1. **不另起技术主线。** C 线只负责场景验证、平台适配和对外交付。技术缺口一律回到 E 项解决，不在场景代码里打补丁。
2. **门禁先于宣传。** 对外公布的数字必须来自空闲机器上的复测；凡是写「支持 X」，都必须有 CI 用例。沿用 20261106 的执行约束 1。
3. **先内部灯塔，再外部客户。**
4. **遵守 ROADMAP §10。**
   - 不做多语言绑定、K8s Operator、可视化管理界面，不同时支持多种数据库。
   - 不以 Star 数作为研发目标。本文的采用指标只用来检验商业假设是否成立。
5. **保持分层。** 新模块按 `check_module_deps.py` 规定的方向放置；stdx 只进 http / json / integration。

### 6.6 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 仓颉生态增长慢于预期 | 用户少，商业化假设不成立 | 绑定 Agent 和鸿蒙这两个华为战略方向；核心保持小而可信，降低维护成本 |
| 可信度问题外溢（假实现、文档不符被用户发现） | 信誉一次性受损 | 先完成 C0；对外只宣传 L3 能力（AP1） |
| 单一维护者 | 支持承诺无法兑现；项目可能中断 | 优先招募第二维护者（D5）；关键设计都写进 `docs/plan/` |
| Cangjie Magic 自建运行时，或方向改变 | AP8 失去意义 | 尽早沟通；`cactor_agent` 保持独立可用，不依赖 Magic |
| 官方在语言或标准库中内置 Actor | 核心定位被替代 | 跟踪语言演进；如果发生，CActor 转为其上的集群、持久化和 Agent 层，或向上游贡献 |
| 端侧平台限制（API 不可用、能耗过高） | 鸿蒙场景不成立 | AP10 尽早做；结论不利就降级为以云侧为主 |
| 性能数字被质疑 | 宣传起反作用 | 只发布复测数据，并附复现脚本（AP3） |
