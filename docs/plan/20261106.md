## 0. 总体结论

**性能已达标，正确性、可信度和工程纪律没有达标。**

- **性能**：每 Actor 存活堆约 1.2 KB，类型化互发 25M+ msg/s，顶层创建 551k/s（仓库自测：Akka 415k/s，protoactor-go 707k/s）。这些数字已接近一线框架。
- **正确性与可信度**：对照 Akka/OTP 逐条比较监督、DeathWatch、停止协议这三项核心语义，都有偏差。生产代码中约一半是零引用或假实现。
- **工程纪律**：没有 CI 流水线，最近 15 个提交直推 main，最新提交本身让 CI 永久卡死。

**v1 结论需要更正：**

1. v1 §3 写的"M1 完成：ci.sh 全绿（435/435）"从 `6183072` 起不再成立。该提交新增的 `routing_e9_test` 中，两个 Random 路由用例会**死循环**（单独跑时 30 s 超时，对照用例 0.85 s 通过），`tools/ci.sh` 永远结束不了。其余 445/447 通过。
   - 另有 5 个日志用例在设置 `CACTOR_LOG_LEVEL` 时失败，清掉变量后通过。属于测试依赖环境，不是代码缺陷。
2. v1 §1.5 中两条"已核实为非问题"被推翻：
   - "停止合批无重复扣减"：实际会重复扣减，见 R3；
   - "CRDT SIGSEGV 修复已彻底"：commit 所述的成因不成立，真正根因未明，见 N0。
3. v1 标为 ✅ 的 E1、E3、E4、E5 都只修了一半。E6 和 E9 在修复的同时引入了新缺陷：E6 引入 R2（顶层退避重启跑在定时器线程上），E9 引入 T1（Random 路由死循环）。

### 1.2 CActor 已具备的优势（改造时须保持）

- **调度握手可靠**：INCOMING_BIT 与 SCHED_BIT 位于同一个原子字。经全序论证，没有丢失唤醒，也不会两个线程同时处理同一个 Actor。邮箱的关闭与入队在同一把锁内互斥。
- **类型化适配器正确**：消息判别、`applyNext` 的快路径、DeathPact、重启时重跑 setup 都已核实无误。
- **枚举即协议**：配合 `@actor` 宏，可在编译期检查漏处理、协议漂移和重复处理器，与 Scala sealed trait 的保障等价。
- **其余已核实可用的部分**：
  - 内存与吞吐：每 Actor 1.2 KB，5M 规模已验证；
  - Phi Accrual 的公式与 Akka 一致；
  - 结构化日志 / MDC / JSON Lines；
  - DurableStateActor 的修订号乐观并发；
  - 模块分层检查已自动化。

## 3. 改造计划

**原则**
- 先恢复门禁，再修正确性，最后补能力。
- 每项单独提交 PR，并能单独回滚。
- 每项先提交失败用例，再修复（先红后绿）。
- 性能优化类提交必须同时跑 stop_race、soak 和并行集群套件，防止再次出现"用正确性换性能"。

**估算**：S（≤0.5 天）/ M（1–2 天）/ L（≥3 天）。v1 的整改项编号 E1–E24 保留；本版新增从 E25 起编号；带撇号（如 E6′）的表示在 v1 原项基础上重定义或扩展。
