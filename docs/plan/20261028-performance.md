# CActor 与 Akka 性能对比及仓颉性能优化要点（2026-10-28）

> 本文所有数字都在同一台机器上实测得到，没有引用任何公开宣传数据。
> 机器：Intel Xeon Platinum 8582C，32 个逻辑核（单路，每核 2 个超线程），123 GB 内存，Linux 5.15。
> 复现：CActor 运行 `./target/release/bin/cactor_examples.real_benchmark`；Akka 基准见 §5。

---

## 1. 对比方法

| 项 | CActor | Akka |
|---|---|---|
| 版本 | 仓颉 cjc 1.2.0（cjnative） | Akka 2.6.21（最后一个 Apache-2.0 版本），经典 Actor API，OpenJDK 17 |
| 配置 | 默认配置：`-O2`，8 个调度线程，空闲自旋 50µs | 默认配置，未调参：fork-join dispatcher，throughput=5 |
| 预热 | AOT 编译，无需预热 | 同一进程跑 3 轮，取第 3 轮（JIT 已预热） |

两边的场景、消息数和计时方式完全一致，都用单调时钟纳秒计时，只统计“消息被 Actor 实际处理完”的时间：

1. 单 Actor 吞吐：1 个发送方连续 `tell` 100 万条。
2. 扇出吞吐：8 个发送线程 × 100 个 Actor，共 200 万条。
3. ping-pong：两个 Actor 之间往返 2 万次，丢弃前 10% 作为预热。
4. Ask：请求-应答往返 2 万次，调用方阻塞等待结果。
5. 远程：两个节点通过本机回环 TCP，发送 20 万条字符串消息。

## 2. 结果

| 场景 | CActor 优化前（-O0） | 只加 -O2 | **CActor 优化后** | **Akka 2.6.21** | 差距 |
|---|---|---|---|---|---|
| 单 Actor 吞吐 | 1.51–1.64 M/s | 1.76–1.80 M/s | **5.6–7.2 M/s** | 2.7–3.4 M/s | CActor 约快 2 倍 |
| 扇出吞吐 | 0.54–0.58 M/s | 0.69–0.75 M/s | **2.5–4.5 M/s** | 9.1–11.9 M/s | Akka 约快 3 倍 |
| ping-pong P50 / P99 / P99.9 | 5.6 / 62 / 100–126 µs | 5.0 / 57–61 / 83–105 µs | **1.9–2.2 / 2.8–4.3 / 12–13 µs**¹ | 3.0–3.1 / 5.9–6.7 / 11.6–14.7 µs | P50、P99 CActor 更好，P99.9 持平 |
| Ask P50 / P99 | 6.9 / 22 µs | 5.1 / 16–18 µs | **5.0–6.0 / 11–13 µs** | 8.7–8.8 / 10–16 µs | P50 CActor 更好，P99 持平 |
| 远程 TCP（回环） | 46–48 k/s | 171–177 k/s | **146–194 k/s**（波动，最高测到 336 k/s） | 135–308 k/s（第 3 轮 308 k/s） | 预热后 Akka 约快 1.6 倍 |

¹ 3 次运行中有 1 次 P50 为 4.0µs、P99 为 11µs。仓颉的 M:N 调度会带来运行间波动，见 §3.3。

总结：

- **点对点场景**（单 Actor、ping-pong、Ask）已经追平或超过 Akka。原因是 AOT 编译、没有 JIT 预热期，再加上我们的邮箱是专门写的侵入式无锁队列。
- **差距主要在扇出**，Akka 约快 3 倍，原因见 §3.4。**远程**约慢 1.6 倍，原因是每条消息都做一次系统调用、没有写合并，见 §3.5。

## 3. 差距是怎么定位和缩小的

每一步都先用微基准确认原因，再修改，再测一次。微基准源码见 §5。

### 3.1 编译没有开启优化（单项收益最大，零代码改动）

`cjpm build -V` 显示，cjpm 调用 cjc 时**不传任何 `-O` 参数**，而 cjc 默认是 `-O0`，即使产物放在 `target/release` 下也一样。在 workspace 的 `compile-option` 中加上 `-O2` 后：

| 微基准（ns/次） | -O0 | -O2 |
|---|---|---|
| 不逃逸的对象分配 | 9.8 | 0.33（逃逸分析后被消除） |
| 接口调用 | 11.1 | 0.18（去虚化后内联） |
| `match` 类型匹配 | 8.1 | ≈0（被消除） |
| 跨线程自旋往返 | 243 | 147 |
| 原子 fetchAdd / Mutex 加解锁 | 9.7 / 25 | 8.4 / 22（本来就是运行时函数，几乎不变） |

整个基准的结果：远程吞吐提高 3.6 倍（47k → 175k），扇出提高约 30%，单 Actor 提高约 12%。

### 3.2 标准库并发容器太慢：邮箱和就绪队列改为自写 MPSC

| 微基准（-O2，ns/条） | 单线程入队+出队 | 8 生产者 / 1 消费者 |
|---|---|---|
| `std.collection.concurrent.ConcurrentLinkedQueue` | **186–195** | 423 |
| `LinkedBlockingQueue` | 285 | 343 |
| 自写 Vyukov 侵入式 MPSC | **38**（批量时 30） | 214 |
| 原 `foundation` 版 MPSCQueue（带统计计数和消费者锁） | 71 | — |

改动：

- 邮箱换成 `CellMailbox`：节点直接保存消息和发送方，**不再额外分配元组**。
- 每个调度线程的就绪队列换成 `RunQueue`，结构相同。

### 3.3 调度器：全局队列争用严重，并且 M:N 调度有特殊的坑

1. **全局就绪队列导致争用崩溃**：线程数越多，扇出越慢。用 `cjProcessorNum` 限制原生线程数测得：4 个时 2.73 M/s，8 个时 1.33 M/s，16 个时 0.93 M/s，64 个时 0.71 M/s。
   - 改为**亲和调度**（与 Akka 的 `AffinityPool` 同类）：每个 Actor 固定分给一个调度线程，每个调度线程有独立的就绪队列，调度时不再争用全局锁。
   - 调度线程数默认取核数的 1/4（4–64），可以用 `CACTOR_DISPATCHER_THREADS` 调整。不取全部核数，是因为发送方、I/O 等仓颉线程也要占用处理器。
2. **唤醒开销**：每次阻塞唤醒的往返约 2.6µs（`LinkedBlockingQueue`），`Mutex` + `Condition` 往返约 1.4µs。所以空闲的调度线程先**自旋一段时间再休眠**。
3. **坑 1：自旋要按时间算，不能按次数算**。
   - 按次数自旋时，队列变快后自旋时间就变短了，ping-pong 的 P99 会从 8µs 退化到 64µs。
   - 改为按时间自旋（默认 50µs，可用 `CACTOR_DISPATCHER_SPIN_US` 调整）之后，P99 降到 3–4µs。
4. **坑 2：自旋会挡住同一处理器上刚被唤醒的线程**。
   - 现象：Ask 的延迟正好等于调度线程的自旋时长（自旋 0 时 5µs，100 次时 16µs，2000 次时 31µs）。
   - 推断：调度线程用 `notify` 唤醒 Ask 的等待方之后，被唤醒的仓颉线程排在这个调度线程所在的处理器上，要等它自旋结束、休眠后才能运行。在自旋循环里调用 `sleep(Duration.Zero)` 让出处理器也无效。
   - 解决：等待方 `Completion.await` 先自旋最多 50µs，结果到达就不进入休眠。Ask 的 P50 从 26µs 降回 5µs。
5. **坑 3：无锁 MPSC 的“半链接窗口”不能原地自旋**。
   - 生产者执行完 `swap`、还没写 `next` 时，消费者会看到队列非空但取不出元素。
   - 原地自旋等待时，如果那个生产者恰好排在同一处理器上，消费者可能空转若干毫秒。实测单 Actor 吞吐在 5 M/s 和 0.48 M/s 之间剧烈波动。
   - 改为：遇到半链接时返回“暂无”，让出处理器一次，之后再重新调度。
6. **发送路径**：调度标志改为“先读后 CAS”。Actor 已在调度中时，只做一次读（2 ns），不再每次写共享缓存行（CAS 失败也要 9 ns，并且会让缓存行在核间来回同步）。

### 3.4 扇出仍差约 3 倍的原因（尚未解决）

- **每条消息几乎都会触发一次调度**。100 个 Actor 消费得比 8 个发送方发得快，邮箱经常是空的，所以几乎每次 `tell` 都要走完整的调度流程：CAS、分配一个 `RunNode`、入队、检查休眠标志，必要时还要唤醒。Akka 外部提交走的是 ForkJoinPool 的数组型提交队列，开销更低。
- **每条消息要分配 3–4 个对象**：邮箱节点、节点内的 `AtomicOptionReference`、上下文，以及调度时的 `RunNode` 和它的原子引用。在仓颉中原子类型是独立的对象（实测分配约 9.5 ns），不能像 JVM 那样用字段级原子操作（Unsafe/VarHandle）把原子变量嵌进节点里。
- **没有工作窃取**。亲和调度在负载不均时会有调度线程空闲。
- **无法填充缓存行**。仓颉没有 `@Contended` 之类的手段，相邻 Actor 的调度标志、邮箱头可能落在同一缓存行上（伪共享）。这一点是推断，尚未单独验证。
- **结果波动大**（2.5–4.5 M/s），和 M:N 调度下发送方与调度线程的放置位置有关。

### 3.5 远程差约 1.6 倍的原因（尚未解决）

- CActor 每条消息都单独加锁并调用一次 `socket.write`。Akka Artery 把多条消息合并成大块写入 TCP，并且使用独立的出站流。
- 下一步：出站加一个队列，由一个写线程批量合并写入（write coalescing）；接收端改为批量读取并解析多帧。

## 4. 仓颉性能优化要点

### 4.1 编译

1. **一定要显式开启优化**：cjpm 默认不加 `-O`，相当于 `-O0`。在 workspace 的 `compile-option` 中加 `-O2`（本项目已加）。
2. `-O2` 下真正起作用的优化有：
   - **逃逸分析与栈分配**：不逃逸的对象分配几乎为零。
   - **去虚化与内联**：接口调用从 11ns 降到 0.2ns。
   - 消除无用分配，结构体返回值优化（`cj-simple-opt`），以及写屏障消除（`cj-barrier-opt`）。
3. 还可以尝试（本项目尚未测）：
   - `--lto=thin|full`：跨包内联。热路径分散在 core、runtime、foundation 等多个包时可能有效。
   - `--pgo-instr-gen` 加 `--pgo-instr-use`：基于实际运行数据去虚化热点调用。
   - `--target-cpu`（实验性）。
4. 写代码时要配合编译器：
   - 热路径上的临时对象不要存进全局变量或字段，否则会逃逸，变成堆分配。
   - 小而不可变的数据用 `struct`（值类型），访问不需要 GC 屏障。

### 4.2 内存与 GC

- 逃逸到堆上的对象分配约 7.5ns，和 JVM 的线程本地分配同一量级，所以分配本身不是瓶颈，**分配的次数**才是。
- 原子类型（`AtomicInt64`、`AtomicOptionReference` 等）是独立的堆对象，每个都是一次额外的分配，访问时还要多一次间接寻址。需要原子字段的高频节点要特别计入这部分成本。
- 运行时参数（环境变量）：
  - `cjHeapSize`：默认 256MB。实测把它调到 2GB 对本基准没有可测量的影响。
  - 其他还有 `cjGCThreshold`、`cjRegionSize`（线程本地分配缓冲，默认 64KB）、`cjGCInterval`（默认 150ms）等。
  - 分配密集的服务应该根据 `MRT_REPORT` 输出的 GC 日志来调这些参数，不要凭直觉调。

### 4.3 并发与调度（M:N 模型）

| 原语（-O2 实测） | 开销 |
|---|---|
| `AtomicInt64.fetchAdd` / `AtomicBool` CAS | 8–9 ns |
| 先 load、需要时再 CAS | 2 ns（已设置的情况） |
| `Mutex` 无竞争加解锁 | 22 ns |
| `spawn` + `get` | 0.8–1.5 µs |
| `Mutex` + `Condition` 往返 | 1.4 µs |
| `LinkedBlockingQueue` 阻塞往返（2 次唤醒） | 2.6 µs |
| 跨线程自旋往返 | 0.15 µs |
| 字符串插值 `"actor-${i}"` | 61 ns |

1. **仓颉线程是用户态线程，采用 M:N 调度**。`cjProcessorNum` 决定最多同时运行多少个仓颉线程（默认等于核数，最大为核数的 2 倍）。线程不是越多越好，有共享数据结构时反而越多越慢（§3.3）。
2. **不要每来一个任务就 `spawn`**（约 1µs）。长期运行的工作线程配合任务队列，效果最好。
3. **在一个处理器上自旋，会挡住排在同一处理器上的其他仓颉线程**，`sleep(Duration.Zero)` 也解决不了。所以：
   - 自旋要设时间上限。
   - 无锁算法里需要等待的地方（例如半链接窗口），不要原地自旋，应该返回并稍后重试。
   - 唤醒方和等待方最好都短暂自旋（等待方也自旋，就不会被挂起）。
4. **阻塞的外部调用（C FFI、阻塞 I/O）会占住整个原生线程**，同一原生线程上的其他仓颉线程都无法运行。可能阻塞的 Actor 应该放到独立的调度器上。
5. **标准库的并发容器**（`ConcurrentLinkedQueue` 约 190ns）适合一般用途。每秒百万级的热路径应该使用专门的数据结构，例如 Vyukov MPSC 或有界环形缓冲。
6. **热路径上不要打日志**：一次字符串插值约 61ns，比整个消息投递还贵。

## 5. 复现

```bash
# CActor
source ~/.cangjie/1.2.0/cangjie/envsetup.sh
cjpm build
./target/release/bin/cactor_examples.real_benchmark
# 可调参数
CACTOR_DISPATCHER_THREADS=8 CACTOR_DISPATCHER_SPIN_US=50 cjProcessorNum=32 ./target/release/bin/cactor_examples.real_benchmark

# Akka（依赖：akka-actor/akka-remote/akka-stream/akka-protobuf-v3 2.6.21、scala-library 2.13.12、
#   scala-java8-compat 1.0.2、config 1.4.2、reactive-streams 1.0.4、ssl-config-core 0.6.1、agrona 1.15.1）
java -cp "jars/*" AkkaBench.java 3     # 3 轮，取最后一轮
```

本次使用的 Akka 基准程序和仓颉原语微基准都放在 `/tmp`（`/tmp/akka-bench/AkkaBench.java`、`/tmp/cjperf*/src/main.cj`），没有纳入仓库。如需长期跟踪，可以把它们移到 `modules/examples` 或单独的 `cactor_bench` 模块。

## 6. 下一步

| 优先级 | 事项 | 预期 |
|---|---|---|
| 高 | 远程出站写合并 + 接收端批量解析 | 远程吞吐追平或超过 Akka |
| 高 | 扇出：发送方批量提交、减少每条消息的分配（就绪节点复用，或把 Cell 本身作为侵入式节点） | 扇出差距从 3 倍缩小到 1.5 倍以内 |
| 中 | 在亲和调度之上增加工作窃取（空闲线程从邻居窃取） | 负载不均时的吞吐 |
| 中 | 评估 `--lto=thin` 和 PGO | 跨包内联带来的提升 |
| 中 | 独立的阻塞调度器（供阻塞 I/O 和 FFI 使用） | 避免阻塞操作拖慢普通 Actor |
| 低 | 把 Akka 对比基准和微基准纳入仓库，接入 CI 做性能回归检测 | 防止性能退化 |
