## 1. 仓颉模块化机制调研

### 1.1 语言层：包（package）

| 机制 | 规则 | 对 CActor 的意义 |
|---|---|---|
| 包 = 目录 | 同一包的源文件必须在同一目录；子包就是子目录；包目录下必须**直接**含有 `.cj` 文件，否则子目录不会被扫描 [V] | 每个模块的 `src/` 根目录都需要一个根包文件（`pkg.cj`） |
| 禁止循环依赖 | “任意两个包之间都不允许循环依赖，即使在同一模块内”，且按传递关系判断 | 拆分前必须先打破层间的环 |
| 顶层声明可见性 | `private`：文件；`internal`（默认）：本包及子包；`protected`：本模块；`public`：所有包 | 跨包使用的符号本来就必须是 `public`，因此拆成多个模块不会引起可见性错误 [V] |
| 包的可见性 | `package` 可以用 `internal`/`protected`/`public` 修饰，默认 `public`；根包只能是 `public`；子包的可见级别不能高于父包 | 用 **`protected package`** 把实现细节限制在模块内部（已落地） |
| import 修饰符 | `import` 默认 `private`（仅当前文件）；`public`/`protected`/`internal import` 可以重导出**成员**，但**不能重导出包** | 由模块根包通过 `public import a.b.{X, Y}` 对外暴露精选的 API（facade） |
| 宏包 | `macro package x`：对外只能暴露宏；可以重导出其他包的非宏声明，供宏展开后使用；宏的定义和调用不能在同一个包里 | 宏单独成模块 `cactor_macros`（已落地，并已验证可以作为模块根包） |
| main | 每个包最多一个 `main`；编译成库时会忽略 `main` | 示例和可执行测试通过 `package-configuration` 声明为 `executable` |

### 1.2 工具层：模块（module）与 cjpm 工作区（workspace）

- **模块 = 根包加上它的所有子包**。模块名就是根包名，所有包名都以模块名开头。
- **模块名不能带点**：`name = "cactor.core"` 会报错 *“the example is 'cjDemo'”* [V]。所以模块名只能取 `cactor_core` 这种形式，或者使用组织前缀。
- **组织（organization）**：`organization = "demo"` 以后，包名必须写成 `package demo::a.x`，导入写成 `import demo::a.x.*`，依赖写成 `"demo::a" = { path = ... }` [V]。这个机制面向中心仓发布。CActor 暂时不用，详见 3.4 的 M9。
- **workspace**：`[workspace]` 与 `[package]` 不能同时出现。字段包括 `members`、`build-members`、`test-members`、`compile-option`、`override-compile-option`、`link-option`、`target-dir`。成员之间用 `{ path = "../x" }` 声明依赖；源码里 import 了某个包，但没在 `cjpm.toml` 中声明对应模块依赖，构建会失败 [V]。
- 在 workspace 根目录执行 `cjpm build`、`cjpm test`、`cjpm run --name <pkg>` 都能直接工作 [V]。`cjpm build -m <member>` 可以只构建单个成员。
- 其他依赖形式：`[test-dependencies]`、`[script-dependencies]`、`git = ...`，以及 `[target.<triple>.bin-dependencies]`（stdx 等二进制依赖）。
- `--enable-features` 和 `experimental = true`：属于仓颉多平台（CJMP）源集机制，还是实验特性 [G]，暂不采用。
- **`[test-dependencies]` 同样参与成环检测** [V]：模块 A 的测试依赖模块 B，而 B 又依赖 A 时，`cjpm test` 报 *cyclic dependency*。因此，一个模块的单元测试只能使用同层或更低层的模块；需要 `cactor` 门面的测试只能放在更上层的测试模块里。
- **同包测试文件** [V]：`xxx_test.cj` 与被测代码在同一个包里时，可以直接访问 `internal` 成员；其中的声明只在 `cjpm test` 时编译，普通构建不可见。
- **单成员操作** [V]：`cjpm build -m modules/core` 只构建一个成员（参数是路径，不是模块名）。在成员目录内直接 `cjpm build` 也可以，但不会继承 workspace 的 `compile-option`。`cjpm test -m <path> --filter <pattern>` 可以只跑部分测试。
- **依赖诊断** [V]：`cjpm check` 校验依赖并输出包级编译顺序；`cjpm tree --depth N / --invert <pkg>` 显示包依赖树，可用于在 CI 中排查意外依赖。
- **打包发布**：`cjpm bundle` 打包（默认会先跑 `cjpm test` 和 cjlint），`cjpm publish` 发布到中心仓。发布要求 `name`/`organization` 长度在 3–64 之间，并需要配置 token；可以用 `include`/`exclude` 控制打包内容。
- **stdx 依赖方式**：二进制方式是 `[target.<triple>.bin-dependencies] path-option = ["<stdx>/dynamic/stdx"]`（Linux x86_64 的 triple 为 `x86_64-unknown-linux-gnu`）；源码方式是 `[dependencies] stdx = { git = ..., output-type = "dynamic" }`，再执行 `cjpm update`。本机 stdx 位于 `~/.cangjie/stdx-1.2.0.1/linux_x86_64_cjnative/{static,dynamic}/stdx`。

### 1.3 设计结论

1. 以**模块**作为部署和依赖边界，以**包**作为代码组织单元，以 **`protected package`** 作为模块内部封装手段，以**根包的 `public import`** 作为对外门面。
2. 模块名统一使用 `cactor_<层>`；面向用户的门面模块保留名字 `cactor`，因此 `import cactor.*`、`import cactor.api.*` 等用户代码不受影响。
3. 依赖必须严格自底向上，由 `cjpm`（防循环、检查依赖声明）和 `tools/check_module_deps.py`（检查分层方向）共同保证。

### 2.2 具体改动

1. **单模块改为 workspace**：用 `git mv` 把 `src/<层>/` 移到 `modules/<层>/src/`，保留 git 历史；`src/cactor.cj`、`src/api`、`src/config` 移入门面模块 `modules/cactor`。

5. **模块级封装**：`cactor_runtime` 中 13 个只在模块内部使用的实现包声明为 `protected package`：actor、context、guardian、registry、message、monitoring、execution、scheduler、mailbox.lockfree、mailbox.ringbuffer、dispatcher.batch_processing / optimized / work_stealing。已用探针验证：从其他模块 import 会报 *“package 'cactor_runtime.registry' is 'protected' which cannot be imported by irrelevant package”* [V]。

## 3. 后续模块化方案

目标：在“模块即边界”的基础上，做到**每个模块职责单一、API 精简、可以单独构建和测试，可选能力可插拔**。

### 3.1 目标模块图（终态）

```
L0  cactor_foundation   并发原语、队列、序列化接口、断路器（无外部依赖）            [现有]
L0  cactor_macros       宏（可选）                                                [现有]
L1  cactor_core         Actor / ActorRef / Props / Message / Supervision / Typed  [现有]
L2  cactor_runtime      唯一的 ActorSystem 实现：Actor Cell + dispatcher + guardian [现有，待收敛]
L2  cactor_remote       stdx.net 传输与序列化注册表（可选，实验性）               [v3 已拆出]
L2  cactor_persistence  EventStore / Snapshot / CQRS（可选，实验性）              [v3 已拆出]
L3  cactor_patterns     ask / routing / backpressure（可以依赖 runtime）          [v3 已换序]
L4  cactor              门面：只做 public import 重导出 + 配置加载                [现有]
L5  cactor_testkit      TestProbe / TestActorSystem / awaitCondition              [待建]
L5  cactor_streams      流 DSL                                                    [现有]
L5  cactor_cluster      成员管理与分片（依赖 remote）                             [v3 已拆出]
L6  cactor_xstate       状态机（只依赖 cactor）                                   [待：移出 enterprise.distributed]
L6  cactor_xstate_cluster  xstate 分布式扩展                                      [待建]
L6  cactor_distribution 聚合模块（只做重导出）                                    [v3 已完成；streaming 待迁出]
L6  cactor_integration  日志、指标适配（stdx.log）                                [现有，待瘦身]
--  cactor_tests / cactor_examples / cactor_bench   不发布                        [bench 待建]
```

与现状相比，剩下的调整：
- **xstate 去掉对 cluster 的依赖**：把 `xstate.enterprise.distributed` 拆为 `cactor_xstate_cluster`。
- **testkit 的位置**：由于 test-dependencies 也参与成环检测（见 1.2），testkit 依赖 runtime 之后，就不能再被 core 或 runtime 自己的测试使用。因此 core 和 runtime 的单元测试只能使用同包的 `_test.cj` 辅助代码，testkit 只服务于 L4 及以上的模块和外部用户。
- `distribution.streaming` 并入 `cactor_streams`，或者删除，使 `cactor_distribution` 成为纯聚合模块。

### 3.2 模块内部规范（每个模块都要满足）

1. **根包即 API 清单**：`src/pkg.cj` 只包含 `public import x.{A, B, C}`，显式列出对外类型，禁止 `public import x.*`。
2. **对外和内部分开**：模块内子包默认 `protected package`，只有 API 包才是 `public package`；跨模块只能 import 根包或明确标为 public 的包。
3. **测试就近存放**：单元测试写成同包的 `xxx_test.cj`。仓颉测试文件可以访问 `internal` 成员，并且只在 `cjpm test` 时编译 [V]。测试只能依赖同层或更低层的模块（否则会成环）[V]；需要门面的测试放在 `cactor_tests`。
4. **自己的 `cjpm.toml` 自己负责**：版本号、描述、依赖最小化；不依赖“经由别的模块传递过来”的包。
5. **示例不放进库模块**：库模块中不出现 `main`。

### 3.3 分阶段任务

#### M1：已完成（2026-10-28）

### 6.4 已知限制与下一步

1. **扇出吞吐**：仍比 Akka 慢约 3 倍（每条消息几乎都触发一次调度，每条消息分配 3–4 个对象，没有工作窃取）；**远程**慢约 1.6 倍（没有写合并）。详见性能文档 §3.4、§3.5。
2. **远程投递语义是至多一次**：对端重启后，第一次写入可能丢失（重连只重试一次）。下一步加入应用层确认或重发，以及远程 ask。
3. **阻塞**：在 `receive` 中执行阻塞操作会占住一个工作线程。需要提供独立的阻塞调度器。
4. **Cluster** 仍是原型（P1-6）；**宏代码生成**（M7）、**API 收口**（M2）、**去重**（M3）、**testkit**（M4）、**CI 与告警清零**（M8）还未开始。
5. 库代码中仍有大量 `println` 日志（P2-13），需要引入日志抽象。

以上限制及第 7 节差距分析中的事项，统一纳入第 8 节路线图（R1–R8）。

### 7.3 核心 Actor 语义（对标 Akka 经典 API 与 Erlang/OTP）

关键事实 [V]：
- 经典 API 的 `ActorContext` 接口只有一个方法 `func sender(): Option<String>`（`modules/core/src/context/actor_context.cj:13`）。发送方是**路径字符串**，不是 `ActorRef`。
- 主路径的实现 `SimpleUserActorContext`（`modules/runtime/src/guardian/runtime_user_guardian.cj:534`）也只保存 self 和 sender，不对外提供。
- 所有用户 Actor 都由 user guardian 直接创建（`runtime_user_guardian.cj:48`），层级是扁平的，并统一使用默认的 OneForOne 策略（`:61`）。

| 能力 | Akka / OTP | CActor 现状 | 状态 |
|---|---|---|---|
| 异步 `tell`、同一 Actor 串行处理 | `!` / `tell`；进程邮箱 | Actor Cell + 侵入式 MPSC 邮箱，5 个并发语义测试 | ✅ |
| 回复发送方 | `sender() ! reply` | sender 只是字符串，不能直接回复；Ask 需要在消息里携带 `replyTo` | 🟠 |
| `self` | `self` / `self()` | 经典上下文不提供 | ❌ |
| 子 Actor 与监督树 | `context.actorOf`；supervisor 子进程规格 | 没有父子层级，所有 Actor 都挂在 user guardian 下 | ❌ |
| 死亡监视 | `context.watch` + `Terminated`；`monitor` / `link` | 经典 API 没有；不存在 `Terminated` 消息 | ❌ |
| 行为切换 | `become` / `unbecome`；gen_statem | 没有（只有测试工具类里有同名方法） | ❌ |
| 停止 | `context.stop`、`PoisonPill`、`Kill` | `MessageResult.Stop`、`system.stop(ref)`；没有 `PoisonPill` / `Kill` | 🟡 |
| 接收超时 | `setReceiveTimeout` | 缺失 | ❌ |
| 定时器 / 调度器 | `Timers`、`system.scheduler` | 经典 API 没有；Typed 的 scheduler 忽略延时（7.4） | ❌ |
| Stash | `Stash` trait | 只有 Typed 的 `StashBuffer`，没有接入 Cell | 🟠 |
| 按 Actor 配置邮箱 / 调度器 / 监督策略 | Props / Deployment 配置 | `Props.withMailbox/withDispatcher/withSupervisionStrategy` 存在，但 `createUserActor` 全部忽略 | 🟠 |

| 协调关闭 | CoordinatedShutdown | 已实现并接入 runtime | ✅ |

### 7.6 性能

详见 [20261028-performance.md](20261028-performance.md)。同机（32 核）对比 Akka 2.6.21 的结论：

| 场景 | CActor | Akka 2.6.21 | 结论 |
|---|---|---|---|
| 单 Actor 吞吐 | 5.6–7.2 M msg/s | 2.7–3.4 M msg/s | CActor 约快 2 倍 |
| ping-pong P50 / P99 | 1.9–2.2 / 2.8–4.3 µs | 3.0 / 5.9–6.7 µs | CActor 更好 |
| Ask P50 / P99 | 5.0–6.0 / 11–13 µs | 8.8 / 10–16 µs | 基本持平 |
| 扇出（8 × 100 Actor） | 2.5–4.5 M msg/s | 9.1–11.9 M msg/s | **Akka 约快 3 倍** |
| 远程 TCP（本机回环） | 146–194 k msg/s | 308 k msg/s | **Akka 约快 1.6 倍** |

主要差距与原因：
1. **扇出**：几乎每条消息都触发一次完整调度；每条消息分配 3–4 个对象（仓颉的原子类型是独立的堆对象）；没有工作窃取；无法做缓存行填充。
2. **远程**：每条消息单独加锁并调用一次 `write`，没有写合并和批量解析。
3. **吞吐参数不可配**：Akka 的 `throughput`（每次调度处理的消息数）可配置；CActor 固定为 64。
4. **没有阻塞调度器**：Akka 推荐把阻塞 I/O 放到独立的 dispatcher。仓颉中阻塞的 FFI 调用会占住整个原生线程，影响更大。
5. **没有有界邮箱与背压**：生产者比消费者快时，邮箱会无限增长，最终内存耗尽。
6. **规模测试缺失**：还没有测过百万级 Actor 的创建速度和每个 Actor 的内存占用（Akka 约 300–500 字节/Actor；Erlang 进程约 2.6 KB）。
7. **编译优化未用尽**：`--lto`、PGO 尚未评估。

### 7.11 仓颉 DSL 化

**现状** 🟠：`cactor_macros` 定义了 20 个宏，但基本都原样返回输入，例如 `@actor`（`modules/macros/src/macros.cj:67`）。用户写一个 Actor，仍需手写 `name`、`description` 两个属性和一个 `match` 分发。和 Akka（Scala）的 `Behaviors.receiveMessage { case Ping(n) => ... }`、Erlang 的模式匹配 `receive` 相比，样板代码明显更多。

**已验证的仓颉语言能力**（cjc 1.2.0 实验工程）[V]：

| 能力 | 结果 | 可用于 |
|---|---|---|
| 宏解析类声明并生成方法 | ✅ 宏用 `std.ast` 解析 class，收集所有 `onXxx(m: T)` 方法，自动生成按类型分发的 `receive`，运行结果正确 | `@Actor` 宏：消除手写 `match` 分发 |
| 接口中声明带默认实现的运算符 | ✅ `interface Ref { operator func <<(m: String): Ref { ... } }`，可以链式写 `ref << a << b` | 在 `ActorRef` 接口上提供 `<<` 作为 `tell` 的简写 |
| 用 `extend` 给接口加运算符 | ❌ 编译报错 *extending type 'Interface-Ref' is not allowed* | 运算符只能直接声明在接口内，不能事后扩展 |
| 扩展内置类型的属性 | ✅ `extend Int64 { prop seconds: Duration }`，可写 `3.seconds + 500.millis` | 时长 DSL，对应 Scala 的 `3.seconds` |
| 尾随 lambda | ✅ `receive<Msg> { m => match (m) { ... } }` | 行为构造器，形式接近 Akka Typed |
| 管道运算符 `\|>` | ✅ | 流处理组合，例如 `source \|> map(f) \|> sink` |
| 枚举（ADT）+ 穷尽 `match` | ✅（语言内置） | 类型化协议：编译器检查消息是否都已处理 |

另外两点限制：仓颉没有 Scala 那样的二元 `!` 和 `?` 运算符，`tell` 只能用 `<<` 之类可重载的运算符代替；宏只能在单独的宏包中定义，调用方需要依赖 `cactor_macros`。

**目标写法（示意）**：

```cangjie
// 1) 经典 Actor：@Actor 宏生成 receive 分发、name/description 默认实现
@Actor
class Counter {
    var count = 0
    func onIncrement(m: Increment): Unit { count += m.n }
    func onGet(m: Get): Unit { m.replyTo << CountIs(count) }
}

// 2) 类型化 Actor：枚举协议 + 尾随 lambda
enum CounterMsg { | Increment(Int64) | Get(TypedActorRef<Int64>) }

func counter(n: Int64): TypedBehavior<CounterMsg> {
    Behaviors.receive<CounterMsg> { ctx, msg =>
        match (msg) {
            case Increment(k) => counter(n + k)
            case Get(replyTo) => replyTo << n; Behaviors.same()
        }
    }
}

// 3) 监督与定时器
let child = ctx.spawn(Behaviors.supervise(worker()).onFailure(restartWithBackoff(1.seconds, 30.seconds)), "worker")
timers.startTimerWithFixedDelay(Tick(), 500.millis)

// 4) 流：管道组合
Source.range(1, 1000) |> Flow.map { x => x * 2 } |> Sink.foreach { x => println(x) }
```

### 7.12 仓颉平台带来的优势与约束

| 类型 | 内容 | 影响 |
|---|---|---|
| 优势 | AOT 编译，没有 JIT 预热期 | 启动快、尾延迟稳定，适合边缘侧和短生命周期服务；点对点延迟已优于 Akka |
| 优势 | `struct` 值类型、逃逸分析 | 消息可以设计为值类型，减少堆分配 |
| 优势 | M:N 用户态线程 | 每个 Actor 不需要独立线程，调度成本低 |
| 优势 | 鸿蒙生态 | 端侧 Actor（设备协同、离线优先）是 JVM 方案难以覆盖的场景 |
| 约束 | 原子类型是独立的堆对象，没有字段级原子操作 | 高频节点每多一个原子字段就多一次分配 |
| 约束 | 没有缓存行填充手段 | 无法消除伪共享 |
| 约束 | 自旋会挡住同一处理器上的其他仓颉线程；阻塞的 FFI 会占住原生线程 | 必须限制自旋时长，并提供阻塞调度器 |
| 约束 | 生态较新：没有成熟的 Protobuf、OpenTelemetry、数据库驱动 | 序列化、可观测性、持久化插件需要自建或依赖 stdx |
| 约束 | 不能 `extend` 接口 | DSL 运算符必须直接定义在接口里 |

## 8. 后续路线图（v5）

### 8.1 总体目标与原则

**目标**：在保持点对点性能优势的前提下，**先补齐单机 Actor 的语义完整性，再做稳定性与工程质量，最后扩展分布式与生态**，成为仓颉上可以用于生产的 Actor 框架。

**原则**：
1. **先语义，后功能**：监督树、监视、行为切换、定时器是 Actor 模型的基础，优先级高于集群、流等上层功能。
2. **一条主路径**：每种能力只保留一个实现，其余删除，不再新增并行实现。
3. **每项能力必须有测试**：README 中列出的每一项都要能对应到可复现的测试。
4. **性能不倒退**：基准纳入 CI，每次合并检查回归。

### 8.2 阶段划分

| 阶段 | 主题 | 优先级 | 预计 | 依赖 | v6 进度 |

| R1 | 核心 Actor 语义补全 | P0 | 3–4 周 | — | **95%** |
| R2 | 类型化 API 真实化 | P0 | 2–3 周 | R1 | **90%** |
| R3 | 稳定性与工程质量（含原 M2、M3、M5、M8） | P0 | 3–4 周（可与 R1、R2 并行） | — | **40%** |
| R4 | 性能第二轮 | P1 | 2–3 周 | R1 | **55%** |
| R5 | 仓颉 DSL 化（含原 M7） | P1 | 2–3 周 | R1、R2 | **50%** |
| R6 | 分布式完善 | P1 | 6–8 周 | R1、R3 | **15%** |
| R7 | 流处理重写 | P2 | 4 周 | R1、R4 | 0% |
| R8 | 生态与可观测性 | P2 | 持续 | R3 | **15%** |

### 8.3 R1：核心 Actor 语义补全（P0）

1. **扩展 `ActorContext`**：
   - `self: ActorRef`；`sender(): Option<ActorRef>`（保留按路径的旧方法，标为弃用）；`reply(msg)`。

### 8.6 R4：性能第二轮（P1）

| 事项 | 做法 | 目标 |
|---|---|---|
| 扇出吞吐 | Cell 本身作为就绪队列的侵入式节点（去掉 `RunNode` 分配）；发送方批量提交；减少每条消息的原子对象 | 与 Akka 的差距从 3 倍缩小到 1.5 倍以内 |
| 工作窃取 | 在亲和调度之上，空闲线程从邻居窃取 | 负载不均时吞吐不下降 |
| 远程 | 出站队列 + 写线程合并写入；接收端批量解析多帧 | 追平 Akka（约 300 k msg/s） |
| 阻塞调度器 | 独立线程池，`Props.withDispatcher("blocking")` | 阻塞操作不影响普通 Actor |
| 背压 | bounded 邮箱满时可选丢弃、阻塞发送方或返回失败 | 生产者过快时内存不会无限增长 |
| 吞吐参数 | 每次调度处理的消息数可配置（对应 Akka 的 `throughput`） | 在延迟和吞吐之间可调 |
| 规模测试 | 创建 100 万个 Actor，测创建速度和每个 Actor 的内存 | 目标 < 1 KB/Actor（Akka 约 300–500 B） |
| 编译 | 评估 `--lto=thin` 和 PGO | 跨包内联 |

### 8.7 R5：仓颉 DSL 化（P1）

1. **`@Actor` 宏**（已验证可行，见 7.11）：
   - 收集 `onXxx(m: T)` 方法，生成按类型分发的 `receive`；未匹配的消息返回 `Unhandled`。
   - 自动生成 `name` / `description` 默认实现。
   - 编译期检查：同一消息类型有多个处理方法时报错。
2. **`@Message` 宏**：为消息类生成 `messageType`、序列化编解码器并自动注册到 `MessageCodecRegistry`，减少远程消息的手写代码。
3. **运算符与扩展**：
   - 在 `ActorRef` 和 `TypedActorRef` 接口中直接定义 `operator func <<`，作为 `tell` 的简写。
   - `extend Int64` 提供 `millis` / `seconds` / `minutes`。
4. **行为构造器**：`Behaviors.receive<T> { ctx, msg => ... }`、`Behaviors.setup<T> { ctx => ... }`，使用尾随 lambda。
5. **状态机 DSL**：`@StateMachine` 宏，或基于 `enum` 状态加转换表的构造器，与 XState 模块整合。
6. **流 DSL**：基于 `|>` 的组合写法（与 R7 一起做）。

**验收**：hello world、计数器、请求-应答三个示例的代码行数比现在减少 40% 以上；宏生成代码有单元测试；文档给出“经典写法 / DSL 写法”对照。

### 8.8 R6：分布式完善（P1）

**规模与内存（v7）**：规模测试暴露了三个问题，均已修复：

| 问题 | 原因 | 修复 | 效果 |
|---|---|---|---|
| 默认 256 MB 仓颉堆下 10 万顶层 Actor 即内存溢出 | 每个 Actor 约 7.6 KB（RSS） | 见下面三行 | 子 Actor 存活堆约 **2.7 KB**，顶层 Actor 约 3.5–4 KB |
| 停止 10 万顶层 Actor 需 7.1 s | `removeUserActor` 每次线性扫描全部顶层 Actor | 按路径最后一段直接查找 | 0.7 s |
| 每个 Actor 多处理一条消息 | 见 R1 的 `system.stop` 修复 | — | — |

内存削减来自实测：仓颉中默认容量的 `HashMap` 约 900 字节、`ArrayList` 约 200 字节、`Mutex` 约 180 字节。改动为：子 Actor 表、监视表等集合以容量 0 创建（首次使用时才分配）；优先级邮箱只在使用时创建；系统消息队列由“互斥锁 + ArrayList”改为无锁栈（Treiber stack，终止时换入哨兵节点关闭）；不再为每个顶层 Actor 在旧的 `SupervisionManager` 中登记（旧实现登记后从不注销，创建再停止的 Actor 会一直占用内存）；默认监督策略不再按 Actor 存一份。Akka 每个 Actor 约 300–400 字节，差距主要还在每个 Cell 的十余个原子变量与 Option 字段、工厂闭包和路径字符串，后续可继续压缩。

运行大量 Actor 时需要调大仓颉堆上限，例如 `cjHeapSize=8GB`。

**性能数字说明**：本轮在负载 30–80 的机器上开发，同一程序前后两次运行可相差 3 倍，因此不在这里给出对比结论。负载较低时的一次观察：远程吞吐最好值 405 k msg/s（同时段旧版本最好值 154 k msg/s），需要在空闲机器上复测确认。另外确认了一个容易踩的坑：`cjpm build -m <模块>` 不继承 workspace 的 `-O2`，用它构建的基准程序会慢 2–3 倍；基准必须在 workspace 根目录执行 `cjpm build` 后运行（已写入 `tools/ci.sh`）。

3. R6 成员协议（gossip、种子节点、成员事件），在此基础上做 Cluster Singleton 与分片；Replicator 改为增量状态。
4. R4 继续压缩每个 Actor 的内存（目标 1 KB 以内），以及工作窃取。
5. R5 `@Message` 宏；R7 流处理。
