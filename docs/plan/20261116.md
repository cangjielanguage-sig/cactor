### 2.3 三个门禁缺陷（已修复）

**缺陷 1：`tools/env.sh` 在 nounset 下 source 仓颉 envsetup.sh 直接中止**

- 现象：`/Users/louloulin/cangjie/envsetup.sh: 行 66: DYLD_LIBRARY_PATH: 未绑定的变量`，整条门禁在第一步行 `exit`。
- 根因：`tools/ci.sh` 是 `set -euo pipefail`，它在第 20 行左右 `source tools/env.sh`；env.sh 里 `source envsetup.sh`，而仓颉 1.2.0 的 `envsetup.sh` 用 `eval "env_var_value=\${$env_var_name}"` 读取变量（`_remove_cangjie_paths`），nounset 下遇到未设置的 `DYLD_LIBRARY_PATH` 就报错。
- 修复：source 前记录并 `set +u`，source 后恢复；顺带修「找不到 envsetup.sh 时提示不直观」——按 `CANGJIE_HOME` / `~/cangjie` / `~/.cangjie/1.2.0/cangjie` 探测，本机装在 `~/cangjie`。
- 验证：`env -u CANGJIE_HOME bash -c 'set -euo pipefail; source tools/env.sh; command -v cjpm'` → 打印 `~/cangjie/tools/bin/cjpm`。

**缺陷 2：TLS 用例因找不到 OpenSSL 3 而以 SIGABRT 崩溃（7 例）**

- 现象：`TOTAL 928 / PASSED 921 / ERROR 7`，7 例全是 TLS：`RemoteTlsTest` 6 例 + `ClusterTlsTest.clusterFormsAndCallsAcrossNodesOverTls`；`REASON: Crashed with exit code 134`。
- 栈：`stdx.crypto.keys.GeneralPrivateKey.decodeFromPem` ← `cactor_remote.RemoteTls.fromPem`（`modules/remote/src/remote_tls.cj:137`），前置告警 `is loading libcrypto in an unsafe way`。
- 根因：`stdx.crypto.keys` 通过 dlopen 找 `libcrypto`；找不到 OpenSSL 3 时落到系统 `/usr/lib/libcrypto.dylib`（LibreSSL 桩），后者拒绝加载并 abort。**与证书无关**：`tools/tls-test-certs/ca.pem` 有效期 `notAfter=Oct 15 2126`，`notBefore=Nov 8 2026` 均正常。
- 定位（可复现）：只跑该套件
  - 不加路径：`./target/release/unittest_bin/cactor_tests.unit.remote_semantics --filter='*RemoteTlsTest*'` → 6/6 ERROR；
  - `DYLD_FALLBACK_LIBRARY_PATH=/opt/homebrew/opt/openssl@3/lib:$DYLD_FALLBACK_LIBRARY_PATH` → 6/6 PASSED；
  - `ClusterTlsTest` 同样由 ERROR 转 PASSED。
- **第二层原因**（第一次修复后 `cjpm test` 仍 7 例 ERROR）：dyld 有两个搜索路径。`unittest_bin` 直接跑时走
  `DYLD_FALLBACK_LIBRARY_PATH`，而 **`cjpm test` 起子进程只透传 `DYLD_LIBRARY_PATH`**，`DYLD_FALLBACK` 被丢掉。
  所以第一次只设 FALLBACK 时"直接跑 70/70 通过、经 cjpm test 仍 7 例崩溃"；两个都设之后
  `cjpm test modules/tests/src/unit/remote_semantics` → 70/70 通过。
- 修复：`tools/env.sh` 在 Darwin 上把 `/opt/homebrew/opt/openssl@3/lib` **同时**追加到
  `DYLD_LIBRARY_PATH` 与 `DYLD_FALLBACK_LIBRARY_PATH`（追加而非前置：不顶掉调用方显式指定的 libcrypto）。
  本机同时装了 openssl@3/3.4/3.5/3.6/4，固定取 `openssl@3`（3.x ABI 稳定）。
  顺带把仓颉库路径的追加改成幂等——`envsetup.sh` 也会设这两个变量，原本会把同一条路径加两遍。
- 遗留（记入 `docs/plan/20261106.md` §3.11 的 DA8）：Linux 上同理由 `LD_LIBRARY_PATH` 决定，本机无法验证；建议在 CI 镜像里显式装 `libssl3` 并在 `ci_pr.sh` 里断言 TLS 两套件计数，防止再次"静默 7 红"。

**缺陷 3：`tools/check_macro_surface.sh` 依赖 bash 4+ 的 `mapfile`**

- 现象：`mapfile: command not found` → `found: unbound variable` → 门禁判红（宏公开面本身没问题）。
- 根因：脚本 shebang 是 `env bash`，但 `ci.sh` 用 `bash tools/...` 调用，取 PATH 上的 bash；macOS 自带 `/bin/bash` 是 3.2，没有 `mapfile`，也没有关联数组的安全空值语义。
- 修复：改成可移植的逐行读取与字符串比较；`ci.sh` 里所有子 shell 脚本改用 `"${BASH:-bash}"`，让子进程与门禁使用同一解释器（这正是 `guard` 注释里"用当前 PATH 中的 Bash"的意图）。
- 验证：`/bin/bash tools/check_macro_surface.sh` 与 `/opt/homebrew/bin/bash ...` 均输出「通过（无占位宏）」，退出码 0。

### 5.1 删除类批次的"复用优先"决策树（B3/B4 通用）

删除前逐项回答，任一步为"是"就**不要新建实现**：

1. **这个能力有活的消费者吗？** 没有 → 进第 2 步；有 → 不删。
2. **仓库里已有等价且被使用的实现吗？** 有 → 直接删旧的，把测试/文档迁到现成实现（如 `log` → `logging`，
   `patterns.backpressure` → `streams`，`core.error` → `actor/signals.cj` + 监督策略，`contracts` → `check_module_deps.py`）。
3. **只有 demo / 测试在用吗？** 是 → 先删 demo（或进 E54 的 `NOT_RUN.not-built` 白名单），再删包。
4. **既不重复、也没宿主，但能力本身是对的？** → 记入本文"待重建"清单，等有真实扩展点需求时再做
   （`plugin`、`attributes` 属此类，宿主应是 E49 收敛后的 `ActorSystem` 扩展点）。**不留在树里当摆设**。
5. 任何删除都必须过 `cjpm build` + 全量测试；包级 import 图只用于筛候选，**权威判据是删掉后构建成功**（§6.3）。

### 5.2 为什么不是"按 E 编号顺序做"

- E20′（runtime 6.2k+6.6k 行）排在第 4 批而不是第 1 批：它最大、最容易踩到隐式依赖，必须等 B3 把
  "删包 → 更新快照 → 更新 CHANGELOG → 跑门禁"这条流水线跑顺，再动它。
- E19′（sleep）独立于删除，可以并行；但它会改 182 处断言，若与 B3/B4 同批做，
  一旦门禁变红无法区分是"删错了"还是"等待改坏了"。
- E50/E51 放最后：它们都依赖"代码侧已收口"，且都需要本会话之外的权限。

### 6.3 复核方法（本次用的三种，可复用）

1. **import 图**（用于 E20′/E46/E47）：收集每个 `.cj` 的 `package` 与 `import`（跳过注释行），
   把成员导入归一化到最长已存在包名，统计"除自身外谁 import 我"。零消费者即为候选。
2. **符号引用**（仅作二次确认）：把候选包的 `class/interface/struct/enum/type/func` 名做全仓全词匹配。
   **不要只靠它**：`size`/`toString`/`LogLevel`/`PriorityQueueMailbox` 这类同名项会造成大量误报
   （本次首轮分析就把 `cactor_foundation.hashing` 误判为死代码，实际 `persistence` 在用 `crc32`）。
3. **删掉再构建**（唯一权威判据，本次对 23 个候选逐个执行）：备份候选文件 →
   `rm` → `source tools/env.sh && cjpm build` → `returncode == 0` 才算"可删" → 还原。
   脚本草稿在 `/tmp/verify_dead.py`，结果在 `/tmp/dead_verify.log`。

   **为什么必须做这一步**：import 图只看到"包级"，抓不到同模块内的依赖方向。
   `cactor_runtime.dispatcher` 在 import 图上零消费，实际删掉后构建报
   `can not find the following dependencies: cactor_runtime.dispatcher.factory`
   （同一模块的 `dispatcher_pool.cj` 进口了子包）。反之 `cactor_runtime.message`、
   `mailbox/queue`、`mailbox/ringbuffer` 图上是零引用、构建也确实通过。
   所以粒度必须是**文件/目录**，判据必须是**构建成功**。
   符号匹配在**活包里的死文件**上是唯一有效的手段：包级 import 图看不出
   `EnhancedDispatcherFactory` 是死类，只能靠"这个类名全仓库只出现 1 次"来判断。

**两个坑（本次都踩过）**：
- 包声明不只有 `package x.y`：`public package` / `protected package` / `macro package` 都存在
  （宏包写作 `macro package cactor_macros.actormacro`）。正则漏掉 `macro package` 会把
  宏包误判成死包——首版 `quality_metrics.py` 就误报了 `cactor_macros.common`。
- "零消费"不等于"整棵子树都死"：只有做不动点（消费者的消费者也死了）才能挖出
  `dispatcher.batch_processing` 这种"只被死包引用"的子树；反过来，活包里的死文件又只有
  符号级能看见。**两层缺一不可**。

### 9.5 本批顺带查清的两个门禁缺陷（**都与会话前的"全绿"记录冲突，必须记下来**）

**缺陷 4：`env -u VAR cmd` 会把 `DYLD_*` 一起丢掉 → TLS 用例 7 例 SIGABRT**

- 现象：`tools/ci.sh` 的「全部测试」在 B3 后稳定 `PASSED: 913 / ERROR: 7`，全部是 TLS：
  `RemoteTlsTest` 6 例 + `ClusterTlsTest` 1 例，`Crashed with exit code 134`，日志里有
  `WARNING: .../cactor_tests.unit.remote_semantics is loading libcrypto in an unsafe way`。
- 但直接跑同一个二进制 3/3 通过，经 `cjpm test` 3/3 失败。
- 根因：macOS 在执行**平台二进制**（dyld 共享缓存里、SIP 保护的 `/usr/bin/env`、`/bin/bash`、`/usr/bin/timeout`）时
  会把环境里的 `DYLD_*` 全部剔除。`env -u CACTOR_LOG_LEVEL cjpm test ...` 里的 `/usr/bin/env` 就是平台二进制，
  于是 `tools/env.sh` 刚准备的 `DYLD_LIBRARY_PATH` / `DYLD_FALLBACK_LIBRARY_PATH` 在 exec `cjpm` 时被删掉，
  `cjpm` 起的测试进程只能找到 `/usr/lib/libcrypto.dylib`（LibreSSL 桩）→ 直接 abort。
- 复现（决定性证据，在**未做任何 B3 改动的 HEAD 干净 worktree** 上同样成立）：`HEAD` 上
  `cjpm test modules/tests/src/unit/remote_semantics --parallel 1` → 退出码 1、同一条 libcrypto 警告。
  所以这不是本批引入的，而是"上一版 env.sh 修复只解决了 dyld 搜索路径，没解决谁来传递环境变量"。
- 修法：`tools/ci.sh` 把 `env -u CACTOR_LOG_LEVEL cjpm test ...` 改成
  `( unset CACTOR_LOG_LEVEL; cjpm test ... )`——子 shell 里不 exec 新程序，环境原样传给 `cjpm`。
  实测修复后全量 **920/920，TLS 0 例 ERROR**。
- 推论（写进 §7 跟踪）：**任何"用 `env` 包装仓颉程序"的写法都会静默破坏 `DYLD_*`**；
  `DYLD_*` 只在"父进程是非平台二进制"时才能继承，因此脚本必须自己 `source tools/env.sh`。

**缺陷 5：6 个 `tools/*.sh` 依赖继承的 `DYLD_*`，经 `guard`（timeout + bash）调用时必崩**

- 现象：修复缺陷 4 之后，门禁走到「示例自检」，`tools/cluster_demo.sh` 的 3 个节点进程全部
  `Abort trap: 6`，`Reason: no LC_RPATH's found`，最后打印 `有进程失败`。
- 根因：`cluster_demo.sh` / `cluster_crash_demo.sh` / `ddata_stress.sh` / `journal_crash_demo.sh` /
  `lease_contend_demo.sh` / `bench_gate.sh` 都只有一段
  `if ! command -v cjpm; then source "${CANGJIE_HOME:-$HOME/.cangjie/1.2.0/cangjie}/envsetup.sh"; fi`：
  ① 默认路径 `~/.cangjie/1.2.0/cangjie` 与本机安装位置（`~/cangjie`）不符，source 静默失败；
  ② 在门禁里 `cjpm` 已在 PATH，整段直接跳过。于是它们完全依赖继承的 `DYLD_*`，
  而 `guard` 用 `timeout --foreground "${BASH}"  script.sh`，`${BASH}` 是 `/bin/bash`（平台二进制）
  → `DYLD_*` 在 exec bash 时被剔除 → 节点进程找不到 `libcangjie-runtime.dylib`。
- 为什么以前"绿"：用 `/opt/homebrew/bin/bash`（**非**平台二进制）启动 ci.sh 时 `DYLD_*` 能穿透，
  所以这类缺陷只在"按文档用 `/bin/bash`"时暴露——正是 §2.1 记录的那个组合。
- 修法：6 个脚本统一改成无条件 `source tools/env.sh`（幂等、含 CANGJIE_HOME 探测与 OpenSSL 3 兜底）。
  实测：`timeout --foreground /bin/bash tools/cluster_demo.sh` → `全部进程正常退出`；
  `--tls` 变体 → `TLS 连接 6 条，被拒绝 0 条`；`cluster_crash_demo.sh` → 通过。

**结论**：B1 的"干净 shell 用 `/bin/bash` 跑通"只验证了 `env.sh` 本身能被 source，没验证
"`env.sh` 导出的 `DYLD_*` 能否穿过门禁里所有的 `bash`/`env` 包装"。B3 把这两层都补上了，
`tools/ci.sh` 因此第一次在 `/bin/bash` 下真正走完「全部测试 → 并行集群 → 示例自检」全链路。
