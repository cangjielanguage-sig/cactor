## 1. 结论与目标

### 1.1 结论

1. **仓颉 1.2.0 的宏能力足以支撑完整 DSL** [V]：宏可解析 `ClassDecl` / `EnumDecl`、遍历成员、用 `quote` 插值生成方法；`@actorReceive`（`modules/macros/src/macros.cj:685`）已经真实工作，能按 `onXxx(m: T, ctx)` 方法生成类型分派的 `receive` 并在重复类型时报错。DSL 化不是"能不能"的问题，而是"如何收敛到最佳形态"的问题。
2. **现有宏体系是三个时代的叠加物** [V]：`cactor_macros` 里 20 个宏中多数（`@actor`、`@handler`、`@safe_execute`、`@smart_route` 等）原样返回输入；只有 `@actorReceive` 和 `@Message` 是真实实现，却与占位宏混在同一文件（909 行单文件）。
3. **"自然语言化"的正确打开方式是分层**：不是做一个万能宏，而是把 DSL 拆成 **协议层（枚举 + `@Message`）→ 声明层（`@actor` + `on`/`when`）→ 行为层（`Behaviors` 组合子）→ 运算符层（`<<`、`|>`、时长字面量）→ 流程层（状态机/流）**，每层独立可用、独立测试。
4. **"自然语言"的载体是四个语法面**：消息即名词（枚举 case / `@Message` 类）、处理器即动词（`on` + 命名处理器）、修饰语即组合子（`when` / `within` / `onTimeout` / `supervised`）、句子即管道（`<<`、`|>`、`ask`）。
5. **宏包与运行时必须分离**：仓颉要求宏定义在独立 `macro package` 且先于调用方编译 [V]；因此 DSL 的运行时类型（`Behaviors`、`on` 组合子、时长扩展）放在 `cactor_core.dsl` / `cactor_runtime`，纯代码生成宏放 `cactor_macros`。

### 1.2 目标

- **G1**：hello world、计数器、请求-应答三个示例，DSL 写法比经典写法**代码行数减少 ≥40%**（R5 原有验收，继续保留）。
- **G2**：漏处理消息、重复处理器、错误字段类型等错误**全部在编译期报错**，错误信息可读（指出类名、方法名、消息类型）。
- **G3**：宏生成的代码有单元测试（宏展开后语义 = 手写等价代码），运行时**零反射、零额外分配**。
- **G4**：一条主路径：删除占位宏，`modules/macros` 按功能拆文件；文档给出"经典 / DSL"对照。
- **G5**：为后续 Agent 场景铺路——Agent 消息协议（`Ask`/`Tell`/`ToolCall`/`ToolResult`/`Stream`）能用同一套 DSL 一屏写完。

## 2. 仓颉 DSL 能力盘点（调研结论）

### 2.1 已验证能力 [V]

| 能力 | 结论 | 证据 | 用途 |
|---|---|---|---|
| 宏解析类并生成方法 | ✅ `parseDecl` + `cls.body.decls.add(parseDecl(quote(...)))` | `modules/macros/src/macros.cj:685` `@actorReceive` | `@actor` 生成 `receive`、`name`、`description` |
| `quote` 插值 | ✅ `quote($arms case m: $t => ...)`，`ToTokens` 支持 Token/Tokens/字符串 | 同上 | 代码模板 |
| 宏内编译期报错 | ✅ `throw ASTException("可读信息")` | 同上：重复 `onXxx` 类型即报错 | 穷尽性/重复检查 |
| 接口内默认实现运算符 | ✅ `operator func <<` 可链式 | `modules/core/src/actor/actor_ref.cj:59` | `ref << a << b` |
| `extend` 接口 | ❌ 编译报错 *extending type 'Interface-Ref' is not allowed* | 20261028 §7.11 | 运算符必须定义在接口内 |
| `extend` 内置类型属性 | ✅ `100.millis` | `modules/core/src/dsl/durations.cj` | 时长字面量 |
| 尾随 lambda | ✅ | 20261028 §7.11 | `Behaviors.receive { ctx, msg => ... }` |
| `|>` 管道 | ✅ | 20261028 §7.11 | 流 / 句子式组合 |
| 枚举 ADT + 穷尽 match | ✅ 语言内置 | — | 消息协议编译期检查 |
| 宏必须独立宏包、先编译、`public` 修饰 | ✅ 官方约束 | 仓颉官方文档《宏的定义与导入》 | 模块结构约束 |

### 2.2 语言限制 [V]

| 限制 | 影响 | 对策 |
|---|---|---|
| 没有 Scala 的 `!`、`?` 单二元运算符 | `tell` 不能用 `!` | 统一用 `<<`（已在 `ActorRef` 落地） |
| 不能 `extend` 接口 | 不能给用户自定义接口事后加运算符 | 运算符直接内建在 `ActorRef` / `TypedActorRef` 接口里 |
| 宏与调用方不能同包 | 每个使用 DSL 的包都要依赖宏包并接受编译顺序 | 宏包只做代码生成、无运行时依赖；运行时 API 全部在非宏包 |
| 宏调试体验弱（无源码级断点） | 宏错误排查成本高 | 宏全部配"展开后等价代码"测试；错误信息带类名/方法名 |
| 没有保证执行的顶层静态初始化 | `@Message` 编解码器需显式 `registerCodec()` [V] | 提供 `cactor.registerMessages(...)` 批量注册入口，作为唯一约定 |
| 没有字段级原子、缓存行填充等底层手段 | DSL 不能靠底层 hack 换性能 | DSL 目标定为"编译期生成 = 手写性能" |

### 2.3 官方文档要点 [G→P0 复核]

- `Tokens` / `Token` / `TokenKind`：宏的基本操作单元，可按 `TokenKind`+字符串直接构造任意 Token。
- `quote` 表达式：以 `$(...)` 插值，插入的表达式须实现 `ToTokens`。
- 宏分类：非属性宏 `macro M(input: Tokens): Tokens` 与属性宏 `macro M(args: Tokens, input: Tokens): Tokens`；声明前调用可省略括号。
- 编译顺序：宏包 → 调用包；`macro package` 中仅宏定义（及 re-export）对外可见。

> 参考：docs.cangjie-lang.cn 《宏的简介》《宏的实现》《Tokens 相关类型和 quote 表达式》《编译、报错与调试》。

## 3. 对标调研摘要

| 框架 | DSL 形态 | 值得借鉴 | 不照搬 |
|---|---|---|---|
| **Akka Typed (Scala)** | `Behaviors.receive { (ctx, msg) => ... }` 返回下一个行为；枚举 case 即消息；`Behaviors.supervise(...).onFailure(...)` | "行为是一等值"的消息处理模型；监督组合子链式写法 | Scala 的 `case` 模式匹配内嵌、`!`/`?` 运算符（仓颉无对应） |
| **Erlang/OTP** | `receive Pattern -> ... end` 原生模式匹配；`gen_server` 的 `handle_call/handle_cast` 约定 | 按意图分派（call/cast/info）天然像自然语言 | 动态类型，编译期无法查漏 |
| **Pekko (Java)** | `newBuilder().match(T.class, ...)` 链式 | Java 无宏时用 builder 补偿——提示我们：**能用宏就不该让用户写 builder** | 冗长的泛型声明 |
| **Proto.Actor-go / Rust actix** | `Message` trait + `Handler<M>` impl，编译器逐条检查 | 每条消息一个 handler、编译期逐条核对 | trait impl 样板多 |
| **Fluent API 研究线**（Evans/Fowler；Roth & Gil《Fluent APIs in Functional Languages》） | 方法链 + 类型状态（typestate）把语法合法化为编译期约束 | "让非法句子无法通过编译"是自然语言 DSL 的核心标准 | 过度 typestate 导致类型爆炸，仓颉泛型推断弱于 Scala，需克制 |

**提炼出的三条设计准则**：
1. **名词化**：消息是值（枚举 case / `@Message` 类），不是字符串字面量——杜绝 `tell("order", data)`。
2. **动词化**：处理方法是 `on` + 语义名，宏按参数类型精确分派，`match` 穷尽检查兜底。
3. **修饰语化**：超时、监督、重试、背压都是组合子，链式拼在句子尾部，而不是散落在处理体内。

### 4.2 缺什么

1. **`@actorReceive` 与经典 `match` 分发并存**，文档没有唯一推荐路径；宏包 909 行单文件，无按宏拆分。
2. **没有 `on(msgType) { ... }` 声明式构造器**：现在是按方法名 `onXxx` 约定分派，缺少与 `Behaviors.receive` 风格对齐的 lambda 写法。
3. **没有修饰语组合子**：`when/within/onTimeout/supervised/withStash` 未统一成一条链式 API（`TypedBehaviors` 有部分能力但未与宏路径打通）。
4. **穷尽性检查缺失**：枚举协议的 `match` 在手写 `receive` 里靠自觉；宏路径只检查"重复类型"，不检查"枚举 case 是否全覆盖"。
5. **宏生成代码无等价性测试**：现有测试验证行为，未验证"宏展开 = 手写等价"。
6. **占位宏污染公开面**：用户 `import cactor_macros.*` 后看到 20 个宏，18 个是假的，伤害信任。

## 5. 设计原则

1. **一条主路径**：每种写法只保留一个推荐实现。占位宏一律删除；`@actorReceive` 升级为 `@actor`（保持旧名一个版本周期作别名）。
2. **编译期优先**：所有能静态检查的错误（漏 case、重复 handler、非法字段类型、在处理体内直接读别的 Actor 状态）都推到编译期，运行时不做兜底检查。
3. **零运行时开销**：宏只生成"本来就要手写"的代码；DSL API（组合子）使用泛型 + 值类型，不引入 Any 装箱、不反射。
4. **自然语言可读性优先，但克制**：不为语法糖引入无法静态检查的动态机制；每个 DSL 结构必须能映射到一句可读英语（"on PlaceOrder, within 3.seconds, reply with OrderPlaced"）。
5. **分层可降级**：不想用宏的用户可以退到 `Behaviors.receive` 尾随 lambda；不想用 lambda 的用户可以退到经典 `match`。三档写法共享同一运行时语义。
6. **与 20261029 API 重构对齐**：DSL 公开面收敛进 `cactor` 门面（`cactor.dsl`），`modules/macros` 仅暴露宏名本身。

## 6. DSL 总体设计（五层）

```
L5 流程层   状态机 DSL（@StateMachine，接 XState 模块）｜流 DSL（|>，接 Streams）   [P4/P5]
```

## 7. 自然语言化消息处理：核心 API 设计

### 7.1 L1 协议层：消息即名词

```cangjie
// 推荐一：enum 协议（进程内、类型化）
enum OrderMsg {
    | PlaceOrder(orderId: String, qty: Int64)
    | GetOrder(orderId: String, replyTo: TypedActorRef<Option<Order>>)
    | Cancel(orderId: String)
}

// 推荐二：@Message 类（需远程传输/跨网络时）
@Message
class PlaceOrder <: Message {
    let orderId: String
    let quantity: Int64
    ...
}
```

增强点：
- **[已实现 ✅]** `@actor` 宏的协议清单核对：`@actor[cases = [A, B, C]]`（类式协议，每种消息一个处理方法）与
  `@actor[protocol = E]`（枚举协议，一个处理方法 + 内部 match）。漏处理 / 协议漂移 / 重复处理器都在编译期报错。
  注：原设想的 `protocol = <枚举>` 自动解析 case 不可行（§12 假设 A 证伪），改为显式清单 + 宏逐项核对；
  枚举协议内部的穷尽性由仓颉 `match` 在编译期保证。
- **[已实现 ✅]**（2026-10-30 v4）Ask 语法糖：类型化路径的 `ctx.ask(target, factory, timeout) { outcome => ... }`
  与 `TypedAsk.ask` 此前已可用；本轮补齐经典路径的零侵入写法 `askInbox()`（`cactor_core.dsl`，
  临时收件箱实现 `ActorRef`，请求消息自带 `replyTo`，目标 Actor 无需解包包装消息；
  超时抛 `AskTimeoutException`，`tryGet` 返回 `Option`）。
  未采用"宏识别 replyTo 参数自动生成包装"的设想：宏无法改写消息类型定义（且会引入隐式行为），
  显式 replyTo 本就是 DSL 的标准写法。

### 7.2 L3 声明层：`on` 即动词（核心层）

**形态 A：类内命名处理器（主力，延续 `@actorReceive` 并增强）**

```cangjie
@actor(protocol = OrderMsg)   // 可选：声明协议用于穷尽性检查
class OrderAgent {
    var orders = HashMap<String, Order>()

    // "on PlaceOrder: record the order and reply OrderPlaced"
    func onPlaceOrder(m: PlaceOrder, ctx: ActorContext): MessageResult {
        orders[m.orderId] = Order(m.orderId, m.qty)
        m.replyTo << OrderPlaced(m.orderId)
        return MessageResult.Handled
    }

    // 修饰语：按消息类型的超时/重试，生成包装逻辑
    @within(3.seconds)
    @retry(2, backoff = 100.millis)
    func onAskModel(m: AskModel, ctx: ActorContext): MessageResult { ... }
}
```

宏职责（相对现有 `@actorReceive` 的增强）：
1. **[已实现 ✅]** 分派规则不变（`onXxx(msg: T, ctx)` → `case m: T => this.onXxx(m, context)`），保持已验证路径 [V]。
2. **[已实现 ✅]** `cases = [...]` / `protocol = X` 参数：显式清单逐项核对，缺失报错 *"Counter 未处理 Query，缺少 onQuery(m: Query, ctx: ActorContext)"*。
3. **[已验证 ⚠️ → 降级实施]** 修饰宏 `@within` / `@retry` 不可行（§12 假设 B 证伪），改为运行时组合子 `within(limit, name) { ... }` / `retry(n) { ... }`（`modules/core/src/dsl/handler_combinators.cj`）。
4. **[已实现 ✅]** 缺省参数（`ctx` 可省略、`MessageResult` 可省略改返回 `Unit`）——宏按实际签名生成适配。
5. **[已实现 ✅]** 错误信息规范化：`<类名>: <原因>（<方法名>）`。

**形态 B：lambda 声明（对齐 Akka Typed，用于无状态/函数式场景）**

```cangjie
let counter = Behaviors.receive<OrderMsg> { ctx, msg =>
    match (msg) {
        case PlaceOrder(id, q) => ...
        case GetOrder(id, replyTo) => replyTo << ...; Behaviors.same()
    }
}
```

这层主要是**打通**：`Behaviors`（现 `TypedBehaviors`）已有 `setup/receive/supervise/withTimers/withStash/intercept` [V README]。
**[已实现 ✅]** 已收敛：`cactor_core.dsl.Behaviors` 门面（组合子面完整，含 intercept/monitor/logMessages），

## 8. 宏实现方案

### 8.1 `@actor` 宏（P1 核心，基于已验证的 `@actorReceive`）

```
输入: @actor(protocol = OrderMsg)? class C { ... onXxx(m: T, ctx)? ... }
输出: class C { ... 原成员 ...
        receive(message: Message, context: ActorContext): MessageResult {
            match (message) {
                case m: T => this.onXxx(m, context)     // 每个 onXxx 一条
                case _ => MessageResult.Unhandled
            }
        }
        name/description 缺省实现（若无）
      }
编译期检查:
  1. 仅 class [V 已有]
  2. 同一消息类型多个 on 方法 → 报错 [V 已有]
  3. onXxx 参数签名非法（参数数≠2、首参非类型）→ 报错（增强）
  4. protocol = E 时：解析 EnumDecl（import 查找 [G]），逐 case 核对 → 缺失报错（增强）
  5. 无 onXxx → 报错 [V 已有]
```

### 8.2 修饰宏 `@within` / `@retry`

- 方案：修饰宏解析 `FuncDecl`，把方法体包进 `try { ... } catch` + 计时 + 循环，生成同签名函数并附加标记属性；`@actor` 展开时读取标记并包裹 case。
- **依赖**：宏调用宏（`quote` 中嵌宏调用）官方支持 [G]；P0 用实验工程验证。
- 降级方案：若嵌套宏不可靠，`@within/@retry` 改为 `@actor` 的命名参数（`@actor(timeoutFor = [("onAskModel", 3.seconds)])`）——语义不变、语法稍逊。

### 8.3 `@Message` 迁移 + 增强

- 原样迁到 `message/message_macro.cj` [V]。
- **[已实现 ✅]** 增强（P2）：支持 `Option<T>`、`HashMap<String, T>` 字段（`MessageFieldWriter/Reader` 新增
  `writeOptionXxx / readOptionXxx / writeXxxMap / readXxxMap`）；字段级错误用 `diagReport` 定位到具体字段（带行列），
  例如 `@Message: BadField.payload 的类型 Int32 不支持`。注：`Token` 的位置信息只能通过 `diagReport` 呈现，
  解析出的 Token 用 `dump()` 取不到行号 [V]。

### 8.4 等价性测试

每个宏配一对测试：**手写等价类**与**宏展开类**在同一测试套中跑同样的消息序列断言相同结果；另加"负例"测试（重复类型、缺 case、非法字段）断言编译失败信息。宏编译失败的断言方式 [G]：把负例放独立 `examples/negative` 目录由脚本 `cjc` 编译并 grep 错误信息（P0 验证 CI 可行性；若不可行则降级为仅正向等价测试 + 文档注明）。

## 附录 A：经典写法 / DSL 写法对照（验收 A1/A6 素材）

**经典（现状）**：

```cangjie
class Counter <: Actor {
    public prop name: String { get() { "counter" } }
    public prop description: String { get() { "计数器" } }
    var count: Int64 = 0
    public func receive(message: Message, context: ActorContext): MessageResult {
        match (message) {
            case m: Increment => count += m.n; MessageResult.Handled
            case m: Get => m.replyTo << CountIs(count); MessageResult.Handled
            case _ => MessageResult.Unhandled
        }
    }
}
```

**DSL（P1 后）**：

```cangjie
@actor(protocol = CounterMsg)
class Counter {
    var count: Int64 = 0
    func onIncrement(m: Increment, ctx: ActorContext) { count += m.n }   // Unit 省略返回
    func onGet(m: Get, ctx: ActorContext) { m.replyTo << CountIs(count) }
}
```

漏写 `onCancel`（若协议含 Cancel）→ 编译期：`Counter: 未处理 CounterMsg.Cancel，缺少 onCancel(m: Cancel, ctx: ActorContext)`。
