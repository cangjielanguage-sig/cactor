# CActor 与 protoactor-go 性能对比：差距从哪来、怎么追平（2026-10-31）

本文记录与 [protoactor-go](https://github.com/asynkron/protoactor-go) 的对比、差距的定位过程和修改。
与 Akka 的早期对比见 [20261028-performance.md](20261028-performance.md)。

## 1. 结论

- 修改前，多对 ping-pong（protoactor 官方 inprocessbenchmark 写法，场景 6）CActor 只有 protoactor-go 的约 1/30，
  并且**工作线程越多越慢**：同样的消息量，8 个工作线程消耗的 CPU 是 1 个线程的约 18 倍。
- 根因不是单条消息的路径太长（单线程时每条消息约 150–210ns CPU，与 Go 的约 110–150ns 同一量级），
  而是几处**只在多线程并发时才暴露**的问题。其中最大的一处是每条消息一次的 `message is AutoReceivedMessage`：
  仓颉判断"别的包里定义的类是否实现某接口"时，多个线程会互相阻塞。
- 修改后，4 个工作线程时每条消息的 CPU 与单线程相同。场景 6 在同一时间窗口内交替运行：
  CActor 33.6M msg/s，protoactor-go 36.2M msg/s（约 93%），整个进程的 CPU 时间基本相同（1.49s vs 1.43s）；修改前为 1.2M msg/s、42.7s。
- 类型化路径有同一类问题的另一种形式：core 的泛型代码以用户类型实例化后，`is C<T>` 和分配 `C<T>` 都要在运行时查找类型信息，
  多线程时互相阻塞。改为种类标记 + `@Frozen` 工厂函数后见第 4.6 节。
- 由外部线程（非 Actor）发送的场景 1、2 仍落后 1.5–3 倍，原因与对策见第 6 节。

### 对比结果

同一个容器、同一时间窗口内三方交替运行 3 轮，吞吐为"最好 / 中位"，延迟为中位轮次的值。
"修改前"是 d66c684；"进程 CPU"是整个基准进程的 CPU 秒数（中位）。

| 场景 | protoactor-go | CActor 修改前 | CActor 修改后 |
|---|---|---|---|
| [1] 单 Actor（M msg/s） | 6.18 / 6.02 | 6.26 / 4.41 | 4.15 / 4.00 |
| [2] 扇出 8 发送方 × 100 Actor | 12.75 / 12.45 | 5.07 / 4.61 | 4.19 / 3.84 |
| [3] ping-pong 延迟 P50 / P99（µs） | 66.0 / 121.7 | 3.8 / 9.4 | 1.5 / 2.0 |
| [4] Ask 延迟 P50 / P99（µs） | 5.0 / 8.4 | 5.2 / 12.9 | 5.2 / 11.1 |
| [6] 多对 ping-pong 64 × 100k（M msg/s） | 36.18 / 35.66 | 1.21 / 1.19 | 33.63 / 33.63 |
| [6] 进程 CPU（s） | 1.43 | 42.66 | 1.49 |
| 类型化互发 64 对（M msg/s，相对值） | — | 1.09 / 1.08 | 1.99 / 1.93 |
| 类型化互发 进程 CPU（s） | — | 4.92 | 2.68 |

上表的"修改后"还不含第 4.6 节的类型化修改和 runNext 窃取。这两项是之后加的，加上之后机器一直处于重负载（load 20–40），
墙钟吞吐没有参考价值，下表只列测量窗口内每条消息的 CPU（ns，两次各 3 轮交替运行的中位值）：

| 场景 | 加入前 | 加入后 | 变化 |
|---|---|---|---|
| 类型化互发，枚举协议，返回 `same()` | 2476 / 3625 | 2250 / 2593 | −9% / −28% |
| 类型化互发，每条消息返回新行为 | 2546 / 4859 | 2375 / 3656 | −7% / −25% |
| 类型化互发，接口协议 | 2273 / 3171 | 2000 / 2921 | −12% / −8% |
| [6] 多对 ping-pong（经典） | 116 / 173 | 124 / 178 | 噪声范围内（最低值 116 vs 117） |
| 经典互发 | 281 / 421 | 281 / 437 | 噪声范围内 |

类型化的收益主要来自消除多线程争用，负载很高时线程很少真正并行，所以这里的降幅小于第 4.6 节微基准的差距；
同样的互发形状，类型化每条 CPU 仍是经典的约 8 倍，剩余开销见第 6 节。

说明：

- [1]、[2] 修改前后的差别在噪声范围内：另一次交替运行中修改后的中位值为 4.02 / 3.80，修改前为 3.99 / 3.75。
- [3] protoactor-go 的接收方 goroutine 在两次消息之间会挂起，延迟包含一次唤醒；CActor 的工作线程空闲时先自旋 50µs 再休眠。
- 类型化互发是 `cbench tbounce`（64 对、每对 64 条在途，枚举协议，处理函数返回 `same()`），计数口径与场景 6 不同，只比较相对值。

## 2. 对比方法

- 同一个容器，cgroup CPU 限额 4 核（`/sys/fs/cgroup/cpu.max = 400000 100000`），宿主机 32 核。
  Go 1.25+ 会按限额把 GOMAXPROCS 设为 4；`nproc` 显示 32，不能用它判断可用的核数。
- 这个 cgroup 与其他构建任务共用，经常 100% 的调度周期都被限流，墙钟吞吐可以在几分钟内相差 5–10 倍。
  因此：
  - 两边**交替运行、多轮取最好值和中位数**，只比较同一时间窗口内的比值；
  - 同时记录**测量窗口内的进程 CPU 时间 / 消息数**（`/proc/self/stat` 的 utime + stime）。
    这个指标受其他负载的影响小得多，是判断"浪费在哪里"的主要依据。
  - 负载很高时线程很少真正并行，多线程争用反而测不出来：判断"是否争用"的微基准要在相对空闲时跑。
- 对照程序：`bench/protoactor`（场景与 `real_benchmark` 一一对应）。
  官方 inprocessbenchmark 用回信的 `Sender` 发下一批，而回信的 `Sender` 是 client 自己，第一批之后实际是自己发给自己；
  修正后（记住 echo）protoactor-go 的吞吐从约 38M 降到约 12M msg/s，对比使用修正后的写法。

## 3. 定位过程：逐个排除

只靠墙钟数字无法定位：负载高时所有配置都慢。下面每一步都用"每条消息 CPU"或单独的微基准确认。

| 假设 | 实验 | 结论 |
|---|---|---|
| 跨线程交接太多（亲和调度下每跳都跨线程） | 让每对 Actor 落在同一工作线程（零跨线程消息） | 4 线程仍比 1 线程多 5 倍 CPU，**不是主因**（但仍值得优化，见 4.4） |
| 环境（限流、缓存冷） | 4 个单线程进程并发 vs 1 个 4 线程进程 | 前者每条 175–212ns，后者 450–750ns：**问题在进程内** |
| 邮箱锁争用 | 统计 `tryLock` 失败次数 | 0 次 |
| 空闲自旋 | 统计空闲次数与自旋时间 | 整个测试只有几十次、约 1ms |
| GC / 分配 | 测量窗口内的 GC 次数与分配量 | 0 次 GC，每条约 0.4 字节 |
| 伪共享 | Actor 之间插入 512B–64KB 的存活填充 | 无明显变化 |
| ThreadLocal 太慢 | 微基准 | 确实很慢（见 5），但去掉后问题仍在 |
| 消息类型 | 同样的两个 Actor 互发 `StringMessage` vs 用户定义的消息类 | **用户消息类慢 8 倍**，定位到每条消息一次的接口类型检查 |
| 仓颉处理器数（`cjProcessorNum`，默认按核数 32） | 设为 4、8 | 场景 1–6 无明显变化，**不是原因** |
| 类型化比经典慢（同样的互发形状每条 2µs vs 0.22µs） | 1 / 2 / 4 线程分别测 | 单线程就慢 4 倍，多线程再慢 2 倍；拆开逐项测，定位到 core 泛型代码里的分配与类型检查（见 4.6） |

关键现象：工作线程从不休眠，但承载它们的原生线程每秒自愿切换数千到数万次、sys 时间与 user 时间相当，
`/proc/<tid>/wchan` 显示阻塞在 futex 上——是仓颉运行时内部的锁，而不是 CActor 的代码在等。

## 4. 修改

### 4.1 控制消息改为按具体类匹配（最大的一处）

`invoke` 原来先做 `message is AutoReceivedMessage`，命中才逐个匹配 5 种控制消息。
用户消息都定义在别的包，这次检查的结果总是"否"，而这种检查：

| 检查（-O2） | 1 线程 | 4 线程并发 |
|---|---|---|
| core 包的类 `is AutoReceivedMessage` | 20–40ns | 20–40ns |
| 用户包的类 `is AutoReceivedMessage` | 60–80ns CPU（墙钟 0.5µs） | **0.4–0.8µs CPU，墙钟 1–4µs** |
| 用户包的类匹配 5 个具体类 | 30ns | 35ns |

改为直接匹配 5 个具体类，语义不变（这 5 个类就是全部会被特殊处理的控制消息）。

### 4.2 类型化行为的特殊值判断不用泛型类型检查

每条类型化消息都要判断返回的行为是不是 `same` / `unhandled` 等。原实现 `b is SameBehavior<T>`：
core 包里的泛型代码以用户类型 T 实例化后，这种检查单线程约 30ns，4 线程时约 0.4µs CPU 且互相阻塞。
改为让需要特殊处理的行为继承一个非泛型的内部基类 `SpecialBehavior`，带种类标记，判断时做一次非泛型类检查（约 10ns，不争用）。

### 4.3 运行时不再启动从不使用的 DispatcherPool

每个 `CActorRuntime` 启动时都会启动一个 `DispatcherPool`（4 个旧调度器），它从不接收任务，
却有多个线程以 10µs–100µs 的间隔轮询。空闲系统因此占约 11% CPU，并持续唤醒仓颉调度器、与 Actor 工作线程争抢处理器。
删除后空闲 CPU 降到原来的约 1/8。

### 4.4 调度：runNext、工作捐赠、按 cgroup 限额定线程数

- **runNext**（与 Go 调度器的 runnext 同理）：工作线程上运行的 Actor 唤醒一个空闲 Actor 时，
  被唤醒的 Actor 紧接着在本线程运行，而不是去它的亲和线程。一来一回的两个 Actor 留在同一线程，不跨核同步、不需要唤醒。
  槽位里原有的 Actor 挤回它的亲和线程，扇出仍然并行；连续插队 16 次后让给队列里的其他 Actor，避免饿死。
- **工作捐赠**：就绪队列是单消费者的，空闲线程不能直接窃取。改为空闲线程举手，忙线程每运行一个 Cell 前看一眼，
  有人举手就把自己队列里的下一个 Cell 交出去。
- **线程数**：默认取核数的 1/4（4–64），再不超过 cgroup CPU 限额（向上取整）。限额 4 核的容器里从 8 个降到 4 个。
  同一台机器上把线程数改回 8，场景 2 从 3.8M 降到 2.5M。
- **当前工作线程**用 `Thread.currentThread.id` 查启动时建好的只读表，不用 `ThreadLocal`（见第 5 节）。
- **runNext 可被窃取**（Go 的 `runqsteal` 也会窃取 runnext）：完整测试中 `testRememberedEntitiesRestartElsewhereWithoutNewMessages`
  稳定失败，原因是分片 Actor 在 receive 里调用 `Replicator.addToSet`，同步等待 Replicator Actor 处理完；
  被唤醒的 Replicator 正排在分片 Actor 所在线程的 runNext 里，两者互相等待到 10 秒超时。
  原来的亲和调度也有同样的风险（两者亲和线程相同的概率约 1/线程数），runNext 把它变成了必然。
  现在 runNext 槽位是原子引用：空闲线程每 10µs 检查一次别的线程，执行计数 100µs 内没有变化且 runNext 非空，就取走运行。
  分片本身也改用不等待的 `addToSetAsync`（库代码不应在 receive 里阻塞）。只靠窃取、不改分片时该测试同样通过。
  仍未覆盖：卡住的线程自己就绪队列里的 Cell（单消费者队列，不能被别的线程取），需要真正的工作窃取。

### 4.5 邮箱：双缓冲数组，稳态零分配

原邮箱是 Vyukov 链表：仓颉的原子变量是独立的堆对象，每条消息至少分配两次（节点 + 原子引用）。
微基准中分配与 GC 不随线程数扩展（8 线程的总吞吐与 1 线程相当），链表版本在多线程下偶发跌到 1/5–1/10，
8 线程时甚至出现过 OOM（已出队节点仍指向后继，推测与 GC 成串滞留有关）。

新邮箱与 protoactor-go 的 goring 同类：发送方持锁追加到 incoming 数组，消费方读空本地数组后持锁整体交换，之后无锁处理整批。
稳态零分配，单线程每条 CPU 从约 214ns 降到约 161ns，GC 次数降为 0。
没有选自旋锁：扇入时持锁方被抢占，其余发送方空转，实测比 Mutex 慢 3 倍以上。
缓冲区在第一条消息到达时才分配，突发后超过 256 的缓冲区在交换时丢弃。

### 4.6 类型化路径：core 泛型代码里的分配与类型检查

同样的互发形状（64 对、每对 64 条在途），经典 Actor 每条约 0.22µs CPU，类型化约 2µs；
类型化单线程就慢约 4 倍，2、4 线程时每条 CPU 再升到约 1.7µs、2µs，又是负扩展。逐项拆开测：

| 操作（-O2，相对空闲时） | 1 线程 | 4 线程并发 |
|---|---|---|
| 用户包里分配泛型类 `C<T>` | 5–9ns | 8–9ns |
| core 里 `TypedBehaviors.same<T>()`（分配 `SameBehavior<T>`） | 38–40ns | **390–430ns，互相阻塞** |
| core 里 `receiveMessage<T>(...)`（分配 `ReceiveBehavior<T>` 与闭包） | 90ns | **530–550ns** |
| core 里 `ClassicTypedRef<T>.tell`（分配 `TypedEnvelope<T>`） | 60ns | **300–330ns** |
| 同上，`same<T>()` 标 `@Frozen` 后 | 17ns | 22ns |

结论：core 的泛型代码以别的包的类型 T 实例化时，编译器不会在使用方的包里为 T 特化，
分配 `C<T>`、判断 `is C<T>` 都要在运行时查找实例化类型的类型信息，这个查找多线程时互相阻塞。

修改：

- `TypedBehaviors` 中构造行为的工厂函数（`receive`、`receiveMessage`、`setup`、`same`、`unhandled`、`stopped`、`ignore`、
  `empty`、`receivePartial`）标为 `@Frozen`。`-O2` 下函数体在调用方的包里展开，分配在那里按具体类型实例化。
  用户每处理一条消息都会调用其中之一（返回 `same()` 或返回新行为），这是类型化路径上最热的分配。
  代价：这些函数的实现会编译进调用方，修改实现后依赖它的包需要重新编译（cjpm 从源码构建，不受影响）。
- `TypedBehaviors.start()` 原来对每个新行为依次做 `as DeferredBehavior<T>`、`as SupervisedBehavior<T>`、`as StartableBehavior<T>`
  三次泛型检查；适配器和 `TransformBehavior` 再做一次 `as StoppedBehavior<T>`。
  现在监督行为和 4 种组合行为（信号、转换、过滤、拦截）也继承 `SpecialBehavior`，带 `SUPERVISED` / `STARTABLE` 标记，
  `start()` 与 `applyNext` 先比较标记，普通行为只做一次非泛型类检查；确认种类之后才做泛型转换。

试过但没有采用：tell 时改用非泛型信封（载荷存为 `Any`），接收时 `payload as T`。
分配确实变便宜（约 35–40ns），但 `as T` 在 core 泛型代码里每次约 75–100ns，合计反而比 `TypedEnvelope<T>`（分配 50–90ns + 类型匹配 5–10ns）慢。

## 5. 仓颉性能要点（本次新增的实测）

| 操作（-O2） | 1 线程 | 4 线程并发 | 建议 |
|---|---|---|---|
| `ThreadLocal.get` | 130–330ns | 0.5µs CPU，墙钟 1–7µs（阻塞） | 热路径禁用 |
| `Thread.currentThread.id` | 25ns | 25ns | 需要线程身份时用它查只读表 |
| 别的包的类 `is 某接口`（否） | 60–80ns | 0.4–0.8µs，互相阻塞 | 热路径改为具体类匹配 |
| core 泛型代码里 `is C<T>`（T 来自别的包） | 30ns | 0.4µs，互相阻塞 | 改为非泛型基类 + 标记 |
| core 泛型代码里分配 `C<T>`（T 来自别的包） | 40–90ns | 0.3–0.55µs，互相阻塞 | 工厂函数标 `@Frozen`，或避免逐条分配 |
| core 泛型代码里 `x as T` | 75–100ns | 80–300ns | 热路径避免 |
| 具体类匹配 / 泛型类实例方法里 `case e: TypedEnvelope<T>` | 4–10ns | 不变 | 可放心使用 |
| 原子引用 load / store / swap / CAS | 1–25ns | 不变 | 可放心使用 |
| `Mutex` 加锁 + 解锁（无争用，含 `synchronized`） | 约 28ns | — | 可放心使用；代价主要在跨核传递锁所在的缓存行 |
| `sleep(Duration.Zero)` | 25–190ns | 不变 | 自旋时让出处理器 |
| 小对象分配 | 约 10ns | 8 线程时每线程约 77ns，总吞吐不涨 | 热路径避免逐条分配 |

判断方法：同样的工作，多线程时每条消息的 CPU 明显高于单线程、原生线程自愿切换很多而业务代码并没有等待，
多半是运行时内部的锁。用"同一进程多线程 vs 多个单线程进程"可以快速区分进程内问题和环境问题。

`@Frozen` 的依据：编译器头文件 `CHIR/IR/Value/Value.h` 中 `IsFuncWithBody` 的说明——
"func declared in imported package with @Frozen and compiled with O2" 的函数体对调用方可见。

## 6. 仍然存在的差距与下一步

- **外部线程发送（场景 1）**：发送耗时约等于总耗时，瓶颈在发送方，每次 tell 约 235ns（Go 约 105–135ns）。
  单线程时同样的步骤（读调度标志、`Mutex` 加解锁、写槽位、原子 store）只要约 37ns CPU，其中 `Mutex` 约 28ns，
  所以多出来的约 200ns 来自跨核：消费方处理得比发送方快，频繁读空并交换缓冲区，
  每次交换都把锁、incoming 计数和数组所在的缓存行从发送方的核上拿走，发送方下一条消息再逐个取回。
  下一步：减少发送方与消费方共同写的缓存行，例如把 incoming 计数与调度标志合并为一个原子状态字，
  或者消费方读空后不立即交换、先处理就绪队列里的其他 Actor。
- **扇出（场景 2）**：Actor 处理得比 8 个发送方快，每次运行只处理 3–4 条，约每 4 条 tell 就要重新调度一次，
  每条消息 CPU 0.9–1.2µs（Go 约 0.3µs）。仓颉的 `Mutex` 和原子变量都是独立的堆对象，无法像 Go 那样把锁和状态放进同一缓存行，
  每条消息牵涉邮箱锁、incoming 数组、计数、调度标志、就绪队列头等多个缓存行的跨核传递。
  Go 的被唤醒 goroutine 进入发送方所在 P 的 runnext，不争用共享队列，空闲 P 再来窃取。
- **类型化路径每条消息仍有一次泛型分配**：`TypedEnvelope<T>`（50–90ns，多线程时争用）。tell 经接口虚调用到 core 的实现，`@Frozen` 帮不上。
  可以考虑：协议类型本身是 `Message` 时免信封、或由运行时提供按具体类型实例化的发送入口。
- **`NotInfluenceReceiveTimeout` 的接口检查**：只在设置了接收超时的 Actor 上每条消息执行一次，同样会在多线程时争用。
- **真正的工作窃取**：捐赠只在有线程完全空闲时触发，负载不均但都不空闲时不会重新分配。
- 运行时自身的问题（接口检查、泛型实例化的类型信息查找、`ThreadLocal` 的并发性能）应反馈给仓颉团队。
