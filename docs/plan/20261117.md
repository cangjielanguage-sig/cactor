## 1. 摘要

### 1.1 一句话结论

**CActor 的"内核 + 单集群语义"已经接近 Akka 的水平，工程纪律（门禁、快照、弃用生命周期、零占位代码）甚至更好；
真正的差距集中在"跨集群/跨数据中心的产品化层"与"运维可观测的产品化层"，而不是 Actor 内核本身。**

具体来说，12 个库、78,177 行生产代码里：

> 按 §3 的 46 条对标项统计：**✅ 20 / 🟡 9 / ❌ 17**。

| 维度 | 判定 | 一句话 |
|---|---|---|
| Actor 内核（类型化/经典、监督、背压、流） | **达标** | 对标 Akka Typed + Reactive Streams，`cactor_core` 与 `cactor_streams` 已是完整实现 |
| 单集群语义（成员/故障检测/脑裂/分片/单例/PubSub/Receptionist） | **达标** | Akka Cluster 的核心子集都在，且有真实 TCP + 多进程演练 |
| Distributed Data（CRDT + Replicator + 增量 + pruning） | **基本达标** | 对标 Akka Distributed Data 的 delta-CRDT + RemovedNodePruning；**缺 Map 系 CRDT** |
| 持久化（EventSourced + Journal + Snapshot + DurableState + Fencing） | **达标** | 对标 Akka Persistence + Orleans 存储抽象的核心语义 |
| **跨 DC / 多集群** | **缺失** | 无 `roles`、无 data-center、无 ClusterClient、无跨集群复制（Akka Multi-DC / Orleans Multi-Cluster） |
| **分片协调状态持久化** | **缺失** | 分片归属只活在内存，节点全灭后重新分配（Akka 有 `sharding-state` 插件） |
| **可观测性的产品化** | **半成品** | 有 Prometheus 文本与 tracing 骨架，但**没有跨节点 trace 上下文传播、没有 OTel 导出、集群侧零指标** |
| **流的产品化** | **达标但缺编排** | Reactive Streams 齐备，但缺 GraphDSL 级别的组合（Akka Streams 生态） |
| **测试与验证工程** | **达标** | 多进程 barrier、故障注入、虚拟时钟、混合版本演练、API 快照门禁 |
| **性能** | **同档** | 实测单 Actor 9.43M msg/s、ping-pong P50 1.0µs（优于 Akka 2.25µs 与 protoactor 10.5µs） |

### 1.2 三条主线（差距的性质不同，补法也不同）

1. **拓扑层缺失（最贵、最像"顶级框架"）**：角色（roles）、数据中心、多集群客户端、跨集群复制。
   → 这是 Akka Multi-DC / Orleans Multi-Cluster / CockroachDB 式系统的分水岭，也是本轮最大的欠账。
2. **状态层缺失（最容易出事故）**：分片协调状态不持久化、分片分配策略写死、脑裂策略写死、
   DData 只有集合/计数器没有 Map、快照策略没有。
   → 事故发生在"节点全灭后"，而这类场景当前**没有任何自动恢复语义**。
3. **运维层半成品（最影响落地）**：trace 不跨进程、集群指标为零、指标注册表与 Prometheus 输出是两套。
   → 分布式系统出问题时的第一需求是"能不能看见"，这一层目前不达标。

### 1.3 工作量总览

| 批次 | 主题 | 规模 | 估算 |
|---|---|---|---|
| **C1** | 拓扑基础：成员 roles + 优雅退出接线 + 远程路径寻址 | 3 项 | 2.5 天 |
| **C2** | 多数据中心（Multi-DC） | 1 大项 | 3.5 天 |
| **C3** | 分片状态持久化 + 两个 SPI（分配策略 / 脑裂提供者） | 3 项 | 3 天 |
| **C4** | DData Map 系 CRDT | 1 项 | 2 天 |
| **C5** | 流编排（GraphDSL 风格组合子） | 1 项 | 3 天 |
| **C6** | 可观测性产品化（trace 传播 + OTel + 集群指标统一） | 3 项 | 3 天 |
| **C7** | 测试与生命周期增强（多节点 TestKit / 快照策略 / Grains 存储与提醒） | 3 项 | 2.5 天 |
| **C8** | 传输与一致性增强（压缩/大消息 / at-least-once 高层 API / Projection） | 3 项 | 3 天 |
| | **合计** | **20 项** | **约 22.5 天** |

> 优先级口径：**P0 = 阻断生产**（C1/C2/C3 的一部分）、**P1 = 显著影响可靠性或可运维性**、**P2 = 生态完整性**。
> 本文不建议一次性做完 C1–C8；建议按 §5 的顺序推进，且 **C3 的 SPI 化必须先于 C2**，否则多 DC 会把写死策略的缺陷放大。

### 2.3 性能：同档甚至更好（有实测数字）

来源：`bench/results/20261101-macos-config-matrix.md`（macOS arm64 14 核，2026-11-01，CActor `d83391f` vs Akka 2.6.21 vs protoactor-go）：

| 场景 | CActor | protoactor-go | Akka 2.6.21 |
|---|---|---|---|
| 单 Actor 吞吐 | **9.43M msg/s** | 3.67M | 8.58M |
| 扇出 8×100 | 10.65M | 22.26M | **32.01M** |
| ping-pong P50/P99 | **1.0 / 2.0 µs** | 10.5 / 28.5 µs | 2.25 / 8.75 µs |
| Ask P50/P99 | **2.0 / 6.0 µs** | 2.3 / 7.2 µs | 7.29 / 16.7 µs |
| 远程 TCP 回环 | **770k msg/s** | — | 277–753k |

**唯一明显的性能短板**：扇出场景（Akka 32M vs CActor 10.65M）——这是邮箱调度路径的差异，属于内核优化而非分布式能力，
且本次未做新的复测（本机 load 常年 20–80，见 `docs/plan/20261116.md` §4.1）。

## 4. 差距逐项分析

每项统一格式：**现状（证据）→ 影响 → 方案（优先复用仓内已有件）→ 可证伪验收 → 工作量/依赖**。

### 4.1 【P0】成员角色（roles）与拓扑元数据缺失

- **现状**：`Member` 只有四个字段（`modules/cluster/src/membership/membership.cj:105`）：
  `address` / `status` / `upNumber` / `uid`。没有任何"这个节点是数据节点还是控制节点"的表达。
  `ClusterSettings`（:570）也没有 roles 配置项。grep `roles`/`role` 在 `membership.cj` = 0 命中。
- **影响**：
  ① 无法表达"只有带 `data` 角色的节点托管分片"这类最常见的部署约束；
  ② 无法做跨 DC 路由（没有 DC 归属，见 4.3）；
  ③ 运维侧只能靠地址前缀约定。
- **方案**（复用现有成员表，不新建并行体系）：
  1. `Member` 增加 `roles: HashSet<String>` 与 `dataCenter: String`（默认 `""`）；
  2. `ClusterSettings` 增加 `withRole(...)` / `withDataCenter(...)`，进入 gossip 载荷并参与兼容性比对
     （复用已有的 `joinCompatibility` 机制，见 :585）；
  3. **分片分配只考虑带 `data` 角色的成员**——这是 roles 唯一的强制语义，其余角色仅是元数据。
- **可证伪验收**：
  - 新用例 `rolesFilterShardOwners`：3 节点中 1 个无 `data` 角色 → 该节点 `ownerCount() == 0`，
    另外 2 个节点分片数之和 = 总分片数；
  - 新用例 `roleMismatchIsRejectedOnJoin`：加入方 roles 与集群不一致 → `joinRejection() != None`；
  - `grep -c 'public let roles' modules/cluster/src/membership/membership.cj` ≥ 1，且旧成员（无 roles 字段）仍能加入（向后兼容）。
- **工作量**：1.5 天（`Member` + `ClusterSettings` + gossip 载荷 + 分配过滤 + 3 例）。
- **依赖**：无；**必须在 C2（Multi-DC）之前**，否则 DC 要重做成员结构。

### 4.2 【P0】脑裂策略不可插拔（`DowningProvider` 缺失）

- **现状**：`DowningStrategy`（`modules/cluster/src/membership/sbr.cj:23`）是**枚举**
  （`NoDowning`/`AutoDownAfter`/`KeepMajority`/`KeepOldest`/`StaticQuorum`），决策函数 `sbrDecide`（:60）是纯函数。
  用户想加"自定义 quorum 规则"必须改框架源码。
- **影响**：这是 Akka `DowningProvider` 的对标位。金融/工业场景常见"按业务分区做 quorum"（如"华东 + 华南至少一个可达"），
  枚举写死就做不到。
- **方案**：
  1. 新增 `interface DowningProvider { func decide(view: MembershipView, unreachable: HashSet<String>): SbrDecision }`，
     框架内置的枚举实现改为 `BuiltinDowningProvider`（保留 `sbrDecide` 纯函数，不动现有语义）；
  2. `ClusterSettings` 增加 `withDowningProvider(...)`；
  3. **决策函数保持纯函数**（现有 `sbrDecide` 是好的设计，别破坏）——SPI 只提供"视图 → 决策"这一步。
- **可证伪验收**：
  - 新用例 `customDowningProviderIsConsulted`：注入一个"可达成员少于 2 就判定分裂"的 provider →
    断言 `cluster.isDownedBySbr()` 为 true，而默认 `KeepMajority` 下为 false；
  - 现有 SBR 用例**全部保持通过**（`modules/tests/src/unit/cluster/sbr_test.cj`），证明内置语义未变；
  - `grep -c 'public interface DowningProvider' modules/cluster/src` = 1。
- **工作量**：1 天。
- **依赖**：无。

### 4.3 【P0】多数据中心 / 集群客户端 / 跨集群复制（最大缺口）

- **现状**：
  - grep `dataCenter|multi-dc|MultiDc` 在 `modules/*/src` = **0 命中**；
  - grep `ClusterClient` = **0**；
  - grep `Artery` = 4（只在注释里）；
  - 远程层是**点对点 TCP**（`modules/remote/src/remoting.cj`），节点之间平等，没有"网关/中继"概念。
- **影响**：无法跨机房部署（机房之间延迟高、需要就近访问、需要异地容灾），
  无法做"从另一个集群访问本集群的服务"（ClusterClient 是 Akka 与 Service Fabric / Orleans 的通用入口）。
- **方案**（分三小步，每步独立可交付）：
  1. **C2a 数据中心感知**：`Member.dataCenter`（复用 4.1 的字段）；`ClusterSettings.withDataCenter(...)`；
     跨 DC 成员**不参与 gossip**（各自的 DC 内自成一圈），只交换"DC 目录"（哪些 DC 存在、各自的种子地址）。
     这是 Akka Multi-DC 的核心机制，先做它。
  2. **C2b DC 感知路由**：分片分配默认"同 DC 优先"（先在本地 DC 内找 owner，跨 DC 兜底），
     并提供 `ShardAllocationStrategy` SPI 的第一个实现（见 4.4）。远程路径寻址（4.1 的第三点）也在这一步落地。
  3. **C2c 集群客户端**：一个"外部进程"用 `ClusterClient` 按**逻辑名**访问集群内的服务
     （内部用 receptionist + 路径寻址 + 远程 ask），无需加入集群。
- **可证伪验收**：
  - C2a：`twoDataCentersGossipSeparately`——两个 DC 各 2 节点，同 DC 内互相可见，**跨 DC 不可见**（成员表里没有对方），
    但 `dcDirectory()` 能列出两个 DC；
  - C2b：3 个 DC × 2 节点，实体调用延迟落在**同 DC** 节点（用 `/cluster/shards` 的 owner 地址断言）；
  - C2c：`clusterClientResolvesLogicalName`——独立进程（不加入集群）通过 `ClusterClient.request("svc", msg)`
    拿到响应；断连目标后明确失败而非挂起。
  - 三步各自的负例：DC 目录不一致 → 明确失败（不静默）。
- **工作量**：3.5 天（a 1.5 / b 1 / c 1）。
- **依赖**：**C2a 依赖 4.1（roles + dataCenter 字段）**；C2b 依赖 4.4（分配策略 SPI）。
- **边界**：不做跨集群数据复制（Akka CrossClusterReplication）——那需要 DC 间的数据同步协议，
  属于另一个量级；本文只把它列为"未来可选"，见 §6.3。

### 4.4 【P0】分片协调状态不持久化 + 分配策略写死

- **现状**：
  - `shardOwner`（`modules/cluster/src/membership/sharding.cj:86`）是**写死的 rendezvous 哈希**：
    `members` 排序后取模，**没有可插拔策略**（grep `ShardAllocationStrategy|allocationStrategy` = 0）；
  - 分片归属**只存在内存**（`ClusterSharding` 的 region 状态，`sharding.cj:2174`），
    节点全灭后靠重新 gossip + 重新分配恢复，**没有"上次分配"的持久记录**。
- **影响**：
  ① 节点全灭重启 → 所有分片重新洗牌，实体全部迁移（Akka 有 `sharding-state` 插件可保持分配）；
  ② 想改哈希函数（如从 md5 换 xxhash）必须停机全量迁移；
  ③ 无法做"按业务亲和性分配"（如把购物车分片优先放在同机房）。
- **方案**：
  1. **分配策略 SPI**：`interface ShardAllocationStrategy { func allocate(shard, members, current): Option<Address> }`，
     内置实现保留现有 rendezvous（`shardOwner` 的算法原样搬进 `RendezvousAllocation`），
     新增 `LeastLoadedAllocation`（复用 `rebalance.cj` 的负载视图与 `decideRebalance` 纯函数，不重写）；
  2. **协调状态持久化**：把"分片 → 宿主"的映射写入 `DurableStateStore`（**复用 `modules/persistence/src/durable_state.cj`**，
     不引入新存储）；重启后先读旧映射再与当前成员求交集，**交集内保留原宿主**，
     只有"原宿主已不在集群"的才重新分配（这正是 Akka `sharding-state` 的语义）。
  3. **迁移期的双写与回滚**：旧映射与新分配并存时，写入两处；任一失败即整体回滚到旧映射（避免半迁移）。
- **可证伪验收**：
  - `allocationStrategyIsPluggable`：注入一个"总是选第一个成员"的策略 → 分片宿主分布随之改变（断言可观测差异）；
  - `shardAssignmentSurvivesFullClusterRestart`：6 分片 3 节点 → 全灭 → 用原成员标识重启 →
    **断言每个分片回到原宿主**（当前实现会重新洗牌，此用例在实现前必须失败——先红后绿）；
  - `staleAssignmentIsReassignedWhenHostGone`：旧映射指向已移除节点 → 该分片重新分配且**不会**留在旧宿主；
  - 现有 `sharding_test.cj` / `sharding_handoff_test.cj` / `sharding_rebalance_test.cj` **全部保持通过**。
- **工作量**：3 天（SPI 0.5 + 持久化 1.5 + 测试 1）。
- **依赖**：C2b 依赖本项的 SPI。

### 4.5 【P1】没有集群感知的路由器

- **现状**：`modules/patterns/src/routing/` 只有**本地**路由（`router.cj` / `router_actor.cj` / `advanced/advanced_routing.cj`），
  grep `ClusterAware|AdaptiveLoadBalancing` = 0。集群里有 `Receptionist`（按名查找）但**没有"按负载/按成员路由"的路由器**。
- **影响**：跨节点的负载均衡只能由应用自己写；Akka 的 `cluster-aware` 路由器（按成员负载选目标）是常用能力。
- **方案**：
  1. 新增 `modules/patterns/src/routing/cluster_router.cj`：`ClusterRouter`，按 `Member` 列表 + 负载报告选目标，
     **复用** `cluster/membership/rebalance.cj` 的 `RebalanceView`/负载语义与 `Cluster.subscribe`（`membership.cj:1792`）；
  2. 目标集合来自 `Receptionist.findTyped`（按 `ServiceKey<T>`）或 `Receptionist.find`（按名）；
  3. 成员掉线时自动剔除并重新解析（订阅 `ClusterEvent`）。
- **可证伪验收**：
  - `clusterRouterPicksLeastLoadedMember`：3 个候选，负载不同 → 断言选中负载最低者；
  - `clusterRouterDropsDownedMember`：候选之一被 down → 断言不再选它；
  - `clusterRouterFailsWhenNoCandidates`：候选全空 → 明确失败（不静默丢消息）。
- **工作量**：1.5 天。
- **依赖**：无（可与 C4 并行）。

### 4.6 【P1】DData 缺 Map 系 CRDT 与视图不一致缓解手段

- **现状**：`modules/cluster/src/ddata/crdt.cj` 只有 `GCounter`/`PNCounter`/`GSet`/`ORSet`/`LWWRegister`；
  grep `ORMap|LWWMap|ORMultiMap|PNCounterMap` = **0 命中**。
  `docs/plan/20261106.md` §3.11 DA5 也把 "无 minCap / WriteTo(n) 缓解视图不一致" 记为遗留。
- **影响**：Map 是分布式配置、会话、路由表最常用的数据结构；没有 Map CRDT 就只能把整个 Map 塞进一个 `LWWRegister`（最后写入者赢，丢并发更新），
  或退化成"以 key 为粒度的多条 LWWRegister"（用户自己拼）。
- **方案**：
  1. **复用 `ORSet` 的内部机制**（点标记 + 墓碑 + pruning）实现 `ORMap<K,V>`：
     每个 key 一个 `ORSet<V>`，按 key 独立合并——这正是 Akka `ORMap` 的定义，不要另造一套点标记协议；
  2. `LWWMap<K,V>`：每个 key 一个 `LWWRegister<V>`，同样按 key 独立合并；
  3. `Replicator` 侧**不改协议**：现有"按 (来源,键) 编号 + 增量"对 Map 天然适用（键即 key），
     只在编码层加一个 kind（复用 `TypedPayloadBox` 的 kind 机制，不新增线协议版本）；
  4. `minCap`：把现有 `ReadConsistency.ReadMajority` 扩展一个 `ReadMinCap(n)`，读至少 n 个副本即返回（Akka `minCap` 语义），
     缓解"写方 3 节点视图、读方 5 节点视图"时过半读写不相交的问题（DA5 Q5）。
- **可证伪验收**：
  - `orMapMergesPerKeyIndependently`：两个节点并发改同一 Map 的不同 key → 合并后两个 key 都在；
  - `orMapConcurrentSameKeyKeepsBoth`（add-wins 语义）：同 key 并发 add 两个值 → 合并后两个都在（与现有 `ORSet` 语义一致）；
  - `lwwMapConvergesToHighestTimestamp`；
  - `readMinCapReturnsAfterNReplicas`：3 节点里 1 个不可达 → `ReadMinCap(2)` 成功、`ReadMajority` 明确失败；
  - 现有 `crdt_concurrency_test.cj` / `ddata_consistency_matrix_test.cj` 全部保持通过。
- **工作量**：2 天。
- **依赖**：无。

### 4.7 【P1】持久化的生命周期能力不足（快照策略 / upcast / Grain 存储）

- **现状**：
  - 快照**能存能读**（`modules/persistence/src/snapshot_store.cj`），且**已有固定形态的自动策略**：
    `EventSourcedActor.snapshotEvery`（`event_sourced_actor.cj:31`，每 N 个事件自动存一次）与
    `RetentionCriteria.snapshotEvery(n, keep)`（`typed/model.cj:153`，保留最近 M 份）。
    缺的是**策略的表达力**：只能按事件数，不能按时间/状态大小/业务时机，也没有"按 persistenceId 调整"的入口；
  - `EventAdapter`（`modules/persistence/src/typed/engine.cj:288`）有 `manifest`，但**没有 schema 演进/upcast**；
  - `Grain`（`modules/cluster/src/membership/grains.cj`）**不接存储**：grep `storage|Storage` = 0，
    状态要用户自己在 `onActivate` 里读 `DurableStateStore`；
  - `persistence/reminders/reminders.cj` 提供了通用 reminder，但**没接到 Grain 上**。
- **影响**：
  ① 快照全靠用户自觉 → 事件日志无限增长（生产事故常见）；
  ② 事件类型改名/加字段后，旧事件无法升级 → 重放失败；
  ③ Grain 状态持久化要写样板代码，正是 Orleans `IGrainStorage` 要消除的东西。
- **方案**（全部复用已有件）：
  1. **快照策略扩展**：**不新建 `SnapshotStrategy` 抽象**——现有的 `snapshotEvery` + `RetentionCriteria`
     已经是"每 N 事件 + 保留 M 份"，只补两件事：① 支持按时间间隔与按状态大小触发；
     ② 允许按 persistenceId 覆盖默认策略。触发点仍在 `EventSourcedActor`（`event_sourced_actor.cj`），
     存储仍复用 `SnapshotStore`（`snapshot_store.cj:82/166`）；
  2. **upcast**：`EventAdapter` 增加 `upcast(oldManifest) -> newManifest`（可选），恢复时按链式 upcast 升级旧事件；
  3. **Grain 存储抽象**：`GrainStorage` 接口（`read`/`write`/`remove`，**直接复用 `DurableStateStore`**），
     `Grain` 增加可选 `storage` 钩子：`onActivate` 前自动读、`onDeactivate` 前自动写；
  4. **Grain reminder**：`Grains` 增加 `registerReminder(key, delay)`，底层复用 `persistence/reminders` 的单写者实现。
- **可证伪验收**：
  - `snapshotPolicyTriggersAutomatically`：设"每 10 个事件"，写 25 个事件 → 断言快照次数 ≥ 2 且恢复后状态正确；
  - `upcastMigratesOldEvents`：写入 v1 事件 → 用 v2 adapter 恢复 → 断言成功且值正确；
  - `grainStateSurvivesReactivation`：Grain 存计数 → 空闲停用 → 再调用 → 断言计数延续（当前实现不会延续）；
  - `grainReminderFiresOnce`：注册 reminder → 断言只触发一次（重复提醒是常见事故）。
- **工作量**：2.5 天。
- **依赖**：无。

### 4.8 【P1】流编排与持久订阅缺失

- **现状**：
  - `modules/streams/src/` 的 Reactive Streams 实现是完整的，但**没有编排层**：
    grep `GraphDSL|MergeHub|BroadcastHub|Partition|Balance|MergePreferred` = **0 命中**。
    现有组合子只有 `map/filter/flatMapConcat/grouped/merge` 一类**线性**算子。
  - `DistributedPubSub`（`modules/cluster/src/membership/pubsub.cj:186`）的订阅**不持久**：
    订阅者离线后消息即丢，没有"持久订阅者 + 重放"语义。
- **影响**：
  ① 多输入流编排（扇出广播、动态分区）要手写；
  ② "订阅者暂时离线也不能丢消息"是常见的业务要求（订单事件、审计事件）。
- **方案**：
  1. **GraphDSL 风格组合子**：新增 `modules/streams/src/graph.cj`，
     提供 `broadcast`/`merge`/`partitionBy`/`balance`/`zip`/`mapMaterializedValue` 的组合器，
     **基于现有的 `Source`/`Flow`/`Sink` 与 `materializer.cj`**，不重写引擎；
     关键约束：**保持 Reactive Streams 语义**（背压、取消传播不得破坏）——现有 `streams` 的 42 例必须全绿。
  2. **Durable Subscriber**：`DistributedPubSub` 增加 `subscribeDurable(topic, subscriber, fromSeq)`，
     消息带序号持久化到 `DurableStateStore`（复用），订阅者重连时从 `fromSeq` 重放；
     存储上限与保留策略显式可配。
- **可证伪验收**：
  - `broadcastFansOutToAllSubscribers`：1 个源 → 3 个消费者 → 断言三者内容一致且各自有独立背压；
  - `partitionByRoutesByKey`：`partitionBy(msg => key)` → 断言同 key 恒定落到同一分区消费者；
  - `durableSubscriberReplaysMissedMessages`：订阅者离线 → 发布 5 条 → 重连 → 断言 5 条全部收到且顺序正确；
  - `streams` 现有 42 例 + 新增用例全绿，且 `zip`/`partitionBy` 的背压不破坏（用慢消费者断言上游请求量上界）。
- **工作量**：3 天。
- **依赖**：无（但会显著增加 `streams` 的 API 面积，建议单独提交、单独快照）。

### 4.9 【P1】远程传输没有大消息与压缩

- **现状**：`modules/remote/src/remoting.cj` 的帧处理**没有**压缩与分片：
  grep `compress|lz4|chunk|maxFrame` 在 `modules/remote/src` = **0 命中**。
  大消息只能整条编码成一个大帧。
  **注意**：压缩能力在仓里并非从零开始——`foundation/src/serialization/enhanced_serializer.cj:94` 有
  `enableCompression` 开关与压缩实现，但它**只被 not-built 示例 `enhanced_serialization_demo` 使用**，
  没有接入远程帧路径（远程走 `MessageSerializer`/`TypedPayloadBox`）。所以本项是"把已有能力接到线上"，
  不是"从零实现压缩"。
- **影响**：跨机房带宽成本高；大消息（>1 MB）受帧长限制（若实现上限）会被拒；序列化开销无法摊薄。
- **方案**：
  1. **帧长上限 + 明确错误**（先做，成本低、收益大）：设定帧长上限，超限时**明确**抛
     `RemoteFrameTooLargeException`（而不是截断或静默丢）；配合"分片"或"外部存储 + 引用传递"；
  2. **压缩**：对超过阈值的帧做 zstd/lz4 压缩（阈值可配），**只影响线格式、不改 API**；
     混合版本必须兼容：压缩标志位放既有帧头的扩展位（复用 `wire_negotiation.cj` 的能力位机制），
     老节点收到压缩帧 → 明确拒绝（不是静默丢弃）。
  3. **外部存储 + 引用传递**：超阈值消息改传"存储引用"，对端拉取（这才是跨机房正解，也和 Orleans 的 blob 思路一致）。
- **可证伪验收**：
  - `oversizedFrameIsRejectedClearly`：发送超过上限的消息 → 断言抛明确异常且连接仍可用；
  - `compressedFrameIsSmallerAndDecodes`：同一条消息压缩后字节数更小，解码结果一致；
  - `oldPeerRejectsCompressedFrameClearly`：模拟不支持压缩的对端 → 断言明确失败并计数；
  - `largeMessageOverThresholdUsesReference`：超阈值 → 断言线上传的是引用而非全量字节。
- **工作量**：3 天。
- **依赖**：压缩能力位要进 `wire_negotiation.cj`，与 2.0.0 发布同批（E51）。

### 4.10 【P0】可观测性没有产品化（trace 不跨节点 / 集群零指标 / 两套指标）

- **现状**（三条独立的缺口）：
  1. **指标**：`modules/runtime/src/prometheus_metrics.cj`（115 行）只导出**运行时**指标
     （`cactor_actors_live`、`cactor_dead_letters_total`、`cactor_dispatcher_*`…），

- **影响**：分布式系统出问题时，"这条消息经过哪几个节点"根本查不出来；

  1. **统一指标**：让 `foundation/monitoring/metrics.cj` 的 `MetricRegistry` 成为**唯一**指标源，

  3. **导出器**：`Tracer` 增加 OTLP/HTTP 导出（导出器接口 + 批量发送 + 失败不阻塞业务），

  - `tracerExportDoesNotBlockBusiness`：导出器故意抛异常 → 断言业务路径不受影响、错误被计数。
- **工作量**：3 天（指标 1 / 传播 1.5 / 导出 0.5）。

### 4.11 【P1】多节点测试工具与分布式测试的时间控制

- **现状**：

### 4.12 【P2】Durable Subscriber / Projection / 集群内服务的强一致入口

- **现状**：
  - Durable Subscriber：见 4.8（并入 4.8 实现）；

- **依赖**：4.8。

### 4.13 【P2】远程一致性语义缺高层 API（at-least-once / 幂等）

- **现状**：可靠投递的**机制**齐全（`remoting.cj` 的 `ReliableEnvelope`、重发、ACK、去重、放弃），
  但**没有面向用户的高层 API**：grep `at-least-once|AtLeastOnce|deliveryId|DeliveryId` = **0 命中**。
  仓内出现的"幂等"全在**流协议内部**（`cluster/src/streamref/` 的 Subscribe 重发幂等确认、序号去重），
  那是"流挂接"的幂等，不是"消息投递"的幂等。
  用户要"至少一次投递 + 幂等处理"，得自己拿 `ReliableEnvelope` 的序号做去重，
  而 `ReliableEnvelope` 是**框架内部类型**（不是消息协议的一部分）。
- **影响**：业务层的"消息不丢、不重复生效"要自己拼；这是分布式系统里最常被重写一遍的错误。
- **方案**：
  1. 新增 `AtLeastOnceEnvelope<M>`（**用户可见的消息包装**，携带 `deliveryId` + `message`），
     由 `ActorRef.tell` 的一个重载或 `ReliableSend` 入口发送；
  2. 提供 `IdempotentHandler`：对同一 `deliveryId` 的重复投递只执行一次（去重表放 `DurableStateStore`，可配 TTL/容量）；
  3. **明确语义边界**：至少一次 = 可能重复、不会丢（进程崩溃时未 ACK 的会重发）；
     "恰好一次"需要事务边界——不承诺（写进文档）。
- **可证伪验收**：
  - `duplicateDeliveryIsProcessedOnce`：同一 `deliveryId` 投递两次 → 断言副作用只发生一次；
  - `unackedMessageIsRedeliveredAfterFailure`：对端崩溃 → 重启 → 断言消息最终被处理；
  - `deliveryIdSurvivesRestart`：去重表持久化 → 重启后重复投递仍被识别。
- **工作量**：1.5 天。
- **依赖**：无（复用 `DurableStateStore` 与现有可靠通道）。

### 6.2 文档与代码的账实核对

本轮顺带核对了自述与实现的一致性（README.md / docs/FEATURES.md）：

- README 对集群能力的描述（`README.md:464`）逐条对应到实际实现，**没有夸大**；
- README 与 FEATURES 都**没有**声称多 DC、跨集群、ClusterClient、GraphDSL、trace 传播——
  这些是**真的没有**，不是"文档漏写"；
- 因此本文列出的差距全部是**能力缺失**，不是**账实不符**。这一点要写清楚，
  避免下游误以为需要先"修文档"。

### 6.3 明确不做（边界）

1. **不做跨集群数据复制**（Akka CrossClusterReplication）：需要 DC 间的数据同步协议与冲突解决，
   属于另一个量级，且与 §4.6 的 CRDT 语义强相关；等 Map CRDT 与 minCap 落地后再评估。
2. **不做共识层/强一致存储**：Orleans 的存储提供器背后是共识日志；CActor 走"单写者 + fencing + 租约"
   （`persistence/src/fencing.cj`、`file_lease.cj`），这是**不同的取舍**——单写者模型在"一个实体一个写者"
   的场景下更简单且够用。若用户需要跨机房强一致事务，应直接用数据库，而不是在 Actor 层造共识。
3. **不做自研消息压缩库**：压缩用成熟算法（zstd/lz4），只做"帧格式 + 能力位 + 阈值"的接线。
4. **不复活已弃用 API**：`cqrs_system.cj`（CQRSBus/ReadModel，15 处 `@Deprecated`）与 `event_sourcing.cj`
   的 Enhanced 一套都按承诺在 2.0.0 移除；Projection 建在**新的** `EventSourcedActor` 之上。
5. **不改写已验证的分布式语义**：故障检测阈值、SBR 决策、pruning 时序、租约与 fencing 的语义
   在本轮**只加扩展点，不改默认行为**；每个改动都要求现有用例全绿作为前置验收。
