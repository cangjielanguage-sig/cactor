## 1. 什么叫"真实例子"（判据）

`best01`–`best10` 是**API 教程**：一个进程、一个人工编排的流程、结尾断言几个数字。
它证明"类型化 Actor 能用"，但不证明"系统能扛住生产"。本文把"真实"拆成 5 条**可判据**：

| # | 判据 | 反例（现状里的写法） | 真实例子的写法 |
|---|---|---|---|
| **R1 真实业务语义** | 有业务对象、状态机、规则约束（金额不能为负、库存不能超卖、订阅不能重复） | `best01` 的"求和" | 订单有状态迁移与不变量（`Place → Pay → Ship`，`Pay` 后不可 `Cancel`） |
| **R2 真实并发模型** | 同一实体的并发写者被序列化，且**这个序列化是被依赖的**（不是"顺手串行"） | `best05` 测背压丢弃 | 每个租户一个写者，跨租户并行；靠**租约 + fencing** 保证"旧写者不能写" |
| **R3 真实故障模型** | 有明确的故障类型与期望行为（进程被杀、网络分区、消息重复、时钟漂移） | `best03` 只测重启策略 | 写入方被 `kill -9` 后：租约过期 → 新写者接管 → **旧写者的迟到写被 fencing 拒绝** |
| **R4 真实可判定验收** | 验收是**业务断言**，不是"打印成功"；且能在 CI 里判定退出码 | `llm_token_stream` 只有 println | "扣减后库存 ≥ 0"；"重复投递 100 次，副作用只发生 1 次" |
| **R5 真实规模与演进** | 有跨进程/多节点形态、有数据迁移与协议兼容问题 | 全部单进程 | 三进程集群 + 混合版本滚动升级 |

> **反向清单**（本文明确**不选**的例子）：
> - `persistence_demo` —— 依赖的 Enhanced/CQRS/Plugin API 已 `@Deprecated`（2.0.0 移除），新示例不能建在将删的 API 上；
> - `xstate_demo` —— `modules/xstate/src/features/placeholder.cj` 与 `enterprise/placeholder.cj` 是标注"简化实现"的占位，`xstate.md` 的宣传与代码现状不符，不能作为真实示例的地基；
> - `idle_probe` —— 纯观测，无业务语义（R1 不满足）。

### 2.1 一个横在所有真实例子前面的事实

**CActor 没有通用 HTTP 服务端**。全仓唯一的 HTTP 服务端是 `ManagementServer`（`modules/cactor/src/api/management.cj:73`）——
它只支持 GET、只做健康/就绪/指标，且 `addRoute`（`:142`）只能挂 JSON 端点；
HTTP **客户端**也没有 CActor 封装，`llm_http_demo/main.cj:16` 直接用宿主仓颉的 `stdx.net.http`。

因此所有"对外提供服务"的真实例子都必须**自带一层薄 HTTP 门面**。本文统一采用的做法：

- **门面放在示例层，不进库**：用 `std.net` 的 `TcpServerSocket`（`llm_http_demo/main.cj:93` 已有可用写法）+ `stdx.net.http` 的客户端；
- 门面只做"HTTP → Actor 消息"的翻译，**所有业务状态留在 Actor 里**（否则就失去 R1/R2）；
- 由此产生的"CActor 缺 HTTP 服务端"记为**框架缺口 G-1**（见 §6），不进 44 项计分表。

> **实施时已改（2026-11-17）**：不再自建薄门面，改用已实现的 **Lou Web 框架**
> （`modules/examples/cjpm.toml` 里的 `lou` git 依赖，tag `v2.0.0`）。ex01 用 Lou 的
> `app.get` / `ctx.sse` 直接提供 HTTP/SSE；G-1 因此关闭。详见 §8.1、§8.5。

### E1 — LLM Agent 编排运行时（多轮会话 × 工具调用 × 流式 × 崩溃恢复）

**场景与真实约束**

一个对外提供 Agent 服务的进程：用户提问 → 模型流式生成 → 模型发起工具调用（查库/调外部 API）→ 结果回灌 → 继续生成。
真实约束有四条：

1. **一次生成可能几十秒**：不能占住请求线程（真实 HTTP 服务里这等于连接被拖死）；
2. **客户端可能中途断开**：必须能**取消**上游 LLM 请求并停止计费；
3. **工具调用会失败**（超时、5xx、返回脏数据）：不能污染对话状态；
4. **进程可能重启**：会话（消息历史 + 未完成的工具调用）要能恢复。

**为什么是 CActor**

- 会话是**有状态的、按会话串行**的 → 私有上下文 + 串行邮箱（这正是 Actor 模型的核心）；
- LLM 的 token 流是**天然的流** → `modules/streams` 的 `Source`/`Flow`/`Sink` 与背压（`dsl.cj:352-455`）；
- 工具调用是**并发的、可取消的、可失败的** → 一个工具一个 Actor + `ctx.ask`（不阻塞邮箱）+ 监督策略；
- 会话恢复 → 事件溯源（`modules/persistence/src/typed/engine.cj:288` 的 `EventAdapter`、`event_sourced_actor.cj:31` 的 `snapshotEvery`）。

**组件映射（证据）**

| 需要的能力 | CActor 现成件 |
|---|---|
| 会话 Actor（串行、状态私有） | `TypedBehaviors.receive` + "返回新行为"（`modules/core/src/typed/`） |
| 工具调用（并发 + 不阻塞） | `ctx.ask` / `TypedAsk.ask`；`TypedBehaviors.supervise(...).onFailure(restart().withLimit(...))` |
| 流式输出 + 背压 + 取消 | `modules/streams/src/dsl.cj:352-455`（`mapAsync`/`mapAsyncUnordered`/`buffer`）、`kill_switch.cj:15`（`KillSwitch`/`UniqueKillSwitch`） |
| 取消上游 HTTP | `llm_http_demo/main.cj` 已实现"取消直接关闭原始 TCP，唤醒停滞读取" |
| 会话持久化 / 恢复 | `EventSourcedActor` + `journal_v2` + `snapshot_store.cj`；`FileDurableStateStore` |
| 超时与提醒（重试、轮询） | `persistence/reminders/reminders.cj` |
| 指标（QPS、token 数、工具耗时） | `modules/runtime/src/prometheus_metrics.cj`（`/metrics`） |

**消息协议与拓扑**

```
enum AgentCmd {
  | Begin(UserId, SessionId, TypedActorRef<String>)   // 开启一轮
  | Token(String)                                     // 模型增量
  | ToolCall(ToolName, Args, TypedActorRef<ToolResult>)
  | ToolResult(ToolName, Ok(Bool), Payload)
  | Cancel                                            // 客户端断开
  | Persist(SessionSnapshot)                          // 事件持久化
}
```
拓扑：`HTTP 门面` → `SessionActor`（每会话一个，串行） → `ToolActor`（每工具一个，可池化）；
工具 Actor 由 `Supervisor` 监督；模型 IO 在协程/阻塞调度器上跑，不占默认线程池。

**故障模型（逐条可注入）**

| 故障 | 注入方式 | 期望行为 |
|---|---|---|
| 客户端中途断开 | `AgentCmd.Cancel` | 关闭上游 TCP、不再写事件、流被取消 |
| 工具超时 | 工具 Actor 抛异常 | 监督策略 `restart().withLimit(3, 1.minutes)`；超限则该轮以错误收尾，**会话不污染** |
| 工具返回脏数据 | 工具返回非法 schema | 在 `SessionActor` 内校验后**丢弃该轮**，不写入事件流 |
| 模型 5xx / 断流 | mock LLM 返回 500 | 重试 N 次（`withTimers`）后明确失败，不静默半截回复 |
| 进程被 `kill -9` | 外部脚本 | 重启后从 `journal_v2` 恢复：已落盘的 token 保留，未完成轮次标记为"可重试" |

**可证伪验收（全部先红后绿）**

1. `streamIsCancelledOnClientDisconnect`：发一半断开 → 断言上游 socket 被关闭、流收到 `cancel`、事件流末尾是"未完成轮次"标记；
2. `toolFailureDoesNotCorruptSession`：工具连续失败 3 次 → 断言会话事件流里**没有**该轮的 token，只有一条失败记录；
3. `sessionRecoversAfterKill9`：写入 200 个 token → `kill -9` → 重启 → 断言恢复出的历史 token 数与内容完全一致；
4. `slowClientDoesNotBlockOtherSessions`：一个客户端以 1 token/s 消费 → 断言另一会话的 P50 首 token 延迟 < 200 ms（**背压不跨会话传染**）；
5. `toolCallIsRetriedExactlyOncePerRound`：模型发出两次相同工具调用 → 断言副作用只发生一次（幂等键 = 轮次 + 工具 + 参数哈希）。

**规模与工期**：单进程 + mock LLM（真 TCP SSE），3–4 天；若要多节点跑（模型调用分散到多个 worker）再加 1 天。

**暴露的框架缺口**

- **G-1**：无通用 HTTP 服务端（§2.1）。
- **差距 4.10**：trace 不跨节点 → 多 worker 时无法回答"这一轮经过哪些节点"。
- **差距 4.13**：工具调用若走远程，缺 `AtLeastOnceEnvelope` 幂等语义（验收 5 需要自建去重）。

### E2 — 多租户订单 / 购物车（分片 + 租约 + fencing + 幂等）

**场景与真实约束**

SaaS 形态：N 个租户，每个租户有购物车与订单；订单状态机 `Place → Pay → Ship`，且 `Pay` 后不可 `Cancel`；
下单要扣减库存，**库存不能为负**。真实约束：

1. **同一租户的写必须单写者**（否则库存扣减会超卖）；不同租户并行；
2. **单写者会故障**：持有租约的节点被 `kill -9` 后，另一节点必须接管，**且旧持有者的迟到写必须被拒绝**；
3. **消息可能重复**（重连重发），重复的扣减不能重复生效；
4. **热点租户**：某租户流量是其他租户的百倍，不能把整个系统卡住。

**为什么是 CActor**

- "同租户单写者 + 跨租户并行" = Actor 模型最标准的用法；
- 单写者的**故障接管** = 分片租约 + fencing token（CActor 已有）；
- 重复投递 = 可靠投递（`tellReliable`）的既有语义，但需要用户可见的幂等包装（**缺口 4.13**）。

**组件映射**

| 能力 | CActor 现成件 |
|---|---|
| 按租户路由到唯一实体 | `ClusterSharding`（`modules/cluster/src/membership/sharding.cj:2174`）、`shardOf`（`:78`）、`shardOwner`（`:86`） |
| 单写者租约 | `shardLeaseName`（`:186`）、`leaseForShard`（`:232`）、`withLease`（`:344`）、`withLeaseRetry`（`:360`） |
| 拒绝旧写者 | `fencingToken`（`:242` / `:2343`）、`modules/persistence/src/fencing.cj:159/:227`（`FencedEventStore`） |
| 热点均衡 | `rebalance.cj` 的 `decideRebalance`（纯函数）+ `busiestShards`（`:2376`） |
| 空闲停用 | `withPassivation`（`:334`） |
| 宕机后记住实体 ID | `rememberedEntitiesKey`（`:448`）+ `ShardingSettings.rememberEntities`（`:261`） |
| 虚拟实体（替代手写 sharding） | `Grains`（`modules/cluster/src/membership/grains.cj:370`）、`callAsync`（`:421`） |
| 幂等（**缺口**） | 需新增 `AtLeastOnceEnvelope`（差距 4.13），落地前用 `DurableStateStore` 自建去重表 |
| 崩溃一致性 | `journal_v2`（fsync + 组提交 + `append(expectedSeq)` 幂等追加） |

**消息协议与拓扑**

```
enum CartCmd {
  | AddItem(Sku, Qty, CartId)
  | Reserve(Sku, Qty)          // 扣库存
  | Checkout(...)
  | Compensate(Sku, Qty)       // 失败回滚
}
```
拓扑：3 个 `cluster_node` 进程 → 一个 `ClusterSharding` region（购物车）+ 一个（订单）；
租户→分片 = `shardOf(tenantId)`；库存写者持 `leaseForShard`，每次写携带 `fencingToken`。

**故障模型**

| 故障 | 注入 | 期望行为 |
|---|---|---|
| 持有租约的节点 `kill -9` | `tools/cluster_crash_node.sh` | 租约过期 → 另一节点接管 → **旧持有者的迟到写被 fencing 拒绝**（现有 `lease_contend` 已验证后半段） |
| 网络分区（单向黑洞） | `BlackholeTransport`（`modules/foundation/src/network/blackhole.cj:22`）+ `/cluster/blackhole` | 分区两侧不能同时成为写者；`Cluster.isDownedBySbr()` 正确判脑裂 |
| 消息重复投递 | 客户端重发 100 次 | 副作用只发生 1 次（幂等键 = `entityId + opId`） |
| 热点租户 | 单租户打满 10× 流量 | 其他租户 P99 不被拖垮（`decideRebalance` 生效） |
| 分片再平衡 | 节点增删 | 实体迁移期间不丢消息、不重复扣减（迁移期双写 → 去重） |

**可证伪验收**

1. `stockNeverGoesNegative`：100 个并发下单打同一 SKU 1000 件 → 断言库存终值 == 0 且**从不为负**，成功单数 == 1000；
2. `staleWriterIsRejectedAfterTakeover`：A 持租约 → `kill -9` A → B 接管 → A 恢复后迟到写 → 断言被 fencing 拒绝且数据未变；
3. `duplicateReservationIsIdempotent`：同一 `opId` 重放 100 次 → 断言库存只扣 1 次；
4. `hotTenantDoesNotStarveOthers`：热点租户压满 → 断言冷租户请求 P99 < 50 ms；
5. `rebalanceMovesEntitiesWithoutLoss`：3→4 节点 → 断言迁移前后每个实体的最终状态一致。

**规模与工期**：3 进程 + 真实 TCP，5 天（幂等包装是主要工作量，若等差距 4.13 则可缩到 3 天）。

**暴露的框架缺口**

- **差距 4.13**：无用户可见的 at-least-once / 幂等 API（`ReliableEnvelope` 是框架内部类型）——**这是本示例的最大障碍**；
- **差距 4.4**：分片归属只活内存，节点全灭后重新洗牌（本示例可接受，但需在文档中写明）；
- **差距 4.1**：`Member` 无 roles，无法表达"只有带 `data` 角色的节点托管分片"。

### E3 — 跨节点可靠事件骨干（可靠投递 + 持久订阅 + 端到端流）

**场景与真实约束**

一个内部事件总线：多个生产者节点产生领域事件，多个消费者节点订阅；要求：

1. **不丢**：生产者崩溃时未确认的事件要重发；
2. **不重复生效**：消费者必须能识别重复（至少一次投递 + 幂等消费）；
3. **慢消费者不能拖垮生产者**：背压要跨节点；
4. **消费者离线期间的事件不能丢**（持久订阅 + 重放）；
5. **大消息**（如批量事件）不能撑爆帧。

**为什么是 CActor**

- 可靠投递、重发、累计 ACK、去重、放弃、预算上限**都已实现**（`modules/remote/src/remoting.cj:358` `ReliableEnvelope`、`:2004/:2008` `tellReliable`、`:212` `withLimits`、`:263` `withNodeBudget`）；
- 跨节点端到端流**比 Akka 的 `SourceRef` 更完整**（`modules/cluster/src/streamref/stream_refs.cj:30`、`:55` sourceRef、`:79` sinkRef；
  `stream_ref_protocol.cj:379` `withReliable`、`:385` `reconnectWindow`）；

**组件映射**

| 能力 | 证据 |
|---|---|
| 可靠投递 / 重发 / ACK / 去重 | `remoting.cj:358`、`:2004/:2008`、`:2013` `reliableStats`、`:2069/:2074` 统计 |
| 背压（跨节点） | `stream_ref_protocol.cj:362` `withBufferSize`、`:366` 订阅超时、`:370` 空闲超时 |
| 订阅与发布 | `pubsub.cj:261/:286/:310` |
| 持久订阅（**缺口**） | 需新增 `subscribeDurable(topic, subscriber, fromSeq)`（差距 4.8） |
| 帧长上限 / 压缩（**缺口**） | 差距 4.9：远程帧无压缩、无分片；压缩算法已在 `foundation/src/serialization/enhanced_serializer.cj:94` 但未接入帧路径 |
| 隔离与准入 | `remoting.cj:2021` quarantine、`:2054` 拒绝握手计数 |

**拓扑**

3 个 `cluster_node` 进程：1 个生产者、1 个消费者、1 个"黑洞"节点（制造分区）；
订阅者用 `ClusterReceptionist.findTyped`（`receptionist.cj:276`）解析生产者的类型化引用。

**故障模型**

| 故障 | 注入 | 期望行为 |
|---|---|---|
| 生产者 `kill -9` | 脚本 | 未 ACK 事件在消费者侧重连后重发（**最终不丢**） |
| 消费者离线 | 停进程 | 离线期间事件持久化（需 4.8 的 durable subscriber）→ 重连后从 `fromSeq` 重放 |
| 单向黑洞 | `BlackholeTransport` | 连接进入 quarantine，重试有上限（`giveUpAfter`），不无限重连 |
| 慢消费者 | 消费端限速 | 生产者侧背压（`maxUnacked` 预算），不无限堆内存 |
| 老版本节点 | 混合版本演练 | 能力位协商成功；不支持的 kind **明确失败**而非静默丢弃 |
| 超大消息 | 发 >1MB 消息 | 明确异常（`RemoteFrameTooLargeException`），连接仍可用（**需 4.9**） |

**可证伪验收**

1. `noEventIsLostWhenProducerDies`：生产 1000 条 → `kill -9` → 重启 → 断言 1000 条**最终全部到达**（去重后计数 == 1000）；
2. `duplicateIsDetectableBySeq`：断言每条消息带单调序号，重复序号可被识别（当前**没有**用户可见序号 → 先红后绿）；
3. `slowConsumerDoesNotOOMProducer`：消费者限速 10 msg/s，生产 10k 条 → 断言生产者堆占用有界（`reliableBudgetUsage` 可观测）；
4. `offlineSubscriberReplaysMissed`：消费者停机期间发 50 条 → 重启 → 断言 50 条按序重放（依赖 4.8）；
5. `oversizedFrameFailsClearly`：发 2MB 消息 → 断言**明确异常**且连接后续仍可用。

**规模与工期**：3 进程 + 真 TCP，4 天（持久订阅与帧上限落地后可缩到 2 天）。

**暴露的框架缺口**：**差距 4.8**（持久订阅）、**4.9**（帧长上限/压缩）、**4.13**（幂等 API）。

### E4 — 边缘–云一致性配置面（CRDT + Gossip + 脑裂处理）

**场景与真实约束**

车联网 / IoT / 边缘盒子场景：几百上千个边缘节点 + 少量云节点，共享一份"配置 + 在线状态 + 计数器"数据。
真实约束：

1. **边缘节点经常掉线又回来**（离线优先）；
2. **不能因为网络分区导致配置回退**（不能丢更新）；
3. **分区要能被识别**（脑裂），且要有明确策略（保留多数派 / 保留最老 / 静态 quorum）；
4. **读要快**（边缘侧不能每次都等 quorum），但写方视图可能与读方不一致（需要 `minCap` 缓解）。

**为什么是 CActor**

- CRDT + 增量传播 + 反熵 + 节点移除 pruning **都已有**（`modules/cluster/src/ddata/crdt.cj`、`replicator.cj`，2,180 行）；
- Gossip 成员 + Phi Accrual 故障检测 + 5 种 SBR 脑裂策略 **都已有**
  （`membership.cj:174` `Gossip`、`:289` `Gossip.merge`；`sbr.cj:60` `sbrDecide`）；
- 一致性级别（Local/Majority/All）已有（`replicator.cj:623/:635`）。

**组件映射**

| 能力 | 证据 |
|---|---|
| CRDT 类型 | `crdt.cj:34` GCounter、`:169` PNCounter、`:247` GSet、`:324` ORSet、`:693` LWWRegister |
| Map 系 CRDT（**缺口**） | 差距 4.6：`ORMap`/`LWWMap` = 0 命中——**配置面几乎必需** |
| 增量 + 反熵 + pruning | `replicator.cj`（`:1845` Replicator、`:212` encode、`:274` digest） |
| 读写一致性级别 | `replicator.cj:623` `WriteConsistency`、`:635` `ReadConsistency`、`:2087` `getWith` |
| `minCap`（**缺口**） | 差距 4.6：读方视图不相交时无缓解手段 |
| 成员与故障检测 | `membership.cj:174/:289`、`:1836` `gossipCount`；`detector/detector.cj` |
| 脑裂策略 | `sbr.cj:60` `sbrDecide`（**纯函数，可单测**）；`Cluster.isDownedBySbr()`（`membership.cj:1757`） |
| 故障注入 | `modules/cluster/src/ops/fault_injection.cj:26`、`management_routes.cj:28/:67` |

**拓扑**：1 个云节点 + 3 个边缘节点；用 `ddata_stress`（`modules/examples/src/ddata_stress/main.cj:162/:174` 已校验收敛与计数器总和）做收敛基线。

**故障模型**

| 故障 | 注入 | 期望行为 |
|---|---|---|
| 边缘节点掉线后回归 | 停进程后重启 | 反熵补齐缺失增量，收敛时间有界（ddata_stress 已有 273ms/57ms/264ms/113ms 量级） |
| 网络分区 | `BlackholeTransport` | 两侧各自继续写；合并后**不丢更新**（CRDT 语义） |
| 脑裂 | 分区 + 少数派侧 | `sbrDecide` 按策略判定 → `isDownedBySbr()` 为 true → 少数派侧停止当写入者 |
| 读方视图过期 | 写方 3 节点 / 读方 5 节点 | `ReadMinCap(n)` 语义（**需 4.6**）；否则明确失败而非返回旧值 |
| 节点被移除 | 集群摘除 | Leader 两阶段 pruning 生效，被移除节点的贡献被清理 |

**可证伪验收**

1. `counterConvergesAfterNodeRejoins`：写方离线期间 N 次自增 → 回归 → 断言三节点最终值**一致且等于真实总量**；
2. `orMapMergesPerKeyIndependently`：并发改同一 Map 的不同 key → 断言两个 key 都在（**当前无 `ORMap` → 先红后绿**）；
3. `partitionedMinorityIsDowned`：3 节点分区 → 少数派侧 `isDownedBySbr()` == true；
4. `readMinCapReturnsAfterNReplicas`：1 个不可达 → `ReadMinCap(2)` 成功、`ReadMajority` 明确失败；
5. `pruningRemovesRemovedNodeContribution`：节点移除 → 断言其计数贡献被清理（现有 pruning 已有，需固化为用例）。

**规模与工期**：4 进程，4 天（Map CRDT 落地后可缩到 2 天）。

**暴露的框架缺口**：**差距 4.6**（Map CRDT + minCap）、**4.1/4.3**（roles 与 data-center——边缘/云天然是多拓扑，**这是本示例与 Multi-DC 缺口的交汇点**）。

### E5 — 可恢复长任务工作流引擎（事件溯源 + 快照 + 提醒 + 分片）

**场景与真实约束**

批量推理、数据管道、报表重算、模型微调编排这类**跑几分钟到几小时**的任务。真实约束：

1. **任务必须跨重启存活**：进程重启后任务继续，而不是从头再来；
2. **长任务要能取消**（用户放弃、参数变更）；
3. **多步骤之间可能有等待**（等审批、等外部回调、等定时）；
4. **同一个任务可能被触发多次**（定时 + 手动），不能重复执行副作用；
5. **步骤失败要能重试且有退避**。

**为什么是 CActor**

- 事件溯源 + 快照 = 任务状态机天然持久；
- `persistence/reminders`（单写者）= "等外部回调/等定时"的现成实现；
- `journal_v2`（fsync + 组提交 + 幂等 `append(expectedSeq)`）= 崩溃一致性的现成实现；
- 监督 + 退避重启 = 步骤重试的现成语义；
- 分片 = 大量任务在集群上的分布与再平衡。

**组件映射**

| 能力 | 证据 |
|---|---|
| 事件溯源 | `EventSourcedActor`（`modules/persistence/src/event_sourced_actor.cj`）、`EventAdapter`（`typed/engine.cj:288`） |
| 崩溃一致日志 | `modules/persistence/src/journal_v2.cj`（序号/CRC32/manifest/tags、原子写、fsync、幂等追加） |
| 快照策略 | `snapshotEvery`（`event_sourced_actor.cj:31`）+ `RetentionCriteria.snapshotEvery(n, keep)`（`modules/persistence/src/typed/model.cj`，见 `snapshotEveryNEvents`/`keepNSnapshots` 字段） |
| 等待外部回调 | `modules/persistence/src/reminders/reminders.cj`；`durable_reminder_demo`（三进程 write/recover/verify） |
| 步骤重试与退避 | `TypedSupervisorStrategy.restartWithBackoff(min, max, randomFactor)` |
| 取消 | `KillSwitch`（`streams/src/kill_switch.cj:15`）、`withTimers` |
| 任务分布 | `ClusterSharding`（`sharding.cj:2174`）、`rememberedEntitiesKey`（`:448`） |
| schema 演进（**缺口**） | 差距 4.7：`EventAdapter` 无 `upcast`——**改了事件结构就重放不了** |
| 快照策略表达力（**缺口**） | 差距 4.7：只能按事件数触发，不能按时间/状态大小 |

**拓扑**：1 个"调度器"节点（用 `ClusterReceptionist` 发布任务 id）+ 3 个"执行器"节点（`ClusterSharding` 托管任务实体）。

**故障模型**

| 故障 | 注入 | 期望行为 |
|---|---|---|
| 执行器 `kill -9`（任务跑到一半） | 脚本 | 任务实体迁移到其他节点 → 从事件流恢复 → **继续未完成的步骤**（不是从头再来） |
| 调度器重启 | 脚本 | 任务仍可被查询与取消（状态在持久层，不在调度器内存） |
| 同任务被触发两次 | 手动重复触发 | 幂等键（任务 id + 步骤 id）→ 副作用只发生一次 |
| 步骤超时 | 步骤 Actor 超时 | 退避重试 N 次 → 之后任务标记失败并可人工重跑 |
| 任务取消 | 取消指令 | 上游资源释放（kill switch），事件流写入"已取消"终态 |

**可证伪验收**

1. `taskResumesAfterExecutorKill`：任务执行到第 5/10 步时 `kill -9` → 断言在新节点上**从第 6 步继续**，且已完成步骤**没有重复副作用**；
2. `snapshotKeepsJournalBounded`：写 500 步 → 断言快照次数 ≥ 1 且重启后恢复结果与不重启一致；
3. `duplicateTriggerHasSingleEffect`：同一任务触发两次 → 断言外部副作用计数为 1；
4. `reminderFiresExactlyOnce`：注册提醒 → 断言只触发一次（重复提醒是常见事故）；
5. `upcastMigratesOldEvents`：写 v1 事件 → 用 v2 adapter 恢复 → 断言成功（**当前无 upcast → 先红后绿**）。

**规模与工期**：4 进程，5 天。

**暴露的框架缺口**：**差距 4.7**（upcast、快照策略表达力、Grain 存储）、**4.11**（多节点 TestKit 与虚拟时间——本示例的验收最需要它）。

### 4.2 推荐落地顺序

**先 E1，后 E2，再 E3 / E5，E4 压轴。** 理由：

1. **E1 排第一**：它最贴仓库定位（README 首句就是"AI Agent 的底层运行时"），
   能在**不依赖任何框架缺口**的前提下（只需自建薄 HTTP 门面）交付一个外部用户能感知价值的东西；
   它同时把"流 + 取消 + 监督 + 持久化 + 背压"五件 CActor 的看家本事串成一条链。
2. **E2 排第二**：它是**唯一一个能把分布式内核压到极限**的候选（分片 + 租约 + fencing + 幂等 + 再平衡），
   且直接暴露"幂等 API 缺失"这个最影响落地的缺口（4.13）——**示例先行、缺口后补**是本文的核心主张。
3. **E3 与 E5 并行**：E3 是"面"（广播、扇出、跨节点），E5 是"点"（单任务的长生命周期与恢复）；
   两者共用"可靠投递 + 持久化"的底层，可以共用一批测试基建。
4. **E4 压轴**：它最依赖 Multi-DC / roles 缺口（4.1/4.3），
   **在 `20261117.md` 的 C1（roles + dataCenter）落地后再做**才不返工。

### 4.3 一条纪律

**示例先行于缺口。** 本文的 5 个候选里，E2/E3/E4/E5 各自点名的缺口，
在示例落地时会以"断言失败"的形式**具体地暴露**，而不是继续停留在 `grep = 0 命中` 的抽象层面。

### 6.2 明确不做

1. **不做通用 HTTP 服务端**（进库）——那是另一个量级（连接管理、HTTP/2、TLS 卸载、路由参数）；示例的 HTTP 由 Lou 承载，CActor 库不引入 HTTP 依赖；
2. **不做跨集群数据复制**（Akka CrossClusterReplication）——沿用 `20261117.md` §6.3 的边界；
3. **不做共识层**——单写者 + fencing + 租约是 CActor 的既定取舍（`20261117.md` §6.3 第 2 条）；
4. **不复用已弃用 API**（`CQRSBus` / `ReadModel` / Enhanced 一套）——新示例一律建在 `EventSourcedActor` 之上；
5. **不复活 xstate 的企业级叙事**——`modules/xstate` 的 `features/`、`enterprise/` 仍是占位，本文的 5 个候选**一个都不依赖它**；
6. **不把 `ManagementServer` 当业务 HTTP 服务**——它只服务健康/就绪/指标。

| ID | 缺口 | 影响示例 | 建议 |

| **G-1** | 无通用 HTTP 服务端/客户端封装 | E1 E2 E3 E4 E5（全部） | **已关闭**：示例改用已实现的 Lou Web 框架（§8.1）；CActor 库仍不做 HTTP |

### 8.5 验收中顺带修掉的两处不稳定

**（1）本地 StreamRef 的终止竞态（库缺陷）**

跑 `tools/ci.sh` 时，并行集群套件（`tools/cluster_parallel_soak.sh 2 8`）在**第 2 轮**
稳定失败：`StreamRefReactiveTest` 的本地用例（先 `localPublisherToStreamDslPreservesOrderAndCompletion`，
再次复跑变为 `sinkFromSubscriberFeedsStreamRef`）报
"生产方 … 已终止且没有发出终止信号"。

**根因**：`Completed/Failed` 走普通消息通道、`DEATH`（`TypedTerminated`）走系统通道，后者可能先到。
`sink` 侧（`stream_ref_sink.cj:637`）对**本地与远程**都给了 `finalTerminationSignalDeadline` 宽限期，
而 `consumer` 侧（`stream_ref_consumer.cj:578`）只在 `producer.isRemote()` 时给宽限期——
同一进程内同样存在信号先到的可能，于是本地流被误判为"对端消失"。

**修复**：`consumerOnSignal` 去掉 `st.producer.isRemote() &&` 条件，与 sink 侧保持一致
（默认宽限 1 s；真正的"对端消失"仍会在宽限期后以同一异常失败，语义不变）。

**验证**：`*StreamRef*` 子集串行 3 次全绿（43/43）；并行套件 3 轮全绿（202/202 × 3）。

**（2）分片获取用例的前提失效（测试缺陷）**

修完 (1) 后重跑 CI，并行第 1 轮又出现另一处偶发失败：
`pendingAcquisitionBecomesVisibleAndResolvesWhenMissingRegionStarts`。
**根因不是负载，是用例前提的概率性失效**：该用例要求"只跑区域的那一侧（a）确实托管了至少一个分片"，
但两个节点做 rendezvous 哈希时，`numberOfShards = 8` 全部分给 b 的概率是 2⁻⁸ = **1/256**；
此时 a 没有可获取的分片，`acquiring > 0` 必然不成立。串行连跑 40 次全绿，也印证是低概率而非稳定复现。

**修复**：`modules/tests/src/unit/cluster/sharding_acquisition_test.cj` 把分片数从 8 提到 **64**
（2⁻⁶⁴ ≈ 0），断言逻辑不变（该用例本来就是"全部托管"的收敛断言，分片数不影响语义）。

**验证**：用例串行 3 次全绿；并行套件 4 轮全绿（202/202 × 4，崩溃 0、断言失败 0）。

**（3）示例断言收紧（非缺陷）**

`ex03` 原 `c.check(idemDups >= 0, ...)` 恒真，改为
`waitUntil(... idemSink.snapshot()[1] > 0)` 并输出实际去重条数（实测 50 条），同时去掉一处裸 `sleep`。

## 18. 第十批：ex28 远程 ActorSelection（2026-11-19）

补齐差距 4.1 的最后一块：此前只能对**已持有引用**的远程 Actor 发消息，
`modules/remote` 没有任何按路径寻址能力。Akka 的 `ActorSelection` / protoactor 的按路径投递
在"知道角色类别、不知道具体名字"的场景（worker 池、临时用户、某前缀实体）是基础能力。

### 18.1 框架实现（`modules/remote/src/actor_selection.cj`）

| 能力 | 语义 |
|---|---|
| `SimpleRemoteManager.actorSelection(addr, path)` | 接受 `cactor://host:port/user/<pattern>`、`/user/<pattern>`、裸 pattern；模式不能含 `\|`/换行 |
| `ActorSelection.tell(msg)` | 目标名写成 `$sel:<pattern>` 发一帧，**由对端本地展开**通配并逐个投递；零额外往返、不阻塞调用方 |
| `ActorSelection.resolveNames(timeout)` | 走 `$sys SELECT`，对端把匹配名称排序后一次回包；超时抛 `TypedAskTimeoutException` |
| `ActorSelection.resolveOne(timeout)` | 0 个或多个匹配都抛 `IllegalStateException`（与 Akka 一致） |
| 通配语义 | `*` 任意长度、`?` 单字节；按 UTF-8 字节匹配 |
| 内部入口隔离 | 以 `$` 开头的处理器（`$sys`、ask/回复临时入口、其它选择器回复入口）永远不参与匹配 |

服务端展开放在 `SimpleRemoteReceiver.dispatch`：`$sel:` 前缀先快照匹配到的业务名称，再逐个走
普通分发；匹配为空时计入对端死信（`undeliverableCount`），与普通"找不到 Actor"的语义一致。

### 18.2 新增示例

| 示例 | 规模 | 关键验收 |
|---|---|---|
| `ex28_actor_selection` | 424 行 | `worker-*` 命中 4 个各收 10 条且按序；`worker-?` 只命中单字符后缀（worker-10 不受影响）；resolveNames 字典序；`*` 不返回内部入口；resolveOne 多/零匹配报错；无匹配计入死信；Lou /workers /broadcast /send /stats 一致 |

外部验证（已实跑）：

```bash

curl -s -X POST 'http://127.0.0.1:18173/broadcast?pattern=worker-*&n=3'
curl -s -X POST 'http://127.0.0.1:18173/send?name=counter&msg=curl'
curl -s -o /dev/null -w '%{http_code}' -X POST 'http://127.0.0.1:18173/send?name=worker-*&msg=x'  # 409
```

### 18.3 本轮问题分析与修正

1. **为什么不让调用方先解析再发送**：先 `resolveNames` 再逐条 `tell` 是两次往返且与发送之间
   有竞态（目标可能在中间停止）。把通配展开放到接收端，一次网络帧、由对端按当时注册表决策，
   与 Akka "selection 由接收端解析" 的语义一致。
2. **内部入口必须显式排除**：最初直接拿 `messageHandlers` 全量匹配，`*` 会命中 `$sys` 与
   ask 回复入口——一次广播就能把用户消息投进控制协议。修复为过滤 `$` 前缀，并让 SELECT
   只遍历 `exposed`（业务暴露表）。
3. **resolveOne 的歧义**：只返回第一个匹配会让"本该唯一"的错误静默化；改为 0/多匹配都抛错。
4. **回复通道**：`$sys` 控制消息不带 sender，所以 SELECT 请求显式携带回复地址与临时入口名；
   本地用一次性处理器 + `TypedPromise` 等待，`finally` 注销，避免临时入口泄漏。

### 19.3 本轮问题分析与修正

1. **规则必须区分"本侧是否存活"与"对方是否该 down"**：第一版规则写成"东西区都必须有可达成员"，

   "指定区域必须可用"（单侧条件），这样多数派/少数派才有明确取舍。
2. **测试断言要选能区分内置策略的场景**：5 节点 2|3 分区下 `KeepMajority` 保留西区、
   自定义规则保留东区，结果相反，才能真正证明 provider 被咨询（否则两种规则同结果，测试无判别力）。
3. **配置注入 vs 代码注入**：从配置文件构造 provider 无法表达闭包/常量表，保持"配置只认内置名、

## 20. 第十二批：ex30 分布式配置与 Map 系 CRDT（2026-11-19）

补齐差距 4.6 的 Map 部分（minCap 已在 ex21 完成）：此前只有 `GCounter/PNCounter/GSet/ORSet/LWWRegister`，
分布式配置只能整体塞进一个 `LWWRegister`，并发改不同 key 会互相覆盖。

### 20.1 框架实现

| 类型 | 语义 |
|---|---|
| `ORMap` | 键值对集合（元素编码 `${key.size}:${key}${value}`）的观察-删除 Map；并发改不同 key 独立、同 key 多值 add-wins、删除不被旧副本复活 |
| `LWWMap` | 每键一个 `LWWRegister<String>`，按 (timestamp, node) 决胜；删除写墓碑 `\u{0001}`，合并后删除不回退 |
| `ReplicatedValue` | 新分支 `ORMapValue` / `LWWMapValue`；线编码复用 ORSet 规范编码 |
| `Replicator` | `putInMap` / `removeFromMap` / `removeMapKey` / `mapValues` / `putInLWWMap` / `removeFromLWWMap` / `lwwMapGet` |

**为什么 ORMap 用"键值对集合"而不是"每 key 一个 ORSet"**：一侧删除整个 key 后，该 key 在它那里不存在；
合并时仅凭"对方没有这个 key"无法区分"对方没见过"与"对方删了"（缺 key 的一侧没有版本向量可依），
会把已删除的值复活。第一版按 key 各存一个 ORSet 正是踩了这个坑（测试 `orMapRemoveValueAndKey` 抓到），
改为所有 (key,value) 放进同一个 ORSet 后，删除即删点，版本向量天然表达"我见过并删除了"。

### 20.2 新增示例

| 示例 | 规模 | 关键验收 |
|---|---|---|
| `ex30_distributed_config` | 424 行 | 3 节点收敛；并发写不同 key 都保留；同 key 并发 a/b 都保留；removeMapKey 后 3 节点都消失且不影响其它 key；LWW 更晚时间戳覆盖、墓碑删除生效；Lou /labels /flags /state 一致 |

外部验证（已实跑）：

```bash
./target/release/bin/cactor_examples.ex30_distributed_config serve 18175
curl -s -X POST 'http://127.0.0.1:18175/labels?key=region&value=east'
curl -s -X POST 'http://127.0.0.1:18175/flags?key=rollout&value=on&ts=100'
curl -s http://127.0.0.1:18175/state
curl -s -X DELETE 'http://127.0.0.1:18175/labels?key=region'
```

### 20.3 本轮问题分析与修正

1. **ORMap 删除语义**（见 20.1）：从"每 key 一个 ORSet"改为"一个 ORSet 存全部键值对"。
2. **编码确定性**：ORMap 初版按 key 拼接多个 ORSet，摘要依赖 key 遍历顺序；改为单 ORSet 后
   元素与点全部排序，`digest()` 与写入顺序无关（测试 `mapWireRoundtripAndDigest`）。
3. **测试口径**：不同来源节点写入的"可见值相同"状态，摘要必须不同（点标记不同）；
   测试改为比较 `x.merge(y)` 与 `y.merge(x)` 的摘要，而不是两个独立构造的 Map。
4. **枚举构造器不可按名导入**：示例里 `import ...{ORMapValue}` 编译失败，改为

## 30. 第二十二批：ex41 持久订阅（2026-11-19）

差距 4.8 的 Durable Subscriber：内存 PubSub 在订阅者离线时丢消息。

### 30.1 框架实现

| 部分 | 说明 |
|---|---|
| `DurableTopic(topic, store, retention!)` | 消息按主题序号写 `DurableStateStore`（meta 键存最高序号，消息键 `topic-msg-<hex>-<seq>`） |
| `publish` | 序号单调递增；写消息后同步投递实时订阅者；`retention > 0` 时删除超出窗口的旧消息 |
| `subscribe(name, offsets, handler, fromSeq!)` | 先回放游标之后的历史再接实时；回放与 publish 同锁，避免缺口/重复 |
| 游标 | 单独存 `DurableStateStore`（`topic-offset-<hex>-<hex>`），handler 成功才推进；失败停下，重连重放 |
| `DurableSubscription` | `unsubscribe` 只停实时投递，游标保留 |
| 锁语义 | 订阅回调在主题锁内执行：回调内不要再次 publish/subscribe（文档写明） |

### 30.2 新增示例

| 示例 | 规模 | 关键验收 |
|---|---|---|
| `ex41_durable_subscriber` | 316 行 | 在线 3 条/游标 3；离线后 2 条重连补齐到 5；同存储新实例不重复消费、游标 6 续读；Lou /publish /history /audit /audit/offline /audit/online /stats；SSE 先补历史后结束 |

外部验证（已实跑，端口 18186）：两次 publish → history 两条；SSE 输出 `id/event/data` 两条。

### 30.3 本轮问题分析与修正

1. **实时投递不推进游标**：最初只在回放路径保存偏移，导致离线重连会重复消费在线已收到的消息；改为 `DurableSubscription.mark` 在每次成功回调后写游标。
2. **回放异常传播**：`subscribe` 内回放 handler 抛异常会中止订阅创建；改为捕获后停在失败条目之前并仍注册实时订阅，offset 保持不变。
3. **示例自锁**：`Audit.online` 持自身锁调用 `subscribe`，而回放回调又要拿同一把锁（Mutex 不可重入）→ 死锁；改为在锁外订阅、订阅完成后再登记句柄。
4. **Condition 用法**：`Condition.waitUntil(timeout, cond)` 的参数名是 `timeout:`，改用 `wait(timeout: left)` 配合 deadline。
5. **并发会话干扰**：本轮构建期间另一个会话正在改 runtime 调度器（`ThreadPerActorExecutor`、循环依赖），构建短暂失败；等其稳定后重试即绿，未触碰对方文件。

### 31.3 每个示例的设计要点

#### 31.3.1 ex42_agent_swarm（多 Agent 协作，优先级最高）

**业务**：一个任务从"需求"到"合并"由多个 Agent 接力：planner 拆步骤，worker 执行工具，
reviewer 校验；高风险步骤暂停等人工审批；整个过程可能跨小时、跨节点、跨进程重启。

**架构**：
- 每个任务一个持久化编排 Actor（`DurableStateBehavior`），子 Agent 是类型化子 Actor（监督树）；
- 工具调用经 `AtLeastOnceDelivery` + `IdempotentReceiver`（ex40），重复回调不重复产生副作用；
- 审批等待用持久提醒（`reminders`），超时升级；节点崩溃后从事件流恢复；
- 全链路 trace：入口 span → 每个子 Agent/tool span，经 `BatchSpanExporter` + OTLP/JSON 导出；
- Lou：`POST /tasks`、`POST /tasks/:id/approve`、`GET /tasks/:id`、`GET /tasks/:id/events`（SSE）、
  `GET /traces`（OTLP JSON）。

**自检**：任务执行到一半 kill 进程 → 新进程续跑且工具副作用计数不变；审批只生效一次；
预算耗尽后拒绝继续；SSE 事件顺序与事件流一致；导出的 trace 父子链完整。
LLM 用脚本化假实现（确定性），不依赖外部 API。

**需要补的框架**：trace 在 Actor 消息边界自动接续（目前 ex32 是应用层手工传 `TraceContext`）；
`MetricRegistry` 与运行时/集群指标统一渲染；可选：Grain 化工具执行器 + reminder。

#### 31.3.2 ex43_inference_gateway（多租户推理网关）

**业务**：按租户限流/配额、流式返回 token、上游推理服务故障时快速失败或切备用、按实际用量计费。

**架构**：
- 每租户一个 Grain（配额、令牌桶、累计费用），状态用 `GrainStorage`（ex39）自动读写；
- `ClusterRouter`（LeastLoaded）选择推理节点，断路器包住上游调用，失败退避恢复；
- 流式输出用 StreamRef/SSE；计费事件经 AtLeastOnce + 幂等扣费（ex40）；
- `ClusterMetrics` + 运行时指标统一到 `/metrics`，含租户维度与拒绝原因。

**自检**：租户 A 超过配额返回 429 且不触达上游；上游连续失败触发 Open，半开后恢复；
客户端中断流不泄漏上游资源；同一请求重试只计费一次；`/metrics` 能被 Prometheus 文本解析。

**需要补的框架**：4.10 指标合并为单一渲染入口；4.4 分片协调状态持久化（租户配额在重启/移交后不丢）；
可选：Grain reminder 做配额周期重置。

#### 31.3.3 ex44_agent_memory（Agent 记忆与画像）

**业务**：按用户写入"情节记忆"（对话、偏好、事实），读侧需要时间线、画像摘要与增量订阅；
记忆有 TTL/删除请求，租户之间强隔离；schema 会演进（新增字段/改变单位）。

**架构**：
- 每用户一个事件溯源 Actor（分片），写路径幂等（deliveryId）；
- `Projection` 维护两类读模型：时间线（全量）与画像摘要（聚合），支持 `reset()` 全量重建；
- `DurableTopic` 作为变更流，供下游（推荐、审计）离线补齐；
- `EventAdapter.upcast` 处理 v1/v2/v3 记忆格式；
- Lou：`POST /users/:id/memories`、`GET /users/:id/timeline`、`GET /users/:id/profile`、
  `POST /users/:id/rebuild`、`GET /users/:id/changes`（SSE/游标）。

**自检**：写入 → 读模型一致；全量重建一致；下游离线后补齐；删除/TTL 后不再返回且不影响其他用户；
旧格式事件冷恢复；跨租户不可见。

**需要补的框架**：`DistributedPubSub` 接入 `DurableTopic`（或提供统一门面）；
Grain reminder 做 TTL/保留清理；4.4 分片状态持久化（重建窗口内归属稳定）。

#### 31.3.4 ex45_edge_twin（边缘-云数字孪生）

**业务**：设备在边缘侧持续工作，网络中断时本地可读写；恢复后与云侧收敛，冲突按业务规则解决；
云端运维不加入边缘集群，但要能下发命令、读取状态。

**架构**：
- 云侧每设备一个 Grain（期望状态/影子），边缘侧一个本地 Actor + 本地持久日志；
- 配置/期望状态用 `LWWMap`，能力集合用 `ORMap`，断网期间双向累积，恢复后 CRDT 合并；
- 命令经 `DurableTopic` 保证离线不丢；边缘用 `ClusterClient`（不加入集群）查询/投递云端服务；
- 断网用 `BlackholeTransport` 或直接停远端模拟；Lou 提供设备看板与 SSE。

**自检**：断网期间边缘写 100 条、云端改 5 个配置；恢复后双方收敛到同一视图；
命令离线排队、重连后恰好生效一次（幂等键）；云侧 down 掉一台节点后客户端仍能找到服务；
边缘不加入 gossip 也能按逻辑名访问。

**需要补的框架**：roles/data-center 语义（4.3）用于表达"边缘/云"拓扑与路由偏好；
大消息（固件/批量元数据）分片或压缩（4.9）；分片协调状态持久化（4.4）。

#### 31.3.5 ex46_live_lakehouse（CDC 到实时数仓）

**业务**：业务库的 Outbox 事件进入流式管道，按主题分区写入多个读模型；下游可能离线；
schema 从 v1 演进到 v3；口径变更后需要全量回填；消费延迟要可观测。

**架构**：
- Outbox → `DurableTopic`（按业务主题，retention 可配）→ `Projection` 读模型；
- 管道用 streams 组合（若 GraphDSL 补齐则用 `partitionBy/merge`，否则先线性）；慢消费者背压有界；
- 下游 sink 经 AtLeastOnce + 幂等（ex40）；
- `upcast` 链保证旧事件可重放；`/metrics` 暴露消费位点与滞后。

**自检**：1000 条事件后读模型与源一致；v1/v2 混合日志冷恢复；下游离线 200 条后补齐；
`reset` 全量回填结果一致；慢 sink 触发背压而不是无限堆积；指标滞后随消费下降。

**需要补的框架**：`streams` 的 GraphDSL 组合子（4.8：`broadcast/merge/partitionBy/balance/zip`），
且不破坏现有 Reactive Streams 语义；消费滞后指标进入统一渲染（4.10）。

### 31.4 推荐排期与交付方式

1. **ex42**：先做，验证"AI Agent 编排 + 可观测"这条主线，顺手补 trace 自动传播与指标统一（4.10）。
2. **ex43**：紧接着做，覆盖"多租户 + 流式 + 计费"，并把 4.4 分片状态持久化补到可演示。
3. **ex44**：复用 ex37/ex40/ex41 的积木，把"记忆/画像"做成模板；推动 PubSub 持久化门面（4.8）。

5. **ex46**：等 GraphDSL（4.8）可用后做，作为流编排的验收场景与压测基准。

每个示例统一要求：
- `modules/examples/src/exNN_*`，包名与目录一致，注册进 `modules/examples/cjpm.toml` 与 `tools/ci.sh`；

## 32. 第二十三批：ex42 多 Agent 协作编排（2026-11-20，§31 第 1 项）

§31 首选示例的第一个落地。目标不是再演示 API，而是把"长任务 + 人工审批 + 崩溃恢复 + 可观测"
组合成一个可回归的真实场景。

### 32.1 实现要点

| 部分 | 说明 |
|---|---|
| `TaskAgent` | 每任务一个经典 Actor；状态写 `DurableStateStore`（status/step/budget/approved） |
| 崩溃恢复 | 新进程创建同名 Actor，从存储恢复；running 自动续跑，awaiting 保持等待 |
| 工具幂等 | `ToolExecutor` 以 `effect-<task>-<step>` 为键；重试/恢复只读已存结果，不计新执行 |
| 审批 | `approve` 仅在 awaiting 生效；完成后重复批准只记 `approve-ignored` |
| 预算 | 执行前先检查预算，耗尽即 failed（优先于审批暂停） |
| 事件流 | 每任务一个 `DurableTopic`；SSE 用 fromSeq/limit 回放 + 实时 |
| 追踪 | `SpanRecord`：任务根 span + 步骤 span（parent=根），`toOtlpJson` 输出 |

### 32.2 示例验收

| 场景 | 结果 |
|---|---|
| t1 | 步骤 1 后待审批；批准后完成 3 步；工具 3 次；重复批准不再执行 |
| t2 | 审批点终止系统；新进程恢复 awaiting、不重放工具；批准后完成；effect 共 6 条无重复 |
| t3 | maxEffects=1：执行 1 步后 failed，预算计数 1 |
| trace | t1 共 4 个 span：1 根 + 3 步，同 traceId，步骤带 parent |
| Lou | 创建/审批/状态/SSE 7 条事件/OTLP/effects 全部一致 |

外部验证（已实跑，端口 18187）：创建 → awaiting(step=1) → approve → completed(step=3)；
SSE 输出 started/step-done/awaiting/approved/...；`/traces` 返回 OTLP resourceSpans。

### 32.3 本轮问题分析与修正

1. **HTTP 绑定到已终止的系统**：崩溃恢复测试先 shutdown 原 system，而 Lou 仍指向旧 Env，
   导致 `POST /tasks` 内部错误。改为恢复成功后用新 Env 启动 Lou；HTTP 只面向存活进程。
2. **预算与审批的顺序**：最初预算检查在审批之后，maxEffects=1 时会先停在审批点而不是失败；
   改为"预算 → 审批 → 执行"。
3. **作用域**：`revived` 在 try 内声明却在 finally 使用；取消该 try/finally，改为顺序执行并显式 shutdown。
4. **状态读取对象**：t4 由新 Env 创建，断言仍读旧 Env 的状态；统一改为读 revived。

### 32.4 与差距 4.10 的关系

本例用现有原语手工接续 trace（ex32 的方式），验证了"根 span + 步骤 span + OTLP 导出"可行；
但**框架级自动传播**（Actor 消息边界自动续 trace）仍未做，作为 4.10 的后续项保留。

### 33.2 示例验收

|---|---|
| 配额 | t1 前两次成功，第三次 429，上游调用数保持 2 |
| 故障 | a 故障时转移到 b；连续失败后 a 断路器 open |
| 计费 | 4 次成功计费 4 次；发送两次不重复扣费 |

外部验证（已实跑，端口 18188）：正常推理、a 故障后 by-b、metrics、SSE 逐 token 均符合预期。

### 33.3 本轮问题分析与修正

1. **断路器计数为 0**：第一版把"应答内容 error"的判断放在 `breaker.execute` 之外，断路器看到的是
   "调用成功"，所以两次失败后仍是 closed。把校验移进 execute 内部后正常打开。
2. **ActorRef 暴露**：`exposeActor` 需要 `ActorRef` 而不是 Actor 实例；上游 Actor 改由共享

3. **token 分隔符**：token 文案里含 `-`，用 `:`/`-` 拆分会把 `tok-1` 拆碎；改为 `|` 与空格分隔。
4. **并发会话干扰**：构建期间另一会话在改 runtime（context/budget/prometheus），出现链接期
   undefined symbol；等其构建完成后重试即绿，未触碰对方文件。

## 35. 第二十六批：ex45 边缘-云数字孪生（2026-11-20，§31 第 4 项）

### 35.1 实现要点

| 部分 | 说明 |
|---|---|

### 35.2 示例验收

| 场景 | 结果 |
|---|---|
| 在线 | color=red/firmware=v1 双向可见 |
| 断网 | 边缘 3 条写入缓冲；云端删 color（更新墓碑），双方各自独立 |

### 35.3 本轮问题分析与修正

1. **LWW 时间戳不能各自从 1 计数**：边缘与云各自 `clock++` 时，云端的"离线删除墓碑"可能只比
   边缘旧值大 1，重连后顺序依赖不确定。改为墙钟毫秒 + 同副本严格递增，跨副本可比。
2. **不能重放值来做同步**：`LWWRegister.set` 保证同副本有序（旧时间戳也会被抬到当前+1），
   直接重放离线写会覆盖掉更新的墓碑。改为合并整份 CRDT。
3. **字段/方法同名**：`private var online` 与 `func online()` 冲突，字段改 `connected`。
4. **收敛断言要覆盖墓碑**：只测"值相同"不足以发现复活问题，专门断言 deleted key 在两侧都为 None。

### 35.4 与 §31 前置条件的差距

本例在同进程模拟两副本；真实边缘部署还需要：

1. **match 分支要单表达式**：`case Some(ev) => { a; b; () }` 被解析成 lambda；改为 `if (let Some(ev) <- ...) { ... }`。

## 44. 第三十五批：修复复用缓冲与分片超限（2026-11-21/22）

这一批不是新功能，而是把并行会话落地的 B2/B3/F5 线协议特性修到真实可用，并把门禁拉回全绿。

### 44.1 根因一：`toArray()` 返回共享视图

- 新序列化器为降分配引入线程本地 `ReusableByteBuffer`，但 `toArray()` 写成 `data.slice(0, size)`；
  仓颉的 `Array.slice` 返回**共享底层存储**的视图，下一次同线程序列化原地清空重写，
  调用方已拿到的帧被悄悄覆盖。
- 现场证据：测试 `networkFrame` 中 `full` 的首 12 字节在第二次序列化后从
  `[0,0,0,4,'s','i','n','k',...]` 变成 `[0,0,0,13,'S','t','r',...]`。
- 影响面：所有"序列化后暂存再发送"的路径（replicator 报文、远程帧、可靠通道）。
  表现为 ddata 空闲反熵退化成发全量、线上读到错位长度。
- 修复：`toArray()` 显式拷贝（`Array<UInt8>(size)` + 逐字节）。

### 44.2 根因二：重组/解压后的逻辑消息被当成超限帧

- `processFrame` 先解压再比较 `maxInboundFrame`，`onChunk` 重组后又递归进入同一检查；
  分片的意义就是让逻辑消息超过单帧上限，结果刚拼好就被判超限并回 `GoAway(FrameTooLarge)`。
- 修复：上限只约束**收到的原始帧**（`allowChunks = true` 时）；解压炸弹仍由
  `MAX_DECOMPRESSED_FRAME` 兜住。

### 44.3 测试修正

- `shortTypeIdsAreNegotiatedAndLegacyStillGetsFullNames` 期望旧格式类型名长度 14、
  切片 `[4..18]`；实际 v1.2.x 线格式是"类型名 UTF-8 字节数"（13）。按实际字节数断言。
- `protocol_f5_test.cj` 的 LCG 乘法补 `@OverflowWrapping`（否则整包测试编译失败）。

### 44.4 门禁结果

`tools/ci.sh`：**1020/1020 测试**、并行集群 2 轮各 235 例、ddata 压测 4/4、示例自检到 ex53
全部通过，`CI_EXIT=0`。修复前为 5 失败 + 1 ERROR。

## 50. 第四十一批：GraphDSL 扇出编排（2026-11-22，差距 4.8）

### 50.1 能力与实现

对标 Akka GraphDSL 的最小可用子集，**不改现有 Source/Flow/Sink 组合模型**，只在引擎里加一个一进多出的

- 背压语义：**所有仍打开的出口都 pull 后才向上游要下一个元素**（最慢分支决定节奏）；

| 两个 `headOption` 消费无限源：各取 1 后取消，上游被取消，流结束 | ✓ |

## 52. 第四十三批：GraphDSL 边界问题修复（2026-11-22）

实现 Balance/Zip 后做了一次针对性代码审查，发现并修复三个真实问题：

1. **上游完成时丢缓冲元素**：`FanOutLogic` / `BalanceLogic` 原先在 `onUpstreamFinish` 直接
   `completeStage()`。如果此刻缓冲里还有元素（下游刚取消、需求短暂下降，或元素已到但尚未 push），
   该元素会被静默丢弃。改为 `upstreamDone` 标记：排空缓冲后再结束，剩余出口通过 pull 推动排空。
2. **汇的 async 边界污染后续构建**：`Sink.async()` 在构建时调用 `b.asyncBoundary`，把
   `GraphBuilder.current` 切到新岛。GraphDSL 在循环里连续构建多个汇时，第二个汇会建在新岛，
   但它的入口 Conn 属于 junction 所在的旧岛 → 跨岛连接。修复为每次构建汇前把 `b.current`
   复位到 junction 所在岛。用例 `asyncSinksStayInJunctionIsland`（一个 `seq().async()` + 一个
   普通 `seq()`）验证两份都能拿全。
3. **zip 两侧各自 async 会跨岛**：若左右源都以 async 结尾，两条 Conn 分属不同岛，同一 `ZipLogic`
   会被两个岛并发调用。现在显式拒绝（`IllegalArgumentException`），避免数据竞争；用例
   `zipSupportsAsyncSide` 验证只有一侧 async 时仍正常工作。
