# CActor 性能优化计划（2026-11-01）

> 本文基于 2026-11-01 在 macOS arm64（14 核）上的真实压测与全仓代码分析，
> 对标 protoactor-go（2026-01-18 快照）与 Akka 2.6.21，给出可落地的最小改造优化计划。
> 数据来源：`bg.md`（三方对比 + 100 万 Actor 规模）、`bench/results/20261101-macos-config-matrix.md`（配置矩阵）、
> 本文新增的 `modules/examples/src/mem_profile`（每 Actor 内存归因）。

---

## 1. 结论摘要

### 1.1 性能画像（一句话）

CActor 的**延迟已是三方最优**（空系统 ping-pong 1.0µs、百万 Actor 常驻下 2.0µs，均优于 Akka 与 protoactor-go），
**极限吞吐可追平**（T14 时 125M msg/s ≈ protoactor@14P 的 124.7M），
但**代价是 3–10 倍的 CPU 能耗**、**每 Actor 内存是同行的 5–6 倍**、**扇出只有 Akka 的 1/3**、
**类型化路径每条消息 CPU 是经典路径的 8 倍且随线程数反缩放**。

### 1.2 四个必须解决的问题（按"差距 ÷ 改造成本"排序）

| # | 问题 | 量化差距 | 根因位置 | 最小改造可行性 |
|---|---|---|---|---|
| **A** | **每 Actor 内存过大** | 3371 B vs Akka 521 B / Go 676 B（**5–6 倍**） | 6 个空数组 + 2 个空 HashMap + 4 个空 ArrayList + ActorPath（见 §3.1） | **高**：全部是"懒分配 / 合并字段"，不改语义 |
| **B** | **类型化路径 CPU 是经典路径 8 倍，且加线程变慢** | 4.74M msg/s@T4 → 2.11M@T14；每条 1.1–1.5µs | core 泛型代码里的 `TypedEnvelope<T>` 分配与 `is TypedEnvelope<T>` 匹配（typed_adapter.cj:69,211） | **中**：信封改非泛型 + 类型匹配移到用户包（§3.3） |
| **C** | **扇出只有 Akka 1/3** | 10.6M vs 32.0M msg/s | 单个 runNext 槽 + RunQueue 单点 `head.swap`（actor_cell.cj:1614-1617, 1514-1517） | **中**：槽位散列 + 批量提交（§3.4） |
| **D** | **多线程能耗失控** | T14 时整进程 795% CPU，同吞吐是 protoactor 的 10 倍 | 自旋 50µs + 10µs 一次的跨线程窃取探测 + 10ms 轮询唤醒（actor_cell.cj:1599, 1742, 1763） | **高**：退避 + 探测降频（§3.5） |

### 1.3 不在本次优化范围内

- **分布式栈**（remote 鉴权、persistence fsync、streams 背压）：是 P0 正确性/安全问题，见 `bg.md` §5，不属性能范畴。
- **死代码与重复实现收敛**（约 8.5k 行调度器/邮箱子包、6 套 ask）：属 1.3.0 收敛范围。本计划只依赖"主路径唯一"这一前提，
  完成后收敛工作可直接删除这些子包，不影响本计划任何一项。
- **JVM/Go 运行时差异**：仓颉"泛型实例化需运行时查类型信息"、"原子变量是独立堆对象"是语言层事实，
  只能绕开不能消除；§3.3 的绕法是本计划的核心。

## 2. 测量方法与可复现基线

### 2.1 环境与口径

- 机器：macOS arm64，14 核 / 48GB；压测期间系统负载 load 21–80，双方交替运行取最好值。
- 构建：workspace 根目录 `cjpm build`（-O2）；1M Actor 规模测试需 `cjHeapSize=8GB`。
- CPU 口径：`real_benchmark` 自带的"窗口 CPU"依赖 Linux `/proc/self/stat`，macOS 上静默失效，
  本次改用整进程 user+sys（zsh 内建 `time`；`/usr/bin/time` 因 SIP 剥离 DYLD 路径不可用）。

## 3. 性能问题全景（含根因定位）

### 3.1 A. 每 Actor 内存 3371 B 的构成与归因

一个 `SimpleUserActorRef`（即 Actor Cell）在堆上常驻的对象：

| 常驻对象 | 数量 | 字节 | 小计 | 位置 |
|---|---|---|---|---|
| `CellMailbox` 的 Mutex | 1 | 200 | 200 | actor_cell.cj:164 |
| `CellMailbox` 的 `incomingSize` AtomicInt64 | 1 | 46 | 46 | actor_cell.cj:167 |
| `CellMailbox` 的 6 个空数组（in/dr × msg/sender/senderRef） | 6 | 79 | **474** | actor_cell.cj:169-177 |
| 4 个计数器 AtomicInt64（processed/deadLetter/restart/unhandled） | 4 | 46 | 184 | actor_cell.cj:371-374 |
| `boundedCount` AtomicInt64 | 1 | 46 | 46 | actor_cell.cj:356 |
| `scheduled` / `terminated` AtomicBool | 2 | 47 | 94 | actor_cell.cj:369-370 |
| `sysHead` AtomicOptionReference | 1 | ~70 | ~70 | actor_cell.cj:366 |
| `childMap` HashMap(0) | 1 | 280 | 280 | actor_cell.cj:379 |
| `watching` HashMap(0) | 1 | 280 | 280 | actor_cell.cj:382 |
| `watchers`/`behaviors`/`stashBuffer`/`unstashed` ArrayList(0) | 4 | 96 | 384 | actor_cell.cj:381-385 |
| `actorPath` ActorPath（含 system + path 两个 String） | 1 | 151 | 151 | actor_cell.cj:344 |
| `pathString` String | 1 | 127 | 127 | actor_cell.cj:345 |
| `actorFactory` 闭包 + Actor 实例 | 2 | — | 95 | actor_cell.cj:342-343 |
| Cell 对象自身（~40 个字段） | 1 | — | ~250 | actor_cell.cj:340-437 |
| **guardian 全局表项**：路径 String + ConcurrentHashMap 条目 | 1 | ~150 | 150 | runtime_user_guardian.cj:34,278 |
| **合计** | | | **≈2947**（实测 3371，余量为测试侧引用数组与分配余量） | |

**三个"注释与代码矛盾"的浪费点**（最值得改，因为改动最小、收益最大）：

1. **注释说"缓冲区在第一条消息到达时才分配"，但代码在字段初始化时就分配了 6 个空数组**（每个 79 B）——
   6 个空数组 474 B，而**百万级 Agent 场景里绝大多数 Actor 从不收消息**，这部分是纯浪费。
2. **2 个空 HashMap（560 B）**：注释已写明"容量 0：大多数 Actor 没有子 Actor / 不监视别人"，
   说明设计意图就是懒的，但类型是 `HashMap` 而非 `Option<HashMap>`，**HashMap(0) 仍然分配了 280 B**。
3. **4 个空 ArrayList（384 B）**：同上，`ArrayList<T>(0)` 仍分配 96 B。

**结论**：**约 1418 B（42%）是"还没用到就先分配"的空容器**，改为懒分配即可直接回收；
再合并计数器、惰性构造 `ActorPath`、去掉重复的路径 String，可再回收约 660 B。

### 3.2 A2. 规模操作的两个全局瓶颈

- **所有 Actor（含子 Actor）都登记进 guardian 的全局 `cellsByPath`**（runtime_user_guardian.cj:34, 278-280），
  且注册/注销都串行在同一把 `pathLock` 上。100 万 Actor = 100 万次全局锁 + 100 万条路径 String + 100 万个表项。
  这是"创建速度只有 Go 的 40%"和"停止比 Go 慢 8 倍"的主要原因之一。
- **停止路径**：`finishTerminate` 逐条排空邮箱（actor_cell.cj:1012-1015），100 万 Actor 停止 = 4010 ms。

### 3.3 B. 类型化路径为何是经典路径的 8 倍 CPU

类型化消息在**发送方**和**接收方**各做一次"core 泛型代码以用户类型实例化"的运行时类型查找：

| 操作 | 位置 | 单线程 | 4 线程并发 |
|---|---|---|---|
| 分配 `TypedEnvelope<T>`（core 泛型代码，T 来自用户包） | typed_adapter.cj:69 | 60 ns | **300–330 ns（互相阻塞）** |
| `case e: TypedEnvelope<T>` 匹配（core 泛型代码） | typed_adapter.cj:211 | ~30 ns | **~0.4 µs（互相阻塞）** |
| 分配 `SameBehavior<T>`（已用 `@Frozen` 修好） | typed_actor.cj:362-458 | 17 ns | 22 ns |

这两处是**热路径上 core 包内的泛型实例化**，仓颉编译器不会在使用方的包里为 T 特化，
于是每次都要在运行时查类型信息，且多线程下互相阻塞 → 表现为"线程越多越慢"（4.74M@T4 → 2.11M@T14）。

> 注意：仓库已有的 `@Frozen` 手法（`TypedBehaviors.same<T>()` 等工厂函数）**帮不上忙**——
> `tell` 是经 `TypedActorRef<T>` 接口的虚调用，函数体不会被内联到调用方。

### 3.4 C. 扇出为何只有 Akka 的 1/3

外部线程扇出时，每次 tell 要写两个共享点：

1. **邮箱锁 + incoming 数组**（actor_cell.cj:181,194）：仓颉的 `Mutex` 与原子变量是**独立堆对象**，
   无法像 Go 那样把锁与状态放进同一缓存行 → 每条消息牵涉多���缓存行的跨核传递。
2. **就绪队列单点**：所有目标若落在同一工作线程，其 `runNext` 槽（actor_cell.cj:1609）成为单点竞争，
   `pushRunNext` 每次做一次 `AtomicOptionReference.swap`（actor_cell.cj:1622）。

Akka 的架构免疫第 2 点：每个 Actor 有独立邮箱，ForkJoin 池批量出队，无共享就绪队列。
protoactor-go 也有每 Actor 独立邮箱 + `runnext`，且唤醒的 goroutine 直接进入发送方所在的 P。

### 3.5 D. 多线程能耗为何失控

| 机制 | 位置 | 问题 |
|---|---|---|
| 空闲自旋 50 µs，每轮 `sleep(Duration.Zero)` 让出处理器 | actor_cell.cj:1751-1755 | 14 线程时几乎永远处于"刚自旋完又自旋"的状态 |
| 空闲线程每 10 µs 扫描所有工作线程的 `executed` 计数 | actor_cell.cj:1599, 1742 | 每线程 10 万次/秒的**跨核缓存行读**，14 线程 = 140 万次/秒 |
| 休眠用 `cond.wait(timeout: 10ms)` 轮询 | actor_cell.cj:1763 | 实际不需要轮询：`submit` 已在 `sleeping` 时 `notifyAll`（:1672-1679），10 ms 只是丢失唤醒的安全网 |
| 捐赠扫描固定从 0 号线程开始 | actor_cell.cj:1923-1930 | 低编号线程成为热点 |

T14 时整进程 795% CPU（34 CPU-s 完成与 protoactor 相同的 125M msg/s）即由此而来。

### 3.6 正确性风险（会影响性能优化的可信度，必须先修）

| 问题 | 位置 | 后果 |
|---|---|---|
| **停止与在途消息竞态**：`finishTerminate` 先置 `terminated` 再排空邮箱，生产者在窗口内入队的消息永久滞留（不投递也不计死信） | actor_cell.cj:462 / 981 / 1012-1015 | 消息静默丢失 |
| **hungryCount 记账漂移**：`store` 与 `fetchAdd` 非原子交错 | actor_cell.cj:1632-1637, 1924-1926 | 捐赠机制静默失效 |
| **BlockingCellExecutor 全局单锁 + 16 线程硬上限** | actor_cell.cj:2058-2070 | >16 个阻塞 Actor 即无限饥饿 |

## 4. 优化计划

> 每项都给出：目标 → 改动点（文件:行）→ **最小实现方案** → 风险 → 验收指标。
> 原则：**不改公共 API 语义**；**每一项可独立提交、独立回滚**；**先测量后优化**（每项都有 M0 前置基线）。

### M0（前置）：把回归基线固化进 CI

- 新增 `tools/bench_gate.sh`：跑 `mem_profile` / `scale_latency` / `real_benchmark`，
  与 `bench/results/baseline.json` 比较，超出 ±5% 即失败。
- 理由：§3.3–3.5 的改动都在热路径上，没有自动门禁必然出现"改 A 坏 B"。

### P0（先做）：修正确性，让后续性能数据可信

| 项 | 最小实现 | 验收 |
|---|---|---|
| P0-1 停止竞态 | 把"是否已终止"的判定移到 `mailbox.add` **之后**再决定是否 `trySchedule`：即 `terminated` 改为在排空邮箱**之后**置位；排空与置位之间用现有 `scheduled` CAS 兜底重入 | 新增用例：停止与并发 tell 交错 10 万次，消息要么被处理、要么计入死信，不允许滞留 |
| P0-2 hungryCount 漂移 | `markHungry` 改为 `hungry.compareAndSwap(false, true)` 成功后再 `fetchAdd(1)`；`clearHungry` 同理用 CAS 成功后 `fetchAdd(-1)` | 压测中 `hungryCount` 与实际举手线程数始终一致 |
| P0-3 阻塞池上限 | `BlockingCellExecutor` 线程数改为按 `CACTOR_BLOCKING_THREADS` + 需求动态扩容（最小：默认从 16 提到 64 并在队列等待超阈值时提示） | 64 个阻塞 Actor 并发不饥饿 |

### P1（最大硬差距）：把每 Actor 内存从 3371 B 降到 ~1.35 KB

> 全部是"懒分配 / 合并字段 / 惰性构造"，**不改变任何语义**，是本计划里性价比最高的一组。
> 收益数字来自 §2.3 的逐项实测（每项独立进程、n=20 万）。

| 项 | 目标 | 最小实现 | 风险 | 预期收益 |
|---|---|---|---|---|
| **P1-1 邮箱 6 个数组懒分配** | 空闲 Actor 不持有数组 | `CellMailbox` 的 6 个数组改为 `Option<Array<...>>`，初始 `None`；`add` 首次调用时分配 incoming 三件套；**sender 两件套仅在 `sender.isSome()` 时才分配**（当前实现为"总是分配数组、只是不写值"）；`refill` 首次时分配 dr 三件套 | 低：只在首次使用时分配，逻辑分支增加 | **-474 B** |
| **P1-2 两个 HashMap 懒分配** | 无子 Actor / 不 watch 时不分配 | `childMap` / `watching` 改 `Option<HashMap<...>>`，访问点统一走 `getOrInit` 私有函数 | 低 | **-560 B** |
| **P1-3 四个 ArrayList 懒分配** | 同上 | `watchers`/`behaviors`/`stashBuffer`/`unstashed` 改 `Option<ArrayList<...>>` | 低 | **-384 B** |
| **P1-4 ActorPath 惰性构造** | 不常驻 ActorPath | 只保留 `pathString`；`path` 属性改为按需 `ActorPath("user-system", pathString)` 构造（调用点少且不热） | 低：`path` 返回值每次新建对象，调用方不得长期持有 | **-151 B** |
| **P1-5 四个计数器合并** | 4 个原子 → 1 个 | 合并为一个 `AtomicInt64`，各占 16 位（processed/deadLetter/restart/unhandled），读接口按位提取 | 中：需要覆盖 4 个计数器的现有测试 | **-138 B** |
| **P1-6 scheduled/terminated 合并** | 2 个 AtomicBool → 1 | 合并为一个 `AtomicInt64` 的两个标志位；`scheduled` 的 CAS 改为对标志位做 CAS | 中：CAS 语义需重新验证（与 P2-1 合并做） | **-47 B** |
| **P1-7 子 Actor 不进全局路径表** | 消除全局锁与百万级表项 | `createCell` 仅对**顶层** Actor 登记 `cellsByPath`；`lookup(path)` 改为按路径分段从根遍历（父的 `childMap`）；`liveCellCount` 改为递归统计或另设计数器 | **中高**：`lookup` 是公开 API，需补等价性测试 | **-150 B**，并移除创建/停止路径上的全局锁 |
| **P1-8 去掉重复的名字 String** | 每个 Actor 只留一份路径 | `actorName` 与 `pathString` 重复承载名字；只保留完整路径，`getName()` 按需截取（调用点少） | 低：`getName()` 会分配新 String | **-127 B** |
| 合计 | 3371 B → **~1.34 KB** | | | 进入 Akka 521 B / Go 676 B 的 2–2.6 倍区间 |

> **关于 "<1 KB" 目标**：按上述最小改造能到 ~1.34 KB。要再压到 1 KB 以内需要结构性改动
> （把 Cell 与邮箱对象分离/共享邮箱池、去掉每 Actor 的路径 String、把 watcher/child 结构外置到按需分配的表），
> 超出"最小改造"范围，建议作为 2.0.0 的独立议题；ROADMAP 的 <1 KB 目标应据此调整为 <1.5 KB。

**实施顺序建议**：P1-1 → P1-4 → P1-2 → P1-3（纯懒分配，零风险，先拿到 -1418 B）
→ P1-8 → P1-5 → P1-6（合并字段，需测试）→ P1-7（独立提交，单独验证 lookup 等价性）。

### P2：消息路径 CPU（外部线程 tell 与扇出）

| 项 | 目标 | 最小实现 | 验收 |
|---|---|---|---|
| **P2-1 合并状态字** | 每条 tell 少 1–2 次跨核缓存行转移 | 把 `mailbox.incomingSize`（计数）+ `cell.scheduled`（调度标志）+ `cell.terminated`（终止标志）合并为**一个 `AtomicInt64`**：bit0=scheduled、bit1=terminated、bit2..63=incoming 计数。发送方：一次 CAS（置 scheduled 并读计数）替代现在的 `incomingSize.store` + `scheduled.load` + `scheduled.CAS` 三次操作；消费方排空时一次 `swap(0)` 同时清计数与调度标志 | 外部线程 tell ≤ 190 ns（基线 235 ns）；[6] 吞吐不回退；Dekker 配对逻辑的正确性需新增并发测试 |
| **P2-2 runNext 多槽散列** | 扇出争用分散 | `runNextSlot: AtomicOptionReference` 改为 `runNextSlots: Array<AtomicOptionReference>`（K=8），下标取 `cell.affinity % K`；`takeNext` 按轮转下标取，避免一个槽被 8 个发送方争用 | [2] 扇出 ≥ 15M msg/s（基线 10.65M） |
| **P2-3 邮箱锁临界区再缩小** | 减少持锁时间 | 配合 P1-1：sender 数组只在有 sender 时才分配 → `add` 的持锁段只剩"写消息 + 计数 + 一次 store" | 单线程 tell CPU ≤ 160 ns（基线 178 ns，可比子集） |

### P3：调度与能耗（多线程 CPU 从 795% 降到 <300%）

| 项 | 目标 | 最小实现 | 验收 |
|---|---|---|---|
| **P3-1 空闲指数退避** | 空闲线程不再持续自旋 | 自旋改为：50 µs → 200 µs → 1 ms → 5 ms 逐级退避（每次退避后重置到第一级）；`sleep(Duration.Zero)` 只在第一级使用 | 尾延迟不变（P50 1.0 µs / P99 2 µs） |
| **P3-2 轮询等待改长** | 消除 10 ms 唤醒风暴 | `cond.wait(timeout: 10ms)` → **100 ms**。安全性前提：`submit` 在 `sleeping` 为真时 `notifyAll`（:1672-1679），且 worker 在持锁期间检查队列（:1759-1766），不存在丢失唤醒 | T14 整进程 CPU ≤ 300%；`ping-pong` P99 不超过基线 2 倍 |
| **P3-3 窃取探测降频** | 消除 140 万次/秒跨核读 | 增加一个全局原子计数 `runNextPending`：push runNext 时 +1，取走时 -1；空闲线程仅在计数 > 0 时才扫描各线程的 `executed`；扫描间隔 10 µs → 100 µs | T14 CPU 再降 ≥ 20% |
| **P3-4 捐赠起点轮转** | 消除低编号线程热点 | `donate` 扫描起点按 `affinitySeq` 轮转而非固定从 0 开始 | 负载不均场景吞吐方差下降 |

### P4：类型化路径（当前 8 倍 CPU、加线程反缩放）

> 核心思路：**把热路径上的泛型实例化操作全部移出 core 包**。core 泛型代码里对"用户包类型 T"的任何
> `is`/`as`/分配都要在运行时查类型信息且多线程互斥；只有在**用户包**里编译出来的具体类型匹配才是廉价的（4–10 ns）。

| 项 | 目标 | 最小实现 | 风险 | 验收 |
|---|---|---|---|---|
| **P4-1 信封改非泛型 + 类型匹配移到用户包** | 类型化路径 CPU 降到经典路径 1.3 倍以内 | ① 新增非泛型载体 `class TypedPayloadBox <: Message { let payload: Any }`（非泛型分配 ≈10 ns，无运行时类型查找）；② `ClassicTypedRef<T>.tell` 发送 `TypedPayloadBox(message)`；③ **关键**：在 `typedActorOf<T>`（调用点在用户包）中生成一个"擦除→具体类型"的桥接闭包，其 `match (payload) { case m: T => ... }` 编译在**用户包**内 → 具体类型匹配 4–10 ns；④ adapter 侧 `case e: TypedEnvelope<T>` 改为 `case e: TypedPayloadBox`（非泛型基类检查，不争用），具体类型判定交给 ③ 的桥接闭包 | 中：需要把 `TypedActorRef<T>` 的发送路径与 `TypedActorAdapter<T>` 的接收路径一起改；协议类型若不是 `Message` 子类需保留旧路径（双路径，按类型分派） | 类型化互发 ≥ 30M msg/s（基线 4.74M）；T4 与 T14 吞吐基本一致（消除反缩放）；每条 CPU ≤ 250 ns |
| **P4-2 泛型入口 `@Frozen` 化** | 让桥接闭包在用户包实例化 | 给 `TypedActorSystem.typedActorOf<T>`、`TypedActorRef` 相关入口加 `@Frozen`（参照 `TypedBehaviors` 已有做法，typed_actor.cj:362-458） | 低：仅影响编译期展开，修改实现需重编依赖包（源码构建不受影响） | 与 P4-1 联合验收 |
| **P4-3（长期备选）宏生成具体适配器** | 彻底消除泛型 | 由已有 `@actor` / `@Message` 宏在用户包生成具体的 adapter/sender 类 | 大：需改宏模块与 DSL | 若 P4-1 受阻则启动 |

> 备选方案（若 P4-1 因 API 兼容性受阻）：保留 `TypedEnvelope<T>`，仅把接收侧匹配改为非泛型基类 + `anyPayload(): Any`，
> 由 adapter 在**首次**转换时缓存转换结果（每种载荷类型只转换一次）——牺牲一点内存换取热路径无泛型操作。

### P5：规模操作（创建 / 停止）

| 项 | 目标 | 最小实现 | 验收 |
|---|---|---|---|
| **P5-1 创建去全局锁** | 创建吞吐 246k/s → ≥400k/s | 依赖 P1-7（子 Actor 不进全局表） | 100 万创建 ≤2.5 s（基线 4.06 s） |
| **P5-2 停止批量化** | 停止 4010 ms → ≤1.5 s | `finishTerminate` 排空邮箱时批量丢弃并一次性计数，而不是逐条（当前 :1012-1015） | 100 万停止 ≤1.5 s |
| **P5-3 顶层创建提速** | 顶层 140k/s → 与子 Actor 持平 | 顶层需经 Guardian 登记与 `ActorRef` 包装；P1-7 后顶层仍需登记（语义要求），但可避免重复的路径 String 构造 | 顶层创建 ≥200k/s |

## 6. 风险与取舍

| 风险 | 影响 | 对策 |
|---|---|---|
| P1-7 改变 `lookup(path)` 语义（子 Actor 不在全局表） | 公开 API 行为变化 | 保持 `lookup` 对**全部**路径可用：改为按路径分段遍历；补等价性测试（全局表 vs 遍历结果逐项比对） |
| P1-1~1-6 改变字段布局 | 序列化/反射场景失效（仓颉无反射，风险低） | 字段均为 `private`，外部不可见；`SimpleUserActorRef` 是 public class 但字段私有 |
| P2-1 合并状态字改变 Dekker 配对逻辑 | 可能引入丢失唤醒 | 必须配并发测试：多生产者 + 消费者，断言无丢消息（可用 100 万次随机交错） |
| P3-2 拉长 cond 等待到 100 ms | 极端情况下唤醒延迟变差 | 已验证 `submit` 必 `notifyAll`；若回归失败则回退到 10 ms 并改用"仅在队列非空时等待" |
| P4-1 改动类型化公共路径 | 破坏类型化 API 兼容性 | 双路径并存（按协议是否为 `Message` 子类分派），旧路径标 `@Deprecated` 一个版本后删除 |
| 性能优化与"收敛"（1.3.0）冲突 | 重复劳动 | P1–P5 只依赖"主路径唯一"；收敛删除死代码后本计划不受影响，反之亦然 |
| 仓颉运行时限制（泛型类型查找、原子堆对象） | 某些优化无法根治 | §3.3 的绕法已给出；残余部分反馈仓颉团队（见 20261031 文档 §6 末条） |
