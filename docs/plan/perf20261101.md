## 1. 结论摘要

### 1.1 性能画像（一句话）

CActor 的**延迟已是三方最优**（空系统 ping-pong 1.0µs、百万 Actor 常驻下 2.0µs，均优于 Akka 与 protoactor-go），
**极限吞吐可追平**（T14 时 125M msg/s ≈ protoactor@14P 的 124.7M），
但**代价是 3–10 倍的 CPU 能耗**、**每 Actor 内存是同行的 5–6 倍**、**扇出只有 Akka 的 1/3**、
**类型化路径每条消息 CPU 是经典路径的 8 倍且随线程数反缩放**。

### 1.2 四个必须解决的问题（按"差距 ÷ 改造成本"排序）

| # | 问题 | 量化差距 | 根因位置 | 最小改造可行性 |
|---|---|---|---|---|
| **A** | **每 Actor 内存过大** | 3371 B vs Akka 521 B / Go 676 B（**5–6 倍**） | 6 个空数组 + 2 个空 HashMap + 4 个空 ArrayList + ActorPath（见 §3.1） | **高**：全部是"懒分配 / 合并字段"，不改语义 |
| **B** | **类型化路径 CPU 是经典路径 8 倍，且加线程变慢** | 4.74M msg/s@T4 → 2.11M@T14；每条 1.1–1.5µs | core 泛型代码里的 `TypedEnvelope<T>` 分配与 `is TypedEnvelope<T>` 匹配（typed_adapter.cj:69,211） | **中**：信封改非泛型 + 类型匹配移到用户包（§3.3） |
| **C** | **扇出只有 Akka 1/3** | 10.6M vs 32.0M msg/s | 单个 runNext 槽 + RunQueue 单点 `head.swap`（actor_cell.cj:1614-1617, 1514-1517） | **中**：槽位散列 + 批量提交（§3.4） |
| **D** | **多线程能耗失控** | T14 时整进程 795% CPU，同吞吐是 protoactor 的 10 倍 | 自旋 50µs + 10µs 一次的跨线程窃取探测 + 10ms 轮询唤醒（actor_cell.cj:1599, 1742, 1763） | **高**：退避 + 探测降频（§3.5） |

### 1.3 不在本次优化范围内

- **分布式栈**（remote 鉴权、persistence fsync、streams 背压）：是 P0 正确性/安全问题，见 `bg.md` §5，不属性能范畴。
- **死代码与重复实现收敛**（约 8.5k 行调度器/邮箱子包、6 套 ask）：属 1.3.0 收敛范围。本计划只依赖"主路径唯一"这一前提，
  完成后收敛工作可直接删除这些子包，不影响本计划任何一项。
- **JVM/Go 运行时差异**：仓颉"泛型实例化需运行时查类型信息"、"原子变量是独立堆对象"是语言层事实，
  只能绕开不能消除；§3.3 的绕法是本计划的核心。

### 3.1 A. 每 Actor 内存 3371 B 的构成与归因

**三个"注释与代码矛盾"的浪费点**（最值得改，因为改动最小、收益最大）：

1. **注释说"缓冲区在第一条消息到达时才分配"，但代码在字段初始化时就分配了 6 个空数组**（每个 79 B）——
   6 个空数组 474 B，而**百万级 Agent 场景里绝大多数 Actor 从不收消息**，这部分是纯浪费。
2. **2 个空 HashMap（560 B）**：注释已写明"容量 0：大多数 Actor 没有子 Actor / 不监视别人"，
   说明设计意图就是懒的，但类型是 `HashMap` 而非 `Option<HashMap>`，**HashMap(0) 仍然分配了 280 B**。
3. **4 个空 ArrayList（384 B）**：同上，`ArrayList<T>(0)` 仍分配 96 B。

**结论**：**约 1418 B（42%）是"还没用到就先分配"的空容器**，改为懒分配即可直接回收；
再合并计数器、惰性构造 `ActorPath`、去掉重复的路径 String，可再回收约 660 B。

### 3.2 A2. 规模操作的两个全局瓶颈

- **所有 Actor（含子 Actor）都登记进 guardian 的全局 `cellsByPath`**（runtime_user_guardian.cj:34, 278-280），
  且注册/注销都串行在同一把 `pathLock` 上。100 万 Actor = 100 万次全局锁 + 100 万条路径 String + 100 万个表项。
  这是"创建速度只有 Go 的 40%"和"停止比 Go 慢 8 倍"的主要原因之一。
- **停止路径**：`finishTerminate` 逐条排空邮箱（actor_cell.cj:1012-1015），100 万 Actor 停止 = 4010 ms。

### 3.3 B. 类型化路径为何是经典路径的 8 倍 CPU

类型化消息在**发送方**和**接收方**各做一次"core 泛型代码以用户类型实例化"的运行时类型查找：

| 操作 | 位置 | 单线程 | 4 线程并发 |
|---|---|---|---|
| 分配 `TypedEnvelope<T>`（core 泛型代码，T 来自用户包） | typed_adapter.cj:69 | 60 ns | **300–330 ns（互相阻塞）** |
| `case e: TypedEnvelope<T>` 匹配（core 泛型代码） | typed_adapter.cj:211 | ~30 ns | **~0.4 µs（互相阻塞）** |
| 分配 `SameBehavior<T>`（已用 `@Frozen` 修好） | typed_actor.cj:362-458 | 17 ns | 22 ns |

这两处是**热路径上 core 包内的泛型实例化**，仓颉编译器不会在使用方的包里为 T 特化，
于是每次都要在运行时查类型信息，且多线程下互相阻塞 → 表现为"线程越多越慢"（4.74M@T4 → 2.11M@T14）。

> 注意：仓库已有的 `@Frozen` 手法（`TypedBehaviors.same<T>()` 等工厂函数）**帮不上忙**——
> `tell` 是经 `TypedActorRef<T>` 接口的虚调用，函数体不会被内联到调用方。

### 3.4 C. 扇出为何只有 Akka 的 1/3

外部线程扇出时，每次 tell 要写两个共享点：

1. **邮箱锁 + incoming 数组**（actor_cell.cj:181,194）：仓颉的 `Mutex` 与原子变量是**独立堆对象**，
   无法像 Go 那样把锁与状态放进同一缓存行 → 每条消息牵涉多���缓存行的跨核传递。
2. **就绪队列单点**：所有目标若落在同一工作线程，其 `runNext` 槽（actor_cell.cj:1609）成为单点竞争，
   `pushRunNext` 每次做一次 `AtomicOptionReference.swap`（actor_cell.cj:1622）。

Akka 的架构免疫第 2 点：每个 Actor 有独立邮箱，ForkJoin 池批量出队，无共享就绪队列。
protoactor-go 也有每 Actor 独立邮箱 + `runnext`，且唤醒的 goroutine 直接进入发送方所在的 P。

### 3.5 D. 多线程能耗为何失控

| 机制 | 位置 | 问题 |
|---|---|---|
| 空闲自旋 50 µs，每轮 `sleep(Duration.Zero)` 让出处理器 | actor_cell.cj:1751-1755 | 14 线程时几乎永远处于"刚自旋完又自旋"的状态 |
| 空闲线程每 10 µs 扫描所有工作线程的 `executed` 计数 | actor_cell.cj:1599, 1742 | 每线程 10 万次/秒的**跨核缓存行读**，14 线程 = 140 万次/秒 |
| 休眠用 `cond.wait(timeout: 10ms)` 轮询 | actor_cell.cj:1763 | 实际不需要轮询：`submit` 已在 `sleeping` 时 `notifyAll`（:1672-1679），10 ms 只是丢失唤醒的安全网 |
| 捐赠扫描固定从 0 号线程开始 | actor_cell.cj:1923-1930 | 低编号线程成为热点 |

T14 时整进程 795% CPU（34 CPU-s 完成与 protoactor 相同的 125M msg/s）即由此而来。

> **实施结果（2026-11-02）**：核心思路（把热路径泛型操作移出 core）已落地——
> ① 新增非泛型载体 `TypedPayloadBox`（每次 tell 分配 ≈10ns，无运行时类型查找、无争用）；
> ② `ClassicTypedRef.tell` 改发 `TypedPayloadBox`；③ **关键**：`typedActorOf<T>`（门面，@Frozen）
> 与 `ctx.actorOf<U>`（@Frozen）在**用户包**里生成"Any → Option<T>"桥接闭包（`any as T` 为用户包编译，
> 4–10ns），经 `TypedSpawn.props` 注入适配器，接收侧 `case p: TypedPayloadBox` 非泛型匹配后走桥接；
> ④ 定时器同样改用非泛型载体。旧 `TypedEnvelope<T>` 保留为兼容路径（经 PayloadCarrier 分支处理）。
>
> **实测**：[7] 类型化互发 4.1–4.7M → **5.7–10.6M（+30–125%）**；T14/T4 反缩放比 0.44 → **0.75**
> （泛型类型查找争用已消除，残余反缩放来自每条消息 2 次堆分配：信封本身 + enum 载荷装箱进 Any，
> GC 分配器跨线程争用）。**≥30M 的目标需要消除每消息分配**（信封池化 / 值类型邮箱 / 协议直载），
> 属结构性改造，超出"最小改造"范围，作为 2.0 独立议题。
>
> 备注 1：本计划成文前 7083ff8 已试过"非泛型信封 + core 内 `as T`"并因 core 泛型转换 75–100ns 而放弃；
> 本次的关键差异正是 ③——转换发生在用户包编译的桥接闭包里，而不是 core 泛型代码里。
> 备注 2：顶层路径（facade `typedActorOf` → 具体类 `actorOfVia`，非接口虚调用）的展开效果已由 [7] 基准证实；
> 子 Actor 路径（`ctx.actorOf` 经 `TypedActorContext` 接口调用）的展开未单独测量，即使未展开也只回退到
> core 泛型转换（行为正确，性能不劣于旧实现）。

> 核心思路：**把热路径上的泛型实例化操作全部移出 core 包**。core 泛型代码里对"用户包类型 T"的任何
> `is`/`as`/分配都要在运行时查类型信息且多线程互斥；只有在**用户包**里编译出来的具体类型匹配才是廉价的（4–10 ns）。

| 项 | 目标 | 最小实现 | 风险 | 验收 | 状态 |
|---|---|---|---|---|---|
| **P4-1 信封改非泛型 + 类型匹配移到用户包** | 类型化路径 CPU 降到经典路径 1.3 倍以内 | ① 非泛型载体 `TypedPayloadBox`；② `ClassicTypedRef<T>.tell` 发送之；③ 桥接闭包 `any as T` 由 @Frozen 入口在用户包生成、注入适配器；④ 接收侧非泛型匹配 | 中（已按双路径兼容落地） | [7] ≥30M | ✅ 实现完成（[7] +30–80%，反缩放 0.44→0.75；≥30M 需消除每消息分配，未达） |

#### 7.1.1 类型化路径的两条"捷径"经微基准实测排除

为确认 `≥30M` 是否还有低成本的实现路径，用独立小程序（跨包模拟 core/用户包）实测了每百万次消息传递：

| 写法 | 每 100 万次 | 结论 |
|---|---|---|
| 预建好的 `Message` 引用直接赋值 | 3 ms | 参照系（0 分配） |
| 每次新建 enum → `Message`（值类型装箱） | 20 ms | **enum 协议每次仍产生一次装箱分配** |
| 每次新建 class（引用类型）→ `Message` | 16 ms | 类协议天然不装箱，但类实例本身要分配 |
| `TypedPayloadBox(class)` | 27 ms | 额外信封约 +11 ms/百万 |
| `TypedEnvelope<Volley>`（泛型信封，用户包实例化） | 20–28 ms | 与 `Any` 装箱等价，**没有额外收益** |

由此结论：① 泛型信封在用户包实例化并不比 `Any` 擦除更便宜（两者都要分配），P4-3 宏方案的假设不成立；
② 唯一接近零分配的路径是"协议本身是引用类型且实现 `Message`"，且需要邮箱能直接承载 `Message`
（枚举协议——仓库推荐的"枚举即协议"写法——因值类型语义必然装箱）。
因此 `≥30M` 只能靠**值类型邮箱 / 信封池化**这类运行时改造，属 2.0 议题；本轮不引入任何会改变
类型化公共语义的捷径。

> 同轮附带保留了一处无争议的接收侧改进：适配器把"经典消息 → T"的回退分支从
> core 泛型代码里的 `message as T`（每次运行时查类型信息）改为走已在用户包编译的 `unwrap(message)`
> 桥接闭包，与 P4-1 的机制一致，[7] 实测无回退（9.4–10.6M）。

### 7.2 极致压测：线程扩展性与扇出反缩放诊断（2026-11-03）

用 T1/T4/T14 三档线程（`CACTOR_DISPATCHER_THREADS`）+ 整进程 CPU（zsh `time`）做交叉诊断，
发现一个**基线里就存在、本次优化未消除**的结构性问题：**扇出随线程数强反缩放**。

| 场景 | T1 | T4 | T14 | 结论 |
|---|---|---|---|---|
| [1] 单 Actor 吞吐 | 13.0–24.4M | 13.7–17.1M | 14.0–18.7M | 基本平 |
| [2] 扇出 8×100 | **17.2–25.2M** | 10.4–12.5M | **2.7–4.3M** | **强反缩放（最差项）** |
| [6] 多对 ping-pong | 14.4–15.5M | 59–60M | **149–157M** | 扩展良好 |
| [7] 类型化互发 | 4.6–4.9M | 5.1–6.7M | 3.9M | 轻微反缩放 |

**整进程 CPU（[2] 扇出）**：T4 用户态 7.95s / 墙钟 172ms；T14 用户态 **31.3s** / 墙钟 745ms。
即 T14 把 4 倍的 CPU 花在了更慢的完成上——典型的多线程互踩，不是「算得多」而是「白干得多」。

#### 逐项排除过的假设（都是实测，不是推断）

| 假设 | 实验 | 结果 | 判定 |
|---|---|---|---|
| 同字「计数+调度位」伪共享 | 把 incoming 计数拆成独立原子 | T14 扇出 3.36M → **2.56M** | ❌ 反证：同字一次 RMW 更优，已回退 |
| load+CAS 循环的重试风暴（P2-1 引入） | 改为单次 `fetchOr` 选举 | T14 2.78M → 3.36M (+21%)，且消除重试 | ✅ 保留（真实改进） |
| `trySchedule` 无条件 RMW | 改为「先 load，仅未调度才 `fetchOr`」 | T14 3.36M；T4 持平 | ✅ 保留 |
| 空闲线程 250µs 全量扫描 steal | 加 `runNextPending` 门控；再直接禁用 steal 做 A/B | 门控后 2.84–3.52M；**禁用 steal 后 2.70M（更差）** | ❌ steal 是救援不是负担；门控保留（减少无谓扫描） |
| 空闲线程自旋抢占发送线程 CPU | `SPIN_US=0` vs `50` | 1.83M vs 4.26M，**零自旋更差** | ❌ 排除 |
| 消费侧批大小限制 | `THROUGHPUT` 64/128/256/512 | 10.6–11.6M 不变 | ❌ 已排除 |
| Cell 数过多导致跨线程漂移 | 扇出目标 100 → 8 | T4 反而降到 4.0M，T14 3.6–6.3M（方差极大） | ❌ 不是 Cell 数问题 |
| 一次 `fetchAdd` 合并「计数+选举」 | 合并为单 RMW | **停止彻底失效**（`fetchAdd` 进位污染 bit1 终止位） | ❌ 危险，已回退并留注释警告 |

#### 剩余根因（未能用最小改造消除）

[6] 多对 ping-pong 在 T14 达到 157M（远超基线 125M），说明**调度器与 runNext 本身扩展良好**；
而 [2] 扇出从 T1 的 25M 掉到 T14 的 2.8M，差别在于：

- [6] 是**成对往返**：每个 Cell 只与自己的一对端通信，runNext 的局部性天然成立；
- [2] 是**外部线程随机扇出到 100 个 Cell**：8 个发送线程与 14 个 worker 同时写同一批 Cell 的
  邮箱锁 + 状态字 + runNext 槽，每个 Cell 都是被 22 个线程争用的共享点。

因此真正需要的是**降低每 Cell 的共享写点数量**，而不是调整某个参数：

1. **共享邮箱池**：把「每 Actor 一个 Mutex」改为按工作线程分片的多生产者队列，
   让发送方只写自己分片（消除跨核 mutex 交接）；
2. **就绪队列批量化**：一次入队/出队多个 Cell（Akka ForkJoinPool 的做法），
   把 22 线程 × 100 Cell 的争用摊薄到批次上；
3. **runNext 按发送方散列而非按 Cell 亲和**：让同一发送方的连续 tell 命中同一槽位。

这三项都属于运行时数据结构重构（新增/替换 `CellMailbox`、`CellExecutor` 实现），
超出「最小改造」边界，列为 2.0 议题；本计划明确**不引入**参数级 hack 来掩盖它。

#### 长稳（soak）压测抓到的真实缺陷（已修）

`soak_test 40`（4 生产者持续发送 + Churn 每 10ms 建 50 子/立刻停 + 千分之一故障重启）首轮报**失败**：

```
失败：子 Actor 全部停止（创建 195550，停止 195500）    ← 差 50 个
```

**根因**：本轮新增的"叶子内联停止"（P5-2）在 `terminateIfIdle` 里内联跑完
`initiateTerminate` 后**无条件**清除调度位。若停止过程中 `onCellTerminated` 又投递了系统消息
（Churn 的"建完即停"最容易触发），这条消息就没人收取，Cell 永久停在 `TERMINATING`。

**修复**：释放调度位前先 `hasSystemMessages()`，为真则 `executor.execute(this)` 交回自己的
`run()` 收取，不再直接清位。修复后 **两轮 soak 五项全过**，`创建 == 停止` 精确相等
（173850/173850、172850/172850），吞吐 4.67M msg/s、Churn 4261–4284 个/s。

> 教训：这类"省一次调度"的快速路径必须保持与 `run()` 末尾完全相同的收尾条件，
> 否则省掉的恰是消息的最终归属者。已把该约束写进函数注释。

#### 7.2.1 [7] 类型化路径 6 倍差距的最终定位（2026-11-03 追加）

新增两个**同结构对照组**到 `real_benchmark`，彻底分离"类型化开销"与"协议/批量差异"：

| 场景 | 结构 | T4 实测 |
|---|---|---|
| [6] 经典批量往返 | 经典 Actor + 批量 100 | **55–60M** |
| [9] 经典批量往返（复刻 [8]） | 与 [8] 完全同构（同一批 Start/Ball 消息类、同一批 Actor 数量、同一批量） | **52–55M** |
| [8] 类型化批量往返 | 与 [9] 完全同构，仅 `ActorRef` → `TypedActorRef<T>`、`Actor` → `TypedBehavior<T>` | **9.0–9.9M** |

**结论：同样的消息结构、同样的批量、同样的 Actor 数量，仅换成类型化 API 就慢 5.6–6.1 倍。**
这排除了此前所有"分配/装箱/批量"解释——它们在同一对照下都被抵消了。

用 4 线程独立微基准进一步定位（每线程 300 万次调用）：

| 调用方式 | 4 线程耗时 | 结论 |
|---|---|---|
| `b.on(m)`（`Beh<Int64>` 泛型接口） | **96–104 ms** | 基准 |
| `bn.onn(m)`（`BehN` 非泛型接口，`Int64` 载荷） | **34–37 ms** | 泛型接口本身慢 **2.8 倍** |
| `b.on(m: Any)`（非泛型接口，`Any` 载荷） | **77 ms** | 只收回约 20% |

**最终根因**：`TypedBehavior<T>.onMessage(message: T, ctx)` 是**泛型接口上的虚调用**，`T` 来自用户包。
仓颉对"core 包的泛型接口以用户包类型实例化"的方法调用，每次都要做运行时类型信息查找，
且多线程下互相阻塞——与 §3.3 描述的 `TypedEnvelope<T>` 是同一机制，只是发生在行为对象上而非信封上。
用户每处理一条消息必走一次该调用（`deliver` → `behavior.onMessage`）。

**为什么最小改造无法消除**：`TypedBehavior<T>` 是类型化 API 的核心抽象（Akka Typed 的同类设计），
改成非泛型意味着消息在行为边界退化为 `Any`——① 破坏类型安全与 `match` 穷尽检查；
② 微基准证明只能收回约 20%（96→77ms），仍远达不到 ≥30M；③ 会波及 `TypedActorContext<T>`、
`TypedActorRef<T>` 全部公共 API。真正的解法是**仓颉运行时为泛型接口调用提供特化**
（类似 .NET 的 generic virtualization 或 Rust 的单态化），超出库层能做的范围。

**本轮实际落实的改进**（`applyNext`）：
- 旧实现 `isUnhandled(next) + isSame(next) + start() 内部` 共 **3 次** `specialKindOf(Any)` 调用；
- 合并为 1 次取标记，普通行为（绝大多数）直接更新返回，不再进入 `start()`；
- 全量测试 419 通过、零崩溃；[7] 5.5–9.5M（波动区间内无回退）。

#### 7.2.2 macOS `sample` 剖面复核：接收侧剩余的类型查找点（2026-11-03 追加）

对 T14 的 `real_benchmark` 运行做 3 秒 `sample`，在 `libcangjie-runtime` 里按调用者归并
`TypeInfoManager::GetOrCreateTypeInfo`，定位到 `TypedActorAdapter.receive` 仍有 2 处**每次消息**
的泛型类型查找（与 7.2.1 的行为对象调用是不同位置）：

| 位置 | 原因 | 处置 |
|---|---|---|
| `case a: AdaptedEnvelope<T>` | 对泛型类做 `is` 检查 | 已改为非泛型 `AdaptedEnvelope`（载荷 `Any` + `PayloadCarrier`），接收侧走用户包桥接闭包 |
| `e.anyPayload() as T`（`PayloadCarrier` 分支） | core 泛型代码里的 `as` | 同上，改为 `unwrap(e.anyPayload())` |

改后 `receive` 内不再有泛型类型检查，剖面中剩余的查找全部来自 `deliver → behavior.onMessage`
（7.2.1 的泛型接口虚调用，库层不可消除）。全量 419 通过、集群 flake 隔离复跑通过；[7] T4 7.2–8.1M。

> 说明：这一改进只消除"额外的"查找，`[7] ≥30M` 仍受 7.2.1 的泛型接口调用限制；
> 但它是零风险、与 P4-1 同机制的一致性修复，故保留。

**关于 2M 停止"超线性"的定位（已做实险，结论：不是结构性问题）**：

| 策略（`CACTOR_INLINE_STOP_LIMIT`） | 1M | 2M | 每 Actor |
|---|---|---|---|
| 全并行分发（0） | 1549 ms | 3256 ms | 1.55 / 1.63 µs |

- **内联是三种里最快的**，并行分发（sendSystem 到各子自己的 worker）反而慢 15–20%——

#### 7.2.4 [7] 类型化的最终解法：完全非泛型适配器（2026-11-03）

§7.2.1 判定"`TypedBehavior<T>` 泛型接口虚调用不可消除"后，用更细的微基准把根因再拆一层，
找到了库层可落地的解：

| 实验（600 万次 / 4 线程） | 耗时 |
|---|---|
| core 泛型代码直接调 `b.on(m)` | 776–842 ms |
| core 泛型代码调**用户包编译的**闭包 `(Beh<T>, T) -> Int64` | **53–58 ms** |
| core 泛型代码调**返回 `Option<T>`** 的用户包闭包 | 700–750 ms |
| core **非泛型**类调纯 `Any → Any` 用户包闭包 | **120 ms** |

三条结论，逐层收窄：① 慢的不是"泛型接口"，而是**在 core 里以用户类型实例化**；
② 闭包在用户包编译也不够——**只要签名里出现 T（哪怕只是 `Option<T>` 返回值）**，
core 侧调用就要运行时查类型信息；③ 唯一便宜的形状是**签名完全不含 T 的 `Any → Any`**。

据此把 `TypedActorAdapter<T>` 改为**完全非泛型** `TypedActorAdapter`：

- 行为、消息、上下文在适配器里一律以 `Any` 持有/传递；
- 所有涉及 T 的操作收进 `TypedHooks`（六个 `Any` 签名的闭包：unpack / onMessage / onSignal /
  start / stoppedCallback / describe），由门面 `typedActorOf<T>`（@Frozen）在**用户包**构造；
- 冷路径（建上下文、watchWith 消息、超时消息、stopSelf，每 Actor 一次）走抽象的
  `TypedColdHooks`，泛型实现在 `TypedColdHooksImpl<T>`——适配器只持有抽象类型，自身无泛型方法。

**实测（bench_gate 3 次取最优）**：[7] T4 **4.8M → 29–30M（6 倍）**、T14 **3.2M → 47–70M**；
反缩放比从 0.44 变为 **1.6–2.3（转为随线程正扩展）**；`sample` 剖面里
`TypeInfoManager::GetOrCreateTypeInfo` **归零**（此前 366 次/3 秒）。
全量 419 通过；期间修正了 `Terminated` 信号包装（必须直接传 `TypedTerminated`，
由 `testChildrenWatchAndTerminatedSignal` 抓出）。

> 这同时推翻了 §7.2.1"库层不可消除"的结论：`TypedBehavior<T>` 接口本身不必改，
> 只需让 core 侧**不直接调用**它——把调用搬进用户包闭包、且边界不含 T 即可。

#### 其它压测发现的真实问题（已修）

1. **`trySchedule` 重试风暴**（P2-1 引入的回归）：已改为单次 `fetchOr` 选举 + 读优先，
   扇出 T14 +21%，且代码更简单；
2. **`fetchAdd` 进位污染**：合并「计数+选举」时 `fetchAdd` 会向上进位破坏终止位，
   导致停止失效——已在代码中留注释警告，防止后续再犯；
3. **顶层重名检测失效**（`extractActorName` 返回整条路径）与**创建串行在 guardianLock** 已修；
4. **叶子内联停止的系统消息丢失**（见上）：soak 抓到，已修。

#### 已修复的既有缺陷：Replicator 的 CRDT 并发遍历崩溃（P0 正确性）

`ReplicatorDigestTest.testIdleAntiEntropyOnlySendsDigests` 在**全量并行**跑时约 1/3 的运行会 SIGSEGV
（`ORSet.merge` → `HashMap.contains`，addr 0x8）；单独跑 20 次、整套件跑 20 次均 0 失败。

**根因**：`store.lock` 只保护"从 `store.values` 取出引用"，而 CRDT 值内部的 `HashMap`
（ORSet 的 `entries`/`vv`）在**锁外**被遍历——`merge`（`onLocalUpdate` / `onState`）、
`encode()`（`encodeState`）、`digest()`（`digestsNow` 虽在锁内，但与上述锁外遍历并发）
三者对同一批对象的并发遍历导致崩溃。CRDT 的操作本身不可变（`add`/`remove`/`merge`
都返回新实例），锁的职责是串行化对这些对象的**读取**，而不是保护写。

**修复**（`modules/cluster/src/ddata/replicator.cj`）：
- `onLocalUpdate`：`modify` 与 `merge` 移入 `synchronized(store.lock)`；
- `onState`：`merge` 移入锁内；
- `encodeState`：整个编码过程移入锁内（只做内存拼装，不做 I/O，不会长时间持锁）。

**验证**：修复后连续 **14 次全量测试**，崩溃从"约 1/3 运行"降到 **0 次**（第 6 次曾出现 1 次，
随后 8 连跑未复现；此前 4 连跑中 3 次崩溃）。剩余偶发失败均为集群/分片用例的**断言**
（等待超时类，如 `testEachEntityLivesOnExactlyOneNode`），与本缺陷无关，隔离复跑全部通过。

## 7.3 2026-11-03 追加：每 Actor ≤1.4 KB 达成、CRDT 读路径修复与极致压测复核

### 7.3.1 P1-11：每 Actor 存活堆 1602 → 1300 B（-19%，累计 -61.5%）

两项改动（`modules/runtime/src/guardian/actor_cell.cj`、`runtime_user_guardian.cj`、
`modules/core/src/actor/actor.cj`）：

1. **路径字符串惰性化**：Cell 不再常驻完整路径，只存 `actorName`。子 Actor 的 `name` 与父
   `childMap` 的键是**同一个 String 实例**，因此这一项对子 Actor 是零额外占用；完整路径由
   `fullPath()` 按"父链 + 名字"惰性拼出（顶层用 `guardian.topLevelPathPrefix()`）。
   `hashCode()` 改为创建时混合父链哈希得到的 `pathHashValue`，热路径不再拼路径。
   `pathString` 保留为同名属性（按需拼接）以维持源码兼容；`getName()` 直接返回名字。
2. **创建闭包直达**：新增 `ActorFactory.rawCreator()`（接口默认实现保持语义）与
   `Props.creator()`；Cell 的 `actorFactory` 直接持有用户创建闭包，不再经

**A/B 实测**（交替运行，各 3 次，同一台机器）：

### 7.3.2 P0-4：CRDT 并发遍历 SIGSEGV 消除（5/10 → 0/20）

根因定位与修复（两处，缺一不可）：

1. **`ORSet.merge` 的 `?? HashSet()` 临时空集**：`let theirs = other.entries.get(k) ?? HashSet<String>()`
   在缺键时创建一个临时空集，随后 `theirs.contains(d)` 会访问其内部结构。多线程下这些临时对象
   被并发使用（崩溃固定发生在 `HashMap.contains`，addr 0x8 即对象内部指针为空）。改为显式
   `Option` 分支：缺键直接按"空集合"语义处理，不再分配、也不再触碰临时空集。
2. **读路径不再返回锁内引用**：`Replicator.get(key)` 原来在锁内取出 `store.values` 的引用后直接返回，
   调用方（`setElements` / `counterValue` / `registerValue` / 测试里的 `get(...).encode()`）在锁外
   遍历 CRDT 内部的 HashMap，与 Replicator Actor 线程的 `merge`/`digestsNow` 并发。改为
   "锁内 `encode()` + 锁外 `decode()`"返回独立副本；`setElements`/`counterValue`/`registerValue` 自动变安全。

**A/B 实测**（集群测试包连跑 10–20 次）：

| 版本 | SIGSEGV |
|---|---|
| 基线（P1-11 前） | **5/10** |
| + `get()` 独立副本 | 2/10 |
| + `merge` 去掉 `?? HashSet()` 临时空集 | **0/20** |

修复后：`tools/ci.sh` **全部通过**；全量测试 ERROR 0（剩余失败均为**既有**集群/分片断言 flake，
基线同样 2/3 失败，见 §0 遗留观察）。

补充排查记录：仓颉 `HashMap`/`HashSet` 的并发**只读**（同一对象、不同对象、空集合）经独立微基准
6M+ 次操作均安全；也未检测到同一 Replicator 的 `receive` 被并发执行（Actor 串行性成立）。
因此问题不是"读-读并发"，而是临时空集对象在多线程下被并发触达。

### 7.5.3 P1-13：`Option<Array<T>>` 的 32 字节开销与邮箱瘦身

用独立微基准（跨进程、100 万份）测出仓颉对象布局的几个关键事实：

| 对象/字段 | 每实例 |
|---|---|
| 空 class | 38 B |
| `Option<SomeClass>` 字段 | +8 B |
| `Option<AtomicInt64>` / `Option<HashMap>` 字段 | +8 B |
| `Option<Int64>` 字段 | +16 B |
| `Option<String>` 字段 | +24 B |
| **`Option<Array<T>>` 字段** | **+32 B** |

`CellMailbox` 有 6 个 `Option<Array<...>>`（in/dr × msg/sender/senderRef），合计 **192 B**。
改为普通数组字段 + 共享只读空数组哨兵（`EMPTY_MESSAGES` 等），以 `size == 0` 判定"尚未分配"，
写入前一律先换成新分配的真实数组，因此哨兵永远只读：

- `add`：`inMessages.size == 0` 时按 `INITIAL_CAPACITY` 分配；sender 数组用 `size != slotMsgs.size` 判定；
- `growIncoming`：`inSenders.size > 0` 才同步扩容；
- `poll`：`i < drSenders.size` 才取发送方；
- `refill`：换批后把旧 dr 数组换回 incoming（空数组即回到哨兵语义）。

**实测**：1M 子 Actor 每 Actor 存活堆 **1278–1317 B → 1192–1218 B（约 -90 B，-7%）**；
2M 子 Actor 1387 → **1265 B**。理论上限 144 B 与实测的差额来自 GC region 粒度与对象对齐。

### 7.6.1 消融 1：TTAS 自旋锁（否定，已回退）

**假设**：扇出时 8 个发送方循环 `CAS` 等待同一把锁，每次失败都是 RMW，缓存行被反复踢出；
改成 TTAS（先普通 `load`，看起来空闲才 `CAS`）应能降低锁行弹跳。

**独立微基准**（8 线程 × 100 把锁 × 20 万次/线程，随机分配，模拟扇出）：

| 实现 | 3 轮耗时 | 结论 |
|---|---|---|
| 原实现（循环 CAS） | 177 / 179 / 181 ms | 基准 |
| TTAS（先 load 再 CAS） | 182 / 180 / 186 ms | **无收益，略慢** |

**整机交替 A/B**（同两个可执行文件，T4 各 6 次）：[1] +1.5%、[2] +0.6%、[6] +0.9%、[7] 0%，
均在噪声内；T14 扇出反而略低。**结论**：本场景的争用主要来自临界区本身而非等待者的 RMW，
TTAS 的额外 `load` 不划算。已回退，并在 `SpinLock` 注释里记录该否定结论，避免后人重复尝试。

### 7.6.2 消融 2：捐赠阈值（无稳健收益，已回退）

**假设**：T14 扇出下，空闲 worker 举手后忙线程把队列里的 Cell 捐出去，会让 Cell 在 worker

| 指标 | q=1（等价现行为） | q=8 | q=64（几乎不捐赠） |

| T4 [2] 均值 | 16.68M | 18.04M | 20.33M |
| T14 [1] 均值 | 12.57M | 12.69M | 13.57M |

### 7.7.1 问题与根因

## 7.10 2026-11-05 第四轮：扇出"反缩放"的根因修正——基准线程模型，而非运行时

### 7.10.1 实验：发送方数量扫描

给 `real_benchmark` 加了 `CACTOR_BENCH_SENDERS`（默认仍是 8，保持与三方对比口径一致），
固定 100 个 Actor、每发送方 25 万条，扫描发送方数量：

| 配置 | 总线程数 | [2] 吞吐 |
|---|---|---|
| T14 + 8 发送方 | 22 | 13.2M |
| T14 + 6 发送方 | 20 | 11.4M |
| T14 + 4 发送方 | 18 | 8.3M |
| T14 + 2 发送方 | 16 | 6.0M |
| T14 + 1 发送方 | 15 | 4.6M |
| T4 + 8 发送方 | 12 | 19.5M |
| T4 + 4 发送方 | 8 | 10.5M |
| T4 + 2 发送方 | 6 | 6.9M |

**两个结论**：

1. **吞吐随发送方数量线性增长**（单发送方 4.6M/s ≈ 217ns/tell），说明瓶颈在发送端，
   增加 worker 不会提高该指标；[2] 测的其实是"send 路径"的吞吐。
2. **T14 相对 T4 的下降就是 CPU 超额订阅**：T14 时 8 发送方 + 14 worker + 主线程 = 23 线程
   跑在 14 核上；按 13/23 折算 19.5M × 0.57 ≈ 11.2M，与实测 13.2M 同量级。
   而 worker 驱动的 [6]/[7] 在 T14 仍是正扩展（65M / 31M），证明**运行时消费侧扩展正常**。

因此此前"扇出随线程数强反缩放（需共享邮箱池）"的判断需要修正：**主要部分是基准自身的
线程数超过核数**，不是运行时的结构缺陷。对比 Akka 的 32M vs 本机 T4 的 19.5M 仍有约 1.6 倍差距，
这部分才是真实的每 tell 成本。

### 7.10.2 每 tell 成本的边界（已排除的方向）

在 8 发送方 × 100 Actor 的访问模式下，每个 Cell 的锁、状态字、消息数组分别位于不同缓存行，
发送方每条消息都要跨核取得锁行并写入数组行。逐项实测：

| 尝试 | 结果 |
|---|---|
| TTAS（先 load 再 CAS） | 微基准与整机均无收益（§7.6.1） |
| 锁自旋预算 32 → 256 → 2048 | 3 轮扫描无稳定差异（T4/T14 均值互有胜负） |
| 去掉 enqueue 入口的 TERM 预检（少一次状态字读） | 交替 A/B 均值 [1] 持平、[2] -3%、[6] +1%、[7] 持平 → 无收益，已回退（该读与随后的调度位读同一条缓存行，命中 L1） |
| 链表 MPSC（Vyukov） | 8P1C 微基准 90ns/条（每消息一次节点分配），比现有双缓冲+锁更慢 |
| `CellMailbox` 改 struct 内联 | 大方法每次复制 ~120 B，[1] -65%、[6] -50%，已回退（§7.9.1） |

**结论**：瓶颈是跨核缓存行转移的固有延迟（每 Cell 的锁行 + 数组行），不是锁算法或指令数。
要把 19.5M 提到 Akka 的 32M，需要让发送方**不再写共享的每 Cell 状态**——即按发送线程分片的
邮箱（每 Cell × 每线程一条无锁 lane），内存代价是每 Cell 的 lane 数组；或改变 API 语义做发送端
批量。前者对 100 万 Actor 的场景内存不可接受（每 Cell 多 8 个 lane 引用 ≈ +64 B），后者破坏
`tell` 的即时投递语义。两项都属于 2.0 的接口/结构重设计，且需要专用基准机才能验证是否真的
优于现状。

### 7.10.3 处置

- **不实现**发送端分片邮箱/批量 `tell`：收益未被证明，且与 1M Actor 的内存目标冲突。
- 基准保留 `CACTOR_BENCH_SENDERS` 开关，并在输出里保留发送方数量，避免再次把"线程数超过核数"
  误读为运行时反缩放。
- 后续若要在该指标上对标 Akka，应统一"发送方 + worker ≤ 核数"的口径，或在隔离基准机上运行。

## 7.11 2026-11-05 第五轮：rendezvous 哈希缺陷（真实分配 bug）与最终修复

### 7.11.1 诊断推翻了"故障检测误判"的假设

在 `testGrainsSpreadAndStayPut` 失败时加入诊断输出（仅失败时打印），得到：

```
DIAG hostCounts=[(127.0.0.1:49168, 102), (127.0.0.1:49170, 98)]
DIAG node0 converged=true up=3 members=[...49168=Up, ...49169=Up, ...49170=Up] localEntities=102 ownerCount=3
DIAG node1 converged=true up=3 members=[...49168=Up, ...49169=Up, ...49170=Up] localEntities=0   ownerCount=3
DIAG node2 converged=true up=3 members=[...49168=Up, ...49169=Up, ...49170=Up] localEntities=98  ownerCount=3
```

三个节点的成员视图完全一致（3 个 Up、已收敛），但中间端口 **49169 一个实体都分不到**。
这不是故障检测、不是时序，而是**确定性的哈希缺陷**。

### 7.11.2 根因：共享前缀的字符串 + 直接取 FNV 最大值

`shardOwner` 用 `stableHash("${shard}|${node}")` 做 rendezvous，取分数最大的节点。
测试里节点地址由 OS 顺序分配，形如 `127.0.0.1:4916{8,9,0}`——**前缀完全相同，只有末位不同**。
FNV-1a 对末字节的映射是 `h' = ((h_prefix ^ c) * prime)`，三个候选值互为近平移关系；
直接比较大小会由末位字符系统性地决定胜负，而不是均匀随机。

离线复算（Python 复刻同一 FNV-1a）：

| 地址三元组 | 64 分片归属 |
|---|---|
| `.49168 / .49169 / .49170`（原始） | `.168=32, .170=32, **.169=0**` |
| 同一组 + fmix64 | `.168=23, .169=24, .170=17` |

200 个实体实测 102/0/98，与离线复算逐项一致。

### 7.11.3 修复

`modules/cluster/src/membership/sharding.cj`：

- 新增 `mixHash`（MurmurHash3 fmix64，`@OverflowWrapping`）：对 FNV 结果做雪崩混合；
- `shardOf`：`mixHash(stableHash(id)) % n`，避免短 id/共享前缀造成低位聚集；
- `shardOwner`：用 `mixHash(stableHash("${shard}|${member}"))` 取最大分数；顺带把原来
  绕来绕去的 `match` 守卫改成直白的"取最大、同分按地址字典序"，各节点独立计算结果一致；
- `stableHash` 本身**未改**（公开的跨版本稳定契约，`testStableHashKnownVectors` 继续通过）。

> 兼容性：`shardOf` 的映射变化会改变 remember-entities 的分片键，属于内部布局；
> 集群需要整体升级（本仓库尚未发布该行为的稳定契约）。

### 7.11.4 配套的测试 API 与验证

## 7.12 2026-11-05 第六轮：类型化第三次分配的定位、receive-timeout 惰性化

### 7.12.1 类型化路径其实是"三次分配"（新发现）

计划此前按"两次分配"（`TypedPayloadBox` + enum 装箱）分析。本轮读代码发现 **`TypedBehaviors.same<T>()`
每消息还分配一个 `SameBehavior<T>`**（`typed_actor.cj:398`）：

```cangjie
@Frozen
public static func same<T>(): TypedBehavior<T> {
    SameBehavior<T>()          // ← 每次调用都分配
}
```

而类型化行为的标准写法（包括 [7]/[8] 基准）在每个消息处理末尾都返回 `same()`，所以它是
**每消息第三次堆分配**（既有测量约 17–22ns）。这解释了 [7] 的 30M（≈33ns/消息、4 线程）中
为何分配占比高于预期。

**为什么不能直接改成共享单例**：

| 方案 | 结果 |
|---|---|
| 泛型类静态字段 `static let INSTANCE: SameBehavior<T>` | 仓颉禁止"泛型类的静态成员引用 T"（已编译验证） |
| 函数内静态局部变量 | 仓颉无此语法 |
| 按 T 的 TypeInfo 做全局缓存 | 取 T 的类型信息正是 P4-1 消除掉的昂贵运行时查找；且 `ThreadLocal` 130–330ns |
| 非泛型标记对象 + 强制转换 | `TypedBehavior<T>` 接口被具体化，非泛型对象无法实现它；运行时转换必然失败 |

结论：这是**用户 API 的形态问题**——`same()` 返回一个具体对象才能满足 `TypedBehavior<T>` 的静态类型。
真正的解法是 2.0 的 API 重设计（例如让 `receiveMessage` 的闭包返回一个"保持/停止"的枚举标记，
或提供 `ctx.same()` 复用适配器缓存的实例），而不是运行时能单方面消除的。已如实记录，本轮不改。

### 7.12.2 P1-16：receive-timeout 状态惰性化（每 Actor 约 -32 B）

`receiveTimeoutGeneration` / `receiveTimeoutTimer`，约 32 B），而只有调用过 `setReceiveTimeout`
的 Actor 才会用到。改为：

## 7.13 2026-11-05 第七轮：P1-17 系统队列与启动信号整合（每 Actor 1120 → 1017 B）

### 7.13.1 背景

§7.12 后剩余的内联原子对象里，`sysHead: AtomicOptionReference<SysNode>`（约 55 B）与
`counters`（16 位位域，每消息自增）在 scale 场景都必然分配。其中 `sysHead` 的分配时机
完全由"每个 Actor 创建时都发一条 `SysStarted`"造成——这是一条只为启动服务的系统消息，
却让每个 Actor 的系统队列对象永久驻留。

### 7.13.2 实现（`modules/runtime/src/guardian/actor_cell.cj`）

三项协同改动，全部可用环境变量/行为回归验证：

1. **`START_BIT` 替代 `SysStarted` 消息**：`schedState` 新增 bit4；`createCell` 不再发系统消息，
   改为 `cell.scheduleStart()`（置位 + 调度）；`run()` 进入消息循环前用一次共享读 +
   `fetchAnd` 清位并执行 `startInstance()`。语义等价：`createCell` 在发布引用前调用，
   `run()` 先启动再收消息（由既有测试锁定）。
2. **系统消息队列迁入邮箱并按需分配**：`CellMailbox` 新增 `pushSystem(message): Bool`——
   在邮箱锁内执行（与 `close` 互斥，停止后的消息直接走"死亡后"规则，不会滞留）；
   首次投递时才分配 `AtomicOptionReference<SysNode>` 并置 **`SYS_BIT`（bit3）**发布。
   消费方 `hasSystemMessages()`/`takeSystemMessages()` 先看 SYS_BIT（一次共享读），
   只有置位才解引用队列。锁内推送串行化后，原来的 CAS 重试循环简化为一次 `swap`。
3. **receive-timeout 状态已在前一轮惰性化**（§7.12.2），本轮一并生效。

## 7.14 2026-11-05 第八轮：P1-18 CellMailbox 改 struct 内联（实现→验证→**否决回退**）

### 7.14.1 预期
对象布局微基准显示"struct 字段"比"class 引用字段"省约 16 B 对象头（191 vs 207 B/百万份），
据此把 `CellMailbox` 从 class 改为 struct 内联进 Cell，预期 1017 → ~1000 B。

### 7.14.2 实现
- `class CellMailbox` → `struct CellMailbox`；静态常量（`INITIAL_CAPACITY` 等）挪到包级
  （struct 不支持静态字段）；改字段的方法补 `mut`（`add/close/pushSystem/growIncoming/poll/refill`）；
  Cell 的 `mailbox` 字段 `let` → `var`（let struct 不能调用 mut 方法）。
- 全量编译通过，421/421 测试 ERROR 0，`stop_race` 10/10。

### 7.14.3 验证与否决（交替 A/B，同机同负载窗口）
| 场景 | class（基线） | struct 内联 |
|---|---|---|
| [1] 单 Actor 吞吐 | 12.1–13.5M msg/s | 3.9–5.1M（**-63%**） |
| [6] 多对 ping-pong | 62–65M msg/s | 30–31.5M（**-52%**） |

吞吐损失过半。根因：仓颉 struct 是值类型，`this.mailbox.add(...)` 这类调用把整个
struct（双缓冲 8 字段 + 锁 + 系统栈）按值复制——热路径每条消息一次全量拷贝，远大于
16 B 的对象头节省。测得峰值后即回退为 class，并在源码注释留档"已否决"结论。

### 7.14.4 结论
- **P1-18 正式否决**：Cell/邮箱合并为手工 struct 内联在仓颉当前语义下不可行。
  若仍要省这 ~16 B，唯一路径是 2.0 把邮箱字段手工展开进 Cell（无独立 mailbox 结构），
  但锁/缓冲区直接挂在 Cell 上会显著增加代码复杂度，收益/风险比不划算。
- 项级任务计数不变：32 项实现 + P1-18 否决 + P4-3 不做 → **33 项全部有明确处置（100%）**。
- 内存维持 **1017 B/Actor**（累计 -70%），其余指标无回退（[6] 65M、[1] 11–15M 在窗口内）。

## 7.15 2026-11-05 第九轮：P2-20 `ctx.same()` 零分配（已落地，基准暂不迁移）

### 7.15.1 实现
类型化路径每消息的第三次分配（`TypedBehaviors.same<T>()` 每次返回新 `SameBehavior<T>`，
见 §7.12.1）用"每 Actor 一个缓存实例"消除：

- `TypedActorContext<T>` 新增 `func same(): TypedBehavior<T>`（默认实现转发 `TypedBehaviors.same<T>()`，
  测试桩等自定义上下文零成本可用）；
- `ClassicTypedContext` 新增 `sameBehaviorValue: Option<SameBehavior<T>>` 惰性字段，
  首次调用分配、之后返回同一实例——实例只在 Actor 线程内创建与使用，无并发问题；
  这绕开了"泛型类静态成员不能引用 T"的语言限制（静态不可行 → 每 Actor 实例）；
- `TypedBehaviors.same<T>()` 保持不变且继续 `@Frozen`，现有用户代码**零改动、零回归**；
- 新增回归测试 `testCtxSameIsCachedPerActor`（`behavior_test.cj`）：缓存实例语义
  与 `canonicalize` 归一行为验证。

### 7.15.2 验证
- 全量测试 **422/422（新增 1 例），ERROR 0**；
- 真实基准 [7]（类型化多对互发）用 `ctx.same()` 改写后做了 **7 轮交替 A/B**（同机、跨多个
  负载窗口，每轮 3–5 次采样）：

| 版本 | [7] 稳态中位 | [8] 稳态中位 |
|---|---|---|
| `TypedBehaviors.same<T>()`（基线） | 29.9–31.5M | 28.3–30.8M |
| `ctx.same()`（本实现） | 26.1–29.2M | 26.2–29.4M |

  基准里 `ctx.same()` 路径**未超过**基线（约 -3~-8%）。根因：`receiveMessage` 的
  `(T) -> TypedBehavior<T>` 闭包拿不到 ctx，改用 `receive` 双参闭包后多了一层参数传递；
  且 `@Frozen` 的 `TypedBehaviors.same()` 在调用方包内展开后本身已接近零成本（20ns），
  缓存收益（一次 Option 判空 + 泛型类字段访问）与残余分配的差额在这个量级下被噪声淹没。

### 7.15.3 结论与取舍
- **API 保留**：`ctx.same()` 是 2.0 API 重设计的正确方向（不分配的 same 语义已可用），
  文档注明"每消息热路径推荐 ctx.same()"；
- **基准与内置示例暂不迁移**：在 `receiveMessage` 闭包形态不变的前提下，`TypedBehaviors.same()`
  的 `@Frozen` 展开仍是实测最快路径；迁移需配合闭包形态改造（2.0，见 §7.12.1）。
- 项级任务：33 项处置（32 实现 + P1-18 否决 + P4-3 不做）+ **P2-20 实现为 34 项**；
  类型化"第三次分配"从"无法消除"降级为"提供零分配路径、基准待 2.0 迁移"。
- 其余指标无回退：全量 422 例、`tools/ci.sh` 通过、[7]/[8] 基线（未迁移版）复测 30–32M。
