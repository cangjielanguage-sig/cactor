## 1. 结论与决策总览

### 1.1 结论

1. **CActor 目前没有 HTTP 能力，周边设施大多也是占位实现** [V]。
   - 没有任何 HTTP 代码，也没有引入 stdx。
   - `JsonSerializer` 是假的。
   - 调度器会忽略延时。
   - ask 有 3 套实现，而且要求业务 Actor 自己处理信封。
   - `ActorContext` 只有 `sender()` 一个方法。
   - 库代码中有 472 处 `println`。
   - 公开声明约 3,300 个，创建 ActorSystem 的入口有 8 个以上。

   详见 §2。
2. **仓颉 stdx 自带 HTTP/1.1、HTTP/2、WebSocket、TLS 引擎，可以作为第一阶段的底座** [V]。但它只是协议引擎：没有路由框架；四个超时默认都是无限；日志很吵；在同等 CPU 下的吞吐只有 Akka HTTP 的 0.63–0.77 倍，actix-web 则是 Akka 的 2.6–3.1 倍（§3.5）。所以**必须自研 Native HTTP/1.1 引擎**才能达到性能目标。
3. **最佳方案是“三层借鉴”**：
   - **Ktor 的 API**：`install(Plugin)`、路由树、`call.receive` / `call.respond`、一个请求一个协程，与仓颉的 M:N 协程模型同构。
   - **Akka 的语义**：请求超时返回 503、三阶段优雅停机、各类上限、监督与 ask。
   - **actix-web 的引擎**：接入层反压、零拷贝解析、缓冲水位、流水线、对象池。
4. **融合方式**：HTTP handler 运行在请求协程上，通过**类型化 ask** 调用 Actor（`call.ask(registry, GetUser(id))`，返回类型由消息决定）。Actor 不感知 HTTP。WebSocket 和 SSE 可以选择“每个连接一个 Actor”的写法。HTTP 核心不依赖 ActorSystem，融合层是独立的 `cactor_http_actor` 模块。
5. **CActor 自身的 API 同步重构**：
   - 单一入口 `actorSystem("x") { s => s.install(...) }`。
   - Remote、Cluster、Persistence、Logging、Metrics、HttpServer 统一做成插件。
   - 只保留一套 `Config`。
   - 创建与通信收敛为 `spawn` / `props` / `<<` / `ask`。
   - 提供测试工具 `testActorSystem`。
   - 公开声明从约 3,300 个降到 1,000 个以下，CI 检查 API 快照。
6. **计划**：共 12 个阶段（P0–P11），约 **30–34 人周**。前 5 个阶段（P0–P4，约 12 人周）构成最小可用版本，对应 1.4.0；Native 引擎在 1.5.0 中达到性能验收线；2.0.0 删除旧 API。

### 1.2 决策一览（详细比较见 §4）

| # | 决策点 | 选择 | 主要理由 |
|---|---|---|---|
| D1 | HTTP API 形态 | Ktor 风格，加上 actix 的 `aroundCall` | 与仓颉协程模型同构；插件机制清晰；路由树更快 |
| D2 | HTTP 与 Actor 的融合模式 | 请求协程 + 类型化 ask；WebSocket / SSE 可选择每个连接一个 Actor | 吞吐最高、语义最简单；Actor 不感知 HTTP |
| D3 | HTTP 是否依赖 ActorSystem | 不依赖；融合层单独成模块 `cactor_http_actor` | 吸取 actix-web 4 与 Actor 解耦的经验；可以单独当 Web 框架使用 |
| D4 | HTTP 引擎 | 双引擎：Native（HTTP/1.1，默认）+ stdx（HTTP/2、TLS、过渡期） | stdx 在同等 CPU 下达不到 Akka 水平；h2 和 TLS 先复用 stdx |
| D5 | ask 模型 | 统一的 Completion 内核：经典 Actor 用 `Request<R>`（actix 式），类型化 Actor 用 `replyTo`（Akka Typed 式） | 不需要信封、不查注册表、类型安全 |
| D6 | JSON | 自建 `cactor_json`（基于 stdx `json.stream`）+ `@Codec` 宏 | 流式、无中间对象树；同时生成 DataModel 桥接 |
| D7 | 日志 | foundation 中放门面，后端用 stdx.logger | 核心路径不依赖 stdx；结构化日志 |
| D8 | 配置 | 统一 TOML，支持环境变量和 `-P` 参数覆盖 | 仓颉生态没有 HOCON；与现有配置格式兼容 |
| D9 | 扩展机制 | 通用 `Plugin<Host, Config>` 内核（foundation），ActorSystem、Application、HttpClient 三处共用 | 一套机制、一套写法 |
| D10 | 流抽象 | 先做 `ByteReadChannel` / `ByteWriteChannel`，等 R7 重写 streams 时再提供桥接 | 不阻塞 HTTP 进度 |
| D11 | 默认值 | 三方取舍后的最终表（§7.9） | 安全优先，同时兼顾负载均衡器场景 |
| D12 | 性能目标 | 验收线：同等 CPU 下 ≥ Akka HTTP；挑战线：每核 ≥ actix-web 的 50% | 可度量、可达成 |

## 3. 对标调研摘要

明细见附录 B。

### 3.1 Akka HTTP / Pekko HTTP：功能清单与稳定性语义的来源

- **许可证**：Akka HTTP 自 10.4 起改为 BSL；最后一个 Apache-2.0 版本是 10.2.10。Pekko HTTP 是 Apache-2.0。**只参考 Pekko HTTP 的代码和测试。**
- **能力**：
  - 约 168 个路由指令；拒绝（Rejection）模型；Marshalling 与内容协商。
  - 流式实体，读取受连接级背压控制。
  - Host 连接池客户端；WebSocket、SSE、HTTP/2、TLS；TestKit。
- **稳定性机制（必须继承）**：
  - 请求超时返回 503。
  - 多层超时：idle、request、bind、linger。
  - 解析上限：URI、header 数量、header 值长度、请求体大小。
  - `decode-max-size`，防 zip bomb。
  - HTTP/2 Rapid Reset 防御。
  - 三阶段优雅停机：unbind → drain（新请求返回 503，在途请求处理完后带 `Connection: close` 关闭）→ 到达 deadline 后强制关闭。

### 3.2 Ktor（JetBrains，Apache-2.0，3.6.x）：API 形态的来源

- **运行模型**：一个请求一个协程，handler 是 `suspend` 函数。
- **核心概念**：`embeddedServer(engine) { module() }`、`Application`、`ApplicationCall`。
- **插件**：`install(Plugin) { config }`。插件由 `createApplicationPlugin` 定义，包含配置工厂和 `onCall` / `onCallReceive` / `onCallRespond` 等钩子，可以全局安装，也可以按路由安装。
- **路由**：路由树按匹配质量选择最佳路由，与注册顺序无关。路径支持 `{p}`、`{p?}`、`*`、`{...}`、正则，选择器支持 method、header、accept、param。
- **序列化**：`ContentNegotiation` 根据 Content-Type 选择转换器，配合 `call.receive<T>()` / `call.respond(v)`。
- **客户端**：`HttpClient(engine) { install(...) }`，与服务端共用同一套插件体系（HttpTimeout、HttpRequestRetry …）。
- **测试**：`testApplication {}`，使用内存引擎。
- **不足**：默认值偏宽松，没有请求级超时，也没有连接数上限。这部分用 Akka 的做法补齐。

### 3.3 actix / actix-web（Rust，MIT 或 Apache-2.0）：引擎与融合经验的来源

**版本**：actix-web 4.18.1、actix-http 3.20、actix-server 2.10。actix 0.13.5 已两年没有发版，处于被动维护；actix-web-actors 已废弃，由 actix-ws 取代。

**actix-web 值得照搬的设计**：
- **接入层反压**：独立的 acceptor 按 worker 是否可用来分发连接；某个 worker 达到 `max_connections`（默认 25k）后被跳过，全部满了就暂停 accept；遇到 EMFILE 时退避 500ms；worker 崩溃后自动重建。
- **超时体系**：头部读取超时（5s，返回 408）、keep-alive 5s、断连 1s、TLS 握手 3s、停机 30s；SIGTERM 优雅停机，SIGINT / SIGQUIT 强制停机。
- **协议层上限**：header 最多 96 个，头部缓冲 128KiB，流水线队列 16，写缓冲在 32KiB 时 flush；持续进行请求走私加固（CL 与 TE 冲突、`chunked` 位置、Host 校验）。
- **请求体上限按提取器区分**：JSON 2MB、表单 16kB、字节 256kB。但流式读取没有全局上限，这是一个坑。
- **中间件**：`middleware::from_fn` 环绕式中间件。
- **性能手段**：每个 worker 一个 App，不共享状态；零拷贝缓冲；对象池；Date 头每 500ms 更新一次；静态分派；不需要网络的 `init_service` 测试。

**actix（Actor）的经验**：
- 消息自带回复类型（`Message::Result`），`addr.send(m).await` 直接返回 `M::Result`。
- `SyncArbiter` 用来隔离阻塞型 Actor。

**actix（Actor）的教训**：
- 邮箱容量规则不一致：默认 16，而 `do_send` 和 `notify` 都绕过容量限制。
- 丢弃 future 时消息被静默取消，难以排查。
- `ActorFuture` 很复杂：await 之后再访问状态需要特殊处理，否则会与其他消息交错。
- 监督功能薄弱。
- actix-web 4 最终与 Actor 解耦。

### 3.4 仓颉生态：只依赖 stdx

| 用途 | 选择 | 说明 |
|---|---|---|
| HTTP 引擎（第一阶段）、h2、TLS、WebSocket | `stdx.net.http` / `stdx.net.tls`（1.2.0.1，Apache-2.0）[V] | `ServerBuilder` 的四个超时默认都是 `Duration.Max`；请求体上限默认 2MiB；默认 Distributor 只做精确匹配；每个正常关闭的连接都会打一条 WARN。已知问题：#402（h2 丢 DATA 帧）、#405（客户端不发送 SNI）。客户端只有 `poolSize` 一个连接池参数 |
| JSON | `stdx.encoding.json`（DOM）、`stdx.encoding.json.stream`（`JsonReader` / `JsonWriter` / `JsonSerializable`）[V] | `cactor_json` 的底层 |
| 日志 | `stdx.log`（Logger / LogRecord / Attr）、`stdx.logger`（Text / Json）[V] | 后端 |
| 其他 | `compress.zlib`、`crypto.*`、`encoding.url` / `base64`、`fuzz`、`serialization`（DataModel） | 压缩、JWT、表单、模糊测试 |
| 仓颉标准库 | `std.net`（Native 引擎）、`std.convert.Parsable<T>`（`getAs<T>` 的基础）[V]、`std.deriving`、`std.reflect` | — |

**第三方库只作参考，不作为依赖**：
- Web 框架：cjoy（MulanPSL-2.0）、fountain、spire、tea。
- HTTP 客户端：httpclient4cj（移植自 OkHttp）。
- JSON：cjfast_json（作为性能对照）、CJson。
- 其他：protobuf4cj、rpc4cj、log-cj、toml4cj。

**生态空白**（由 CActor 自己补上）：Prometheus / OTLP 导出、HOCON 解析器。

### 3.5 实测基线（同等 CPU，有效数据）

本机所在容器有 cgroup 配额：`cpu.max = 400000 100000`，即只有 4 核，虽然能看到 32 个逻辑核 [V]。v1–v4 的高并发数据是在超出配额、被大量限流的情况下测得的，**全部作废**。

下面是有效数据：服务端 2 核、oha 压测端 2 核，测量期间限流时间约为 0；场景为 `GET /hello`，keep-alive。

| 并发 | CActor（stdx 引擎） | actix-web 4.18.1 | Akka HTTP 10.2.10 |
|---|---|---|---|
| 1 | 16.0k rps；p50 52.8µs / p99 111µs | **33.5k**；22.5 / 70.8µs | 11.7k；79.4 / 127µs |
| 16 | 27.5k；489µs / 2.3ms | **110.9k**；68µs / 0.81ms | 35.7k；382µs / 1.35ms |
| 64 | 27.8k；2.08 / 14.7ms | **113.4k**；272µs / 11.1ms | 44.3k；1.25 / 7.5ms |

**结论**：
- stdx 引擎在单连接时优于 Akka，但从 16 并发开始不再增长，只有 Akka 的 0.63–0.77 倍。
- actix-web 是 Akka 的 2.6–3.1 倍，可以作为性能上限的参照。
- 256 并发和 Actor ask 场景受到同一容器中其他编译任务的干扰，数据已丢弃，在 P0 中按 §9.1 的规则重测。

## 4. 关键决策与选型

每项决策都列出候选方案、对比和最终选择。

### D1：HTTP API 形态

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. Akka 的 Directive DSL | 功能最全；组合能力强 | 依赖 HList 和 implicit，仓颉没有；指令按顺序尝试，路由多时变慢；Future 链与仓颉协程不同构 | 只作为功能清单 |
| **B. Ktor：插件 + 路由树 + ApplicationCall** | 一个请求一个协程，与仓颉同构；路由树与注册顺序无关；插件有名字、有配置、可以按路由安装；服务端和客户端共用一套 | 仓颉没有带接收者的 lambda，写法上要多一个参数 | ✅ **选择** |
| C. actix 的提取器（handler 参数即提取器） | 类型安全、声明式 | 需要宏或高阶类型推导，仓颉实现成本高 | 只借鉴“按类型配置请求体上限”和 `from_fn` 环绕中间件 |

**结论**：选 B，补上 actix 的 `aroundCall` 环绕钩子。写法统一为显式参数加尾随 lambda：`r.get("/x") { call => ... }`。

### D2：HTTP 与 Actor 的融合模式

| 候选 | 说明 | 吞吐 / 延迟 | 复杂度 | 结论 |
|---|---|---|---|---|
| A. 每个请求一个 Actor（Spray / Akka 经典做法） | 每个请求 spawn 一个 Actor 来处理 | 每个请求都有创建和销毁 Actor 的开销，延迟增加一跳 | 高 | ❌ |
| B. 每个连接一个 Actor | 连接的读写和请求处理都由 Actor 串行完成 | 请求处理被串行化，阻塞操作会卡住整个连接 | 中 | 只用于 WebSocket / SSE（可选） |
| **C. 请求协程 + ask（Ktor / actix-web 4 的做法）** | handler 在请求协程上执行；需要业务状态时 `call.ask(actor, msg)`，协程挂起等待 | 只多一次投递加一次唤醒；无状态的请求完全不经过 Actor | 低 | ✅ **默认** |
| D. 路由写在 Actor 内部（HTTP 即 Actor） | Actor 直接处理 HttpRequest 消息 | HTTP 模型侵入 Actor；难以复用 Ktor 的插件 | 高 | ❌ |

**结论**：默认 C。WebSocket 和 SSE 另外提供 B 风格的 `webSocketActor(props)`，用于需要串行状态的长连接（例如聊天室、订阅）。Actor 一律不感知 HTTP：消息是普通的业务协议，回复由 `Request<R>` 或 `replyTo` 完成。

### D3：HTTP 是否依赖 ActorSystem

| 候选 | 结论 |
|---|---|
| A. HTTP 模块直接依赖 cactor 门面（v2–v4 的做法） | ❌ 只把它当 Web 框架用的人也要引入整个运行时；分层被拉到第 5 层，核心无法独立测试 |
| **B. HTTP 核心（http、http_server、http_client）只依赖 foundation、json 和 stdx；融合层是独立模块 `cactor_http_actor`** | ✅ 与 actix-web 4 的经验一致；核心可以单独做基准测试和模糊测试；依赖方向满足分层脚本 |

### D4：HTTP 引擎

| 候选 | 说明 | 结论 |
|---|---|---|
| A. 只用 stdx | 交付最快；但在同等 CPU 下只有 Akka 的 0.63–0.77 倍，16 并发后不再增长；超时、日志、Distributor 都要绕开 | ❌ 达不到性能目标 |
| B. 只用自研引擎 | 性能可控；但 h2、TLS、WebSocket 都要从零开始写，延迟功能交付 | ❌ |
| **C. 双引擎，共用 `ApplicationEngine` 接口** | 先用 stdx 引擎交付功能（P3、P4）；Native HTTP/1.1 引擎（P5）达到验收线后成为默认；h2 和 TLS 继续用 stdx，直到 Native 引擎支持为止；两种引擎共用同一套测试 | ✅ |

### D5：ask 模型

| 候选 | 说明 | 结论 |
|---|---|---|
| A. 现有的 `AskMessage` 信封 | 业务 Actor 要认识信封；返回值是 `Message`，需要向下转型 | ❌ 废弃 |
| B. 只用 Akka Typed 的 `replyTo` | 类型安全；但经典 Actor 用起来别扭，每个消息都要带一个 replyTo 字段 | 用于类型化 Actor |
| C. 只用 actix 的 `Request<R>` | 消息声明回复类型，`ask` 根据参数推断出返回类型；进程内的消息直接携带 Completion，**回复时不查路径** | 用于经典 Actor 和 HTTP |
| **D. 统一内核（Completion）+ B、C 两种写法** | 一套超时、取消、过载、自旋策略 | ✅ |

### D6–D10：基础设施

| 决策 | 候选 | 选择与理由 |
|---|---|---|
| D6 JSON | stdx DOM / cjfast_json / CJson / 自建 | **自建 `cactor_json`**：基于 stdx `json.stream`，不构造中间对象树；`@Codec` 宏同时生成 `JsonCodec<T>`（快路径）和 stdx `Serializable<T>`（DataModel，供 msgpack 等其他格式使用）；没有第三方依赖。性能以 cjfast_json 为基线 |
| D7 日志 | 沿用 integration 中的 Logger / 直接用 stdx.log / log-cj | **foundation 中放门面**（核心路径只依赖 std），stdx.logger 作为默认后端；integration 现有的 Appender 改为后端实现 |
| D8 配置 | HOCON / YAML / TOML | **TOML**（生态中有现成实现，现有配置也是 TOML），支持环境变量（`${?ENV}`）和 `-P:key=value` 覆盖；不做 HOCON |
| D9 扩展机制 | `ActorSystemExtension` / 每处各写一套 / 通用内核 | **foundation 中的通用 `Plugin<Host, Config>` 内核**，ActorSystem、Application、HttpClient 共用；钩子在安装时展平成数组 |
| D10 流 | 等待 R7 重写 streams / 自带 Channel | **自带 `ByteReadChannel` / `ByteWriteChannel`**（阻塞读写，由协程天然形成背压）；R7 重写时提供桥接 |

### D11：默认值

见 §7.9。原则：安全默认值优先；keep-alive 必须大于常见负载均衡器的空闲超时；一切缓冲和队列都有上限。

### D12：性能目标

| 级别 | 指标 | 依据 |
|---|---|---|
| **验收线** | 同等 CPU 下，各并发档的吞吐 ≥ Akka HTTP 10.2.10，p99 ≤ Akka | 用户的要求；Akka 是功能对标对象 |
| **挑战线** | 每核吞吐 ≥ actix-web 的 50% | actix 是同类框架的上限；仓颉有 GC 加 M:N 调度，100% 不现实 |
| API 开销 | 装上 5 个常用插件、50 条路由后，吞吐 ≥ 裸引擎的 85% | 防止 Ktor 风格的插件链吞掉性能 |
| Actor 层不退化 | 不装插件时，`real_benchmark` 各场景与重构前相差 ±3% 以内 | API 重构不能牺牲已有的性能 |

### 5.4 运行时视图：协程与线程

仓颉是 M:N 模型，所有协程都运行在 `cjProcessorNum` 个载体线程上（默认等于核数）。

```
载体线程 × cjProcessorNum
 ├─ HTTP 接入：accept 协程 × N（Native 引擎：N = 载体数，SO_REUSEPORT [G]；Stdx 引擎：由 stdx 管理）
 ├─ HTTP 连接：每个连接一个协程（读 → 增量解析 → 执行请求 → 写，独占自己的读写缓冲）
 │      └─ 请求在连接协程内执行：aroundCall 链 → 路由树 → handler
 │           └─ call.ask：投递 → 挂起在 Completion 上（不自旋）→ 被回复唤醒，或者超时返回 503
 ├─ Actor 执行：dispatcher worker 协程 × max(核数/4, 1)（affinity 队列 + CellMailbox；空闲时自旋时长可配置）
 ├─ 阻塞型 Actor：blocking dispatcher worker 协程 × K（有界队列）
 ├─ Scheduler：时间轮协程 × 1（请求超时、keep-alive / 头部读取超时、WS 心跳、重试退避、Actor 定时器）
 └─ 后台：异步日志 appender、指标导出、CoordinatedShutdown 执行
```

资源规则（§7.8）：

1. HTTP 协程中的 ask 不自旋。
2. Actor 的 `receive` 中禁止阻塞 IO，需要 IO 时用 `pipeTo`。
3. 阻塞型 Actor 使用 blocking 调度器。
4. 目标邮箱满时，ask 快速失败并返回 503。
5. 在有 CPU 配额的环境中重新验证自旋参数。

### 5.5 请求时序（`GET /api/users/42`，安装了 ContentNegotiation、RequestTimeout 和 CallLogging）

```
客户端          连接协程（Native 引擎）            插件链 / 路由               UserRegistry Actor（dispatcher worker）
  │  GET ──────▶ 读缓冲 + H1Parser（零拷贝切片）
  │             上限检查（URI、头部大小、header 数量）
  │             构造 ApplicationCall（对象池）
  │             ──────────────────────────▶ aroundCall(CallLogging) → onCall(RequestTimeout：在时间轮上登记截止时间)
  │                                          RouteTree 匹配 "/api/users/{id}"（模板记录在 call 上）
  │                                          handler：id = call.parameters.getAs<Int64>("id")
  │                                          call.ask(registry, GetUser(42))
  │                                            ├─ 邮箱已满（有界邮箱）→ ActorOverloaded → 503 + Retry-After
  │                                            └─ tell(GetUser{completion}) ──────────────▶ receive: onGetUser(m)
  │                                               挂起在 Completion 上（不自旋）  ◀── m.reply(Some(user)) 直接完成 Completion
  │                                          call.respond(user) → ContentNegotiation → JsonCodec<User> 写入响应缓冲
  │             H1Writer：状态行和 Date 头预先渲染；超过 32KiB 时 flush
  │ ◀──── 200 ── keep-alive 计时器复位（时间轮）
  （如果 20s 内没有完成：时间轮触发 → 写出 503 → completion.cancel()；之后才到的回复只计入 AskReplyAfterCancel 指标）
```

### 5.6 生命周期与停机（复用现有的 CoordinatedShutdown，并增加阶段超时）

| 阶段（现有 / 新增） | 超时 | HTTP 服务端 | HTTP 客户端 | Actor 与插件 |
|---|---|---|---|---|
| `before-service-unbind` | 5s | `/ready` 改为返回 503，让负载均衡器摘掉流量；触发 `ApplicationStopping` | — | 插件的 `onShutdown` 钩子 |
| `service-unbind` | 5s | 停止 accept，立即关闭空闲的 keep-alive 连接 | — | Remote 停止接收新连接 |
| `service-requests-done`（新增） | 停机期限（默认 30s） | 等待在途请求完成：在途请求完成后带 `Connection: close` 关闭连接；新到的请求返回 503；到期后强制关闭 | — | — |
| `service-stop` | 5s | 引擎释放资源，触发 `ApplicationStopped` | 关闭连接池，取消挂起的请求 | Remote、Persistence 刷盘并关闭 |
| `actor-system-terminate` | 10s | — | — | 按监督树停止所有 Actor |
| `system-terminate` | 3s | — | — | 日志刷盘，导出最后一次指标 |

信号：SIGTERM 触发上述完整流程；SIGINT 和 SIGQUIT 跳过等待，直接强制停机（与 actix 相同）。

### 6.2 Actor 的定义与通信

```cangjie
// 消息协议：Request<R> 声明回复类型（actix 式）；@Message 生成 messageType 和编解码器（用于远程）
@Message public class GetUser <: Request<Option<User>> { public let id: Int64 /* init */ }
@Message public class CreateUserCmd <: Request<User> { public let body: CreateUser /* init */ }

// 经典 Actor：@Actor 宏根据 onXxx 方法生成 receive；m.reply(...) 直接完成调用方的 Completion
@Actor
public class UserRegistry {
    let users = HashMap<Int64, User>()
    var nextId = 0
    func onGetUser(m: GetUser): Unit { m.reply(users.get(m.id)) }
    func onCreate(m: CreateUserCmd): Unit { nextId++; let u = User(nextId, m.body.name); users.add(u.id, u); m.reply(u) }
}

let reg = system.spawn("users", props { => UserRegistry() })
reg << Touch()                                                     // tell
let u: Option<User> = reg.ask(GetUser(1), timeout: 3.seconds)      // 返回类型由 Request<R> 推断；超时抛 AskTimeoutException

// 类型化 Actor：TypedBehavior 构建器 + replyTo（Akka Typed 式）
enum CounterMsg { | Increment(Int64) | Get(TypedActorRef<Int64>) }
func counter(n: Int64): TypedBehavior<CounterMsg> {
    behavior<CounterMsg> { b =>
        b.onMessage { ctx, msg => match (msg) {
            case Increment(k) => counter(n + k)
            case Get(replyTo) => replyTo << n; Behaviors.same()
        } }
        b.onSignal(PostStop) { ctx => ctx.log.info("stopped") }
    }
}
let c: TypedActorRef<CounterMsg> = system.spawn("counter", counter(0))
let v = c.ask(timeout: 1.seconds) { replyTo => Get(replyTo) }

// ActorContext 扩充（P1）：self、sender、spawn、stop、watch、log、timers、pipeTo、reply
```

### 6.3 HTTP 服务端（Ktor 风格）

```cangjie
import cactor_http.*
import cactor_http_server.*
import cactor_http_server.plugins.*
import cactor_http_actor.*                 // 只有用到 call.ask 时才需要
import cactor_json.*

@Codec public class User { public let id: Int64; public let name: String /* init */ }
@Codec public class CreateUser { public let name: String /* init */ }

extend Application {
    public func userRoutes(registry: ActorRef): Unit {
        install(DefaultHeaders)
        install(CallLogging) { c => c.level = LogLevel.Info; c.filter { call => call.request.path().startsWith("/api") } }
        install(ContentNegotiation) { c => c.json() }
        install(StatusPages) { c =>
            c.exception<ValidationException> { call, e => call.respond(HttpStatusCode.BadRequest, ErrorBody(e.message)) }
        }
        install(createApplicationPlugin("Timing", { => Unit }) { p =>          // 环绕式钩子（对应 actix 的 from_fn）
            p.aroundCall { call, next =>
                let t0 = MonoTime.now(); next()
                call.response.headers.append("X-Response-Time", "${(MonoTime.now() - t0).toMicroseconds()}us")
            }
        })
        routing { r =>
            r.get("/health") { call => call.respondText("ok") }
            r.route("/api/users") { u =>
                u.get("/{id}") { call =>
                    let id = call.parameters.getAs<Int64>("id")            // 依赖 std.convert.Parsable；失败时 → 400
                    match (call.ask(registry, GetUser(id))) {              // 超时 / 过载 → 503
                        case Some(user) => call.respond(user)
                        case None => call.respond(HttpStatusCode.NotFound)
                    }
                }
                u.authenticate("api") { s =>
                    s.post { call =>
                        let body = call.receive<CreateUser>()               // 415 / 400 / 413 由 ContentNegotiation 和 BodyLimit 处理
                        call.respond(HttpStatusCode.Created, call.ask(registry, CreateUserCmd(body)))
                    }
                }
            }
            r.webSocket("/echo") { ws => for (f in ws.incoming) { ws.send(f) } }
            r.sse("/ticks") { sse => sse.send(ServerSentEvent(data: "tick")) }
        }
    }
}

// 不使用 Actor 的独立用法（只把它当 Web 框架）：
main(): Int64 {
    embeddedServer(Native, port: 8080) { app => app.routing { r => r.get("/") { call => call.respondText("hi") } } }
        .start(wait: true)
    0
}
```

**ApplicationCall 的主要 API**：
- 请求：`request.{method, uri, path(), headers, queryParameters, cookies, local, origin}`、`parameters`、`attributes`。
- 接收：`receive<T>()`、`receiveText()`、`receiveChannel()`、`receiveMultipart()`、`receiveParameters()`。
- 响应：`respond(v)`、`respond(status, v)`、`respondText`、`respondBytes`、`respondFile`、`respondBytesWriter { ch => }`、`respondRedirect`、`response.{status(), headers, cookies}`。

**插件 API**：
- 定义：`createApplicationPlugin(name, configPath?, createConfig) { p => p.onCall / onCallReceive / onCallRespond / aroundCall / on(CallSetup | CallFailed | ResponseSent) }`；`createRouteScopedPlugin` 用于按路由安装。
- 执行顺序：先 install 的插件在外层。
- 同一个插件重复安装会报错。

### 6.4 HTTP 与 Actor 的融合（`cactor_http_actor`）

| API | 语义 |
|---|---|
| `call.ask(ref, req: Request<R>, timeout?): R` | 经典 Actor。超时默认取 RequestTimeout 的剩余时间；在 HTTP 协程中等待时不自旋；目标邮箱满时抛 `ActorOverloaded`，映射为 503 + Retry-After；请求取消时，之后才到的回复只计入指标 |
| `call.ask(typedRef, timeout?) { replyTo => Msg(...) }` | 类型化 Actor，语义同上 |
| `system.install(HttpServer) { c => c.port; c.module { app => } }` | 带 Actor 场景下的入口：配置来自 `[cactor.http.server]`；停机注册到 §5.6 的各个阶段；`/ready` 与集群成员状态联动 |
| `embeddedServer(engine, ...) { }` | 不带 Actor 场景下的入口；与上一行共用同一个 Application 和引擎 |
| `r.webSocketActor("/chat", props)` | 每个连接 spawn 一个 Actor：读循环把帧 tell 给它；写操作在 Actor 内串行完成；心跳使用 Actor 定时器；写缓冲有上限 |
| `system.install(HttpClient) { }`、`client.requestAsync(req).pipeTo(self)` | 在 Actor 内调用 HTTP 客户端的唯一推荐方式（`receive` 中禁止阻塞） |
| `call.application.actorSystem` | 获取当前 Application 绑定的 ActorSystem |

**原则**：
- Actor 不感知 HTTP。
- HTTP 不感知 Actor 的内部实现。
- 两边只通过业务消息（`Request<R>` / `replyTo`）交互。

## 7. 关键机制设计

### 7.1 Scheduler（foundation.scheduler）

- **结构**：分层时间轮，tick 默认 1ms，三层（1ms × 512、0.5s × 512、256s × 512）。由单个协程推进，空闲时按下一个到期时间休眠。
- **接口**：`scheduleOnce(delay, task): Cancellable`、`scheduleAtFixedRate(...)`、`scheduleWithFixedDelay(...)`。
- **时钟可替换**：`Clock` 接口有 `MonotonicClock` 和 `VirtualClock`（供 testkit 使用）两种实现。
- **使用方**：请求超时、keep-alive 和头部读取超时、WebSocket 心跳、客户端退避、Actor 定时器（`ctx.timers`）、ask 超时。
- 修复 typed scheduler 忽略延时的问题。
- **性能约束**：每个请求的“登记 + 取消”开销 < 100ns；10 万个定时器同时存在时，推进的 CPU 占用 < 1%。

### 7.2 统一 ask（core.ask）

```
Completion<R>    状态：等待中 / 已完成 / 已失败 / 已取消；await(timeout, spin)；回调；被取消后才到的回复计数
Request<R>       抽象类 <: Message，内部持有 Completion<R>（进程内）；reply(v) 直接完成，不查路径；
                 远程场景下序列化为临时路径 /temp/<id>（由 runtime 注册，R6 实现）
PromiseRef<R>    <: TypedActorRef<R>，tell 即完成 Completion（replyTo 写法使用）
ask 入口         ActorRef.ask(req: Request<R>, timeout, spin?)、TypedActorRef<T>.ask(timeout) { replyTo => T }
投递策略         默认 tell；cactor_http_actor 使用 tryTell（有界邮箱满时立即失败 → ActorOverloaded）
```

- **自旋策略**：
  - Actor 之间的 ask 默认自旋 50µs（保持现有的低延迟）。
  - 在 HTTP 协程中 spin=0。
  - 通过 `Config` 可以调整。
- **旧 API 兼容**：`Ask`、`AskPatternManager`、`TypedAskPattern` 改为转调新内核，并标记废弃。`real_benchmark` 的 ask 场景必须保持 p50 ≤ 6µs。

### 7.3 邮箱容量与过载

- **规则统一**：一种邮箱只有一套容量规则，所有入队（包括自发消息、系统消息之外的定时器消息）都计入容量。
- **满了以后的策略**（`OnFull`）只能在 Props 中配置：`Reject`（拒绝）、`DropOldest`（丢弃最旧）、`DropNew`（丢弃新消息）、`BlockSender`（只允许非 Actor 的发送方使用）。
- **默认无界**：保持现有 `CellMailbox` 的性能。有界邮箱用一个原子计数器实现，只有选择了有界邮箱才付这个开销。
- **过载的可观测性**：拒绝次数、丢弃次数、邮箱深度都作为指标导出。

### 7.4 插件内核（foundation.plugin）

```
Plugin<H, C>         name、configPath、createConfig、install(host, config) → PluginInstance
HookRegistry<H>      在 install 时登记钩子；在 start / freeze 时展平成数组（请求路径上不查 Map、不加锁）
宿主                 ActorSystem（SystemPlugin）、Application（ApplicationPlugin / RouteScopedPlugin）、HttpClient（ClientPlugin）
配置                 Config 中 configPath 对应的段 → 生成 C 的默认值 → 再执行代码中的 configure 闭包覆盖
冲突                 重复安装报错；插件之间的依赖通过 requires(OtherPlugin) 声明，安装顺序不满足时报错
```

**环绕式钩子 `aroundCall`** 编译成闭包链，执行顺序为“先安装的在外层”；`onCall` 等普通钩子是数组遍历。

### 7.5 路由树（http_server.routing）

- **构建阶段**：`RouteBuilder` 收集路由；`start()` 时冻结为不可变的前缀树。
  - 节点类型：常量段（哈希）、参数段、可选参数段、通配段、尾部通配段、正则段。
  - 选择器（method、header、accept、param、host）挂在叶子上。
- **匹配**：按 Ktor 的质量规则：常量 > 参数 > 通配 > 尾部通配，选择器质量高的优先，与注册顺序无关。
  - 路径不匹配返回 404；路径匹配但方法不匹配返回 405（带 `Allow` 头）。
  - `trace {}` 可以输出路由解析过程。
- **路由模板**（例如 `/api/users/{id}`）记录在 call 上，供指标、日志、OpenAPI 使用。
- **性能约束**：50 条路由时，单次匹配 < 200ns。

### 7.6 引擎接口与 Native 引擎

```
ApplicationEngine   start(app, config) / stop(grace, deadline) / connectors / events
NativeEngine（P5）   Acceptor × N（达到连接上限时暂停 accept；EMFILE 时退避 500ms；出错后自动重启）
                    Connection 协程：读缓冲（8KiB 起步，按高低水位复用）→ H1Parser（增量解析、零拷贝切片、header 按需解码）
                    请求上限检查 → 执行请求 → H1Writer（预先渲染状态行和 Date 头；写缓冲达到 32KiB 时 flush 形成反压）
                    流水线：最多排队 16 个请求，响应批量写出；对象池：请求、响应、ApplicationCall、header 数组
StdxEngine（P3）     自定义 Distributor（所有路径都交给 Application）；显式设置四个超时；注入日志适配器（把连接关闭的 WARN 降为 DEBUG）；
                    包装 listener 实现连接数上限 [G]；h2 / TLS 场景的默认引擎
```

### 7.7 请求体与流

- `ByteReadChannel.read(buf)` 是阻塞读：协程读得慢，TCP 窗口就收紧，形成连接级背压。未读完的请求体在响应结束时自动丢弃。
- **两层上限**：
  - 全局 `maxContentLength` 默认 8m。
  - 按类型的默认值：JSON 2m、表单 16k、文本 / 字节 1m。
  - `BodyLimit` 插件可以按路由覆盖。
  - **流式读取同样受全局上限约束**（补上 actix 的缺口）。
- **响应**：小响应走 Strict 快路径；大响应用 `respondBytesWriter`；`respondJsonStream(iterator)` 输出 JSON 数组或 NDJSON。

### 7.8 运行时资源划分规则

1. **HTTP 协程中的 ask 不自旋**；Actor 之间的 ask 保持自旋。
2. **`receive` 中禁止阻塞**：需要 IO 时用 `pipeTo(self)`；用 lint 检查 Actor 类中对 `HttpClient` 同步方法的调用。
3. **阻塞型 Actor 使用 `"blocking"` 调度器**（对应 actix 的 SyncArbiter）。
4. **过载时快速失败**：邮箱满时 ask 立即返回 503，不在请求协程中排队。
5. **dispatcher 的线程数和自旋时间**在 P5 中按“线程数 × 自旋时间 × 场景”的矩阵测出推荐值，写进 `Config`。在有 CPU 配额的环境中必须重新验证：自旋会直接消耗配额并引发限流（§3.5）。

### 7.9 默认值最终表

| 参数 | Akka HTTP | actix-web | Ktor | **CActor** | 理由 |
|---|---|---|---|---|---|
| keep-alive 空闲 | 60s | 5s | 引擎相关 | **60s** | 必须大于负载均衡器的空闲超时（例如 ALB 默认 60s），否则会出现 502 |
| 请求头读取超时 | 包含在 idle 中 | 5s，返回 408 | — | **10s，返回 408** | 防慢速攻击，并兼顾移动网络 |
| 请求处理超时 | 20s，返回 503 | 无 | 无 | **20s，返回 503** | 防止 handler 卡死 |
| 断连 linger | 1min | 1s | — | **2s** | 尽快释放资源 |
| 最大连接数 | 1024 | 每个 worker 25k | 无 | **10,000** | 协程开销小；达到上限后暂停 accept |

## 9. 验收标准

### 9.1 性能

**测量规则**（来自 §3.5 的教训）：
1. 先读 `/sys/fs/cgroup/cpu.max`，确保服务端核数加压测端核数不超过配额；默认服务端 2 核、压测端 2 核，各框架的 worker 数等于服务端核数。
2. 每轮测量前后读取 `cpu.stat` 中的 `throttled_usec`，有限流就作废并重测；机器上不能有其他负载。
3. 压测工具用 oha / wrk2；报告 rps、p50 / p99 / p99.9、服务端 CPU 占用和每核 rps。
4. 正式发布的数据应在没有 CPU 配额的独立机器上测得。
5. 每次改动都要先测量再合入；结果追加到 `20261028-performance.md` 的 HTTP 章节。

| # | 场景 | 目标 |
|---|---|---|
| P1 | plaintext，并发 1 / 16 / 64 / 256 / 1024 | 验收线：≥ Akka，p99 ≤ Akka；挑战线：每核 ≥ actix-web × 0.5 |
| P2 | JSON，10 个字段 | ≥ Akka（Jackson） |
| P3 | 50 条路由 + 路径参数 + query + JSON 请求体 + 5 个插件 | ≥ 裸引擎 × 0.85，且 ≥ Akka |
| P4 | 每个请求做一次 Actor ask | ≥ Akka（ask + onSuccess）；`call.ask` 的额外开销 ≤ 2µs；参照 actix-web 的 `addr.send` |
| P4b | Actor 过载（有界邮箱，请求速率是处理能力的 3 倍） | 快速返回 503；成功请求的 p99 不随时间增长；内存平稳 |
| P5 | 短连接 | 每秒新建连接数 ≥ Akka |
| P6 | 100MB 流式上传 / 下载 | 吞吐 ≥ Akka；RSS < 64MB |
| P7 | 1 万个 WebSocket 连接 echo | ≥ Akka |
| P8 | 客户端，并发 256 | ≥ Akka `singleRequest` |
| P9 | 10 万个空闲 keep-alive 连接 | 每连接内存 ≤ Akka |

### 9.2 稳定性（纳入 CI；长时间项每晚运行）

| 类别 | 用例 | 期望 |
|---|---|---|
| 上限 | URI、header 数量、头部大小、请求体（声明长度、chunked、流式读取三种情况） | 414 / 431 / 413；连接按协议规定关闭；不 OOM |
| 超时 | 头部发送缓慢；handler 卡住；keep-alive 空闲 | 408；503（并取消挂起的 ask）；连接关闭 |

| 异常 | handler、Marshaller、插件抛异常 | 500；连接可以复用；Actor 系统不受影响 |
| 优雅停机 | 1000 并发压测期间发送 SIGTERM | 在途请求零丢失；新请求返回 503；`/ready` 先返回 503；在 deadline 内退出 |

| HTTP/2（开启后） | h2spec；Rapid Reset、CONTINUATION 洪泛 | 通过；超过阈值后发 GOAWAY |
| 客户端 | 对端 RST、半关闭、DNS 失败、TLS 失败、不发送 SNI 的场景 | 有界重试；错误类型明确；连接池不泄漏 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Native 引擎的工作量和质量（解析器安全） | 性能目标、安全 | P3 / P4 先用 stdx 引擎交付功能；Native 引擎与 stdx 引擎共用测试集，并加上协议加固用例和模糊测试；达到验收线之前不切换默认引擎 |
| stdx 的缺陷（#402 h2 丢数据、#405 不发送 SNI）和二进制依赖（OpenSSL、cjc 版本绑定） | 功能、部署 | h2 默认关闭；客户端补 SNI；问题提交上游；stdx 只在 json、http*、integration 中使用；CI 固定版本 |
| 仓颉不能把协程绑定到线程，做不到 actix 的“每核一个 worker、不共享状态” | 性能上限 | 用冻结的不可变结构、连接独占缓冲、多个 accept 循环来近似；挑战线定为 actix 的 50% |
| 语言能力假设不成立（§12） | API 形态 | P0 先验证；每项都有退路 |
| 测量环境失真（CPU 配额、压测器瓶颈、其他负载） | 结论错误 | 按 §9.1 的规则执行；正式数据在独立机器上测 |
| API 重构破坏现有用户 | 兼容性 | 1.3–1.6 期间新旧 API 并存，旧 API 转调新实现；2.0 再删除；用 API 快照守住变化 |
| Actor 层性能退化（插件、有界邮箱、ask 改造） | 性能 | 不装插件时零开销；有界邮箱按需付出开销；每个 P 阶段都跑 `real_benchmark`，相差 ±3% 以内 |
| 许可证污染 | 法律 | 只参考 Ktor、Pekko HTTP、actix 的代码（Apache-2.0 或 MIT），以及公开文档；不参考 BSL 期间的 Akka 代码和 MulanPSL 的 cjoy |
| 工作量超出预期 | 进度 | 先交付最小可用版本；P8 / P11 可以按插件拆开、分批发布 |

### B.2 stdx.net.http 主要参数（来源：`stdx/net/http/server.cj`、`client.cj`）

| 项 | 默认值 / 说明 |
|---|---|
| `readTimeout` / `writeTimeout` / `readHeaderTimeout` / `httpKeepAliveTimeout` | 全部为 `Duration.Max`（Stdx 引擎会显式设置） |
| `maxRequestHeaderSize` / `maxRequestBodySize` | 8192 / 2MiB |
| `servicePoolConfig` | 容量 10000，队列 10000 |
| `distributor` | 默认是精确匹配的 HashMap，不能注册 `*`（Stdx 引擎替换为自定义实现） |
| `logger` | 默认输出到 stdout，INFO 级别；每个正常关闭的连接都会打一条 WARN [V] |
| h2 | maxConcurrentStreams 100、initialWindowSize 65535；#402 |
| `closeGracefully()`、`afterBind`、`onShutdown`、`updateCert` | 生命周期与证书热更新 |
| 客户端 | `poolSize` 默认 10（唯一的连接池参数）；读写超时 15s；自动重定向；CookieJar；代理；#405 |
| WebSocket | `upgradeFromServer` / `upgradeFromClient`；单帧硬上限 20MB；没有心跳 |
